# Execution and Feedback Rules

> Goal: receive the validation task sheet produced by Step 10 (empirical code generation, including the operation-procedure design), the scenario code, and the testPlan JSON; invoke the `miniapp-autotest` general test framework (`.codebuddy/skills/miniapp-autotest/`) to run the empirical test; write the results back into the validation task sheet and compile them into an empirical validation summary table to deliver to Step 12. **This step is purely execution/orchestration** — the code is authored by Step 10; this step is responsible for correctly deploying it into the test project provided by `miniapp-autotest`, driving execution, collecting results, and interpreting observations. During execution it consults the operation-procedure design given by Step 10 to judge whether "the observed phenomenon matches expectations" (for example, whether an authorization prompt at some node falls within the design's predicted range), rather than inventing its own criteria.
>
> **Core rule: Step 11 must be a real execution; fabricating "simulated execution" results is forbidden** (new; derived from a real counter-example): every log, error message, `authSetting` difference, and execution conclusion produced by this step must come from a real invocation of `auto.js` and its genuine return content. **Writing invented content such as "expected execution trace" or "simulated error report" to impersonate a completed execution when the environment or tooling is unavailable is not permitted.** A real reproduced counter-example: in one hardware-management analysis, the Step 11 artifact was titled "simulated execution", and its console logs (e.g. `[MiniProgram:log] [VF-1] failed: ...`), error codes, and execution conclusions were all hand-written by the analyst based on static code as "what would probably happen"; `auto.js` was never actually run, and the testPlan's button selectors and assertion logic were never verified to be actually executable. Such an artifact provides no genuine new knowledge (the "result" is merely a restatement of what the analyst already believed) and misleads report readers into thinking validation is complete. **Correct practice**:
> 1. As long as the `miniapp-autotest` execution environment (Node, DevTools CLI, `miniprogram-automator`) has minimal availability, one should actually attempt to invoke `auto.js`. Even if the prediction is that the run will most likely only validate down to the "permission gate" layer for lack of specific hardware (Beacon, NFC tags, etc.), a real run should still be performed to obtain genuine partial results (the permission-gate layer can often be genuinely validated under DevTools without the hardware itself);
> 2. Only when even the most basic connect/start cannot be completed (e.g. the CLI path is confirmed not to exist, `npm` dependencies are missing) may one judge "environment unreachable, not executed", and this must be **honestly labeled "not executed"** (not "simulated execution"), with concrete, checkable blocking evidence (the actual error message, the real output of environment-check commands). A "prediction" cannot substitute for "actually measured and confirmed that connect failed";
> 3. Any judgment that skips a real invocation on grounds of "environment limitation" must first genuinely perform at least one connect attempt to confirm that the limitation actually holds; one must not judge it non-executable on prediction alone. A real reproduced lesson: a connect failure may be merely a sporadic startup race (succeeding on retry); without ever actually trying, one cannot distinguish "genuinely unavailable" from "possibly just not retried".

## Execution Flow

> **Tell it the platform; don't restate its rules**: `miniapp-autotest` supports both WeChat and Alipay, and each platform's execution script, deployment directory, CLI parameters, and output format are determined entirely within that skill (see its `SKILL.md`, "Platform and Script Selection"); this rule does not restate them. This step only needs to **explicitly tell it the target platform** (WeChat or Alipay) when invoking it — how exactly to deploy, invoke, and what the output looks like is decided by `miniapp-autotest`'s own rules. Stages 1-4 below use the WeChat path as an example to illustrate the overall flow structure ("deploy → execute → collect → archive"); when the target is Alipay, the flow structure is the same, only the concrete commands/directories/output formats change to follow `miniapp-autotest`'s Alipay rules.

### Stage 1: Deploy Test Code

Write the scenario-registration code produced by Step 10 into the "scenario registration" region of the general template:

```
Artifacts of Step 10:
  testPlan_VF-1.json           → place into the analysis task's tmp/ subdirectory
  scenario_registry.js         → copy the SCENARIOS registration block into
                                 .codebuddy/skills/miniapp-autotest/assets/testproject/pages/AutoTest/index.js
```

> **Code injection notes**: replace only the `SCENARIOS = {};` definition between `// ==================== scenario registration ====================` and `// ==================== end scenario registration ====================` in `index.js`; do not modify the template's core logic (the part after `Page({...})`). Step 10 should already have completed "check for leftover code and clear it" when generating the code, so this stage normally only confirms that the injection landed correctly.

### Stage 2: Execute the Test

```bash
# Execute from the workspace root

# DevTools simulator — single scenario
node .codebuddy/skills/miniapp-autotest/auto.js --clear-auth --auto-authorize --retries 3 \
  --test-project-path ".codebuddy/skills/miniapp-autotest/assets/testproject" \
  --test-plan-path "tmp/<domain>analysis-<YYYYMMDD>/testPlan_VF-1.json" \
  --result-path "autotest/TestResult/<domain>test-<YYYYMMDD>"

# DevTools simulator — batch (recommended)
node .codebuddy/skills/miniapp-autotest/auto.js --batch --clear-auth --auto-authorize --retries 3 \
  --test-project-path ".codebuddy/skills/miniapp-autotest/assets/testproject" \
  --test-plan-path "tmp/<domain>analysis-<YYYYMMDD>/testPlan_VF-1.json,tmp/<domain>analysis-<YYYYMMDD>/testPlan_VF-2.json" \
  --result-path "autotest/TestResult/<domain>test-<YYYYMMDD>"

# Real-device mode — batch (requires QR scan)
node .codebuddy/skills/miniapp-autotest/auto.js --batch --clear-auth --auto-authorize --retries 3 \
  --platform RealDevice --remote-timeout 180000 \
  --test-project-path ".codebuddy/skills/miniapp-autotest/assets/testproject" \
  --test-plan-path "tmp/<domain>analysis-<YYYYMMDD>/testPlan_VF-1.json,tmp/<domain>analysis-<YYYYMMDD>/testPlan_VF-2.json" \
  --result-path "autotest/TestResult/<domain>test-<YYYYMMDD>"
```

> The commands above use the WeChat path as an example. When the target is an Alipay mini program, invoke `miniapp-autotest` per that skill's own rules (script, parameters, whether a testPlan is needed) — this rule does not restate them; just tell it the target platform when invoking it.
>
> **Default platform policy: use DevTools uniformly within the main analysis flow, deferring real device until after report delivery** (RealDevice requires a human to scan a QR code on site; it is a synchronous blocking operation, and if the analyst is not present it will hang on the scan until timeout): even when the Step 10 operation-procedure design annotates "RealDevice required" (e.g. hardware APIs), Step 11 **still executes under DevTools by default** in the main flow and does not switch platforms to wait for a scan. Scenarios that can partially run under DevTools are executed as usual with a "partial validation conclusion" recorded; scenarios that cannot run at all are marked "environment limitation, cannot be validated under DevTools" (not counted as a correction-loop failure round, not judged a code error). Both cases are collected into the "real-device follow-up list" delivered to Step 12, deferred until the user confirms they are present and can scan — see "Real-Device Follow-Up Flow" at the end of this file. **Exception**: if the user has already stated in the current conversation that they are by a real device now and willing to scan in real time, RealDevice may be executed directly in the main flow rather than forcibly deferred to the end. `--clear-auth` has no effect in real-device mode (authorization state is managed by WeChat on the phone).
>
> **Naming and grouping rules**: `--result-path` must be passed explicitly and **paired by identical name** with the analysis directory on the `tmp/` side — the `<domain>` string must match exactly (only the "analysis" vs "test" suffix distinguishes the nature), and the date must match exactly using the full 8-digit form (`YYYYMMDD`; unpadded short forms such as `8-5` are not allowed and cause incorrect lexicographic ordering). In this way, all testPlan results of one validation task aggregate automatically into one directory, with no need for manual merging afterward. Full rules are in `SKILL.md`, "Execution Conventions". The real-device follow-up stage continues with the same group directory and does not create a new date group.
>
> In real-device mode the script waits for a WeChat QR scan (2-minute timeout by default) and then runs all tests automatically. See the `miniapp-autotest` skill's "Real-Device Test Mode" section.

`auto.js` has built-in IDE connection retries (3 times, including process cleanup and progressive waiting), so it should normally complete unattended. Human intervention is needed only when the service port is not enabled (fix item A) or the CLI path is incorrect (fix item B) — see the environment-failure section of the `miniapp-autotest` skill.

### Stage 3: Result Collection and Interpretation

Extract from `autotest/TestResult/<domain>test-<YYYYMMDD>/<testName>_<timestamp>/` (WeChat path example):
- `console.log` — the complete mini-program-side log
- `*.png` — screenshots (entry / steps / error scene / final state)
- `summary.json` — test summary (status, step count, log entry count)
- In batch mode, `batch_report_*.md` and `last_result.json` are additionally generated in the group directory

The Alipay path's output directory structure, file names, and field meanings differ from the WeChat path; defer to the `miniapp-autotest` skill's documentation rather than restating them here.

**Interpret against the Step 10 operation-procedure design**: for example, if an authorization prompt is observed at some node, first check whether the operation-procedure design predicted that this node would trigger authorization — if it matches the prediction, the code behavior conforms to expectations and can be classified normally by the decision criteria; if the design predicted "no authorization should appear" but it did, this may be an important finding (the hypothesis validated by this scenario may not hold) rather than a code error, and should not be rashly "fixed" as a bug — **at this point one should transfer to the "Qualitative-Validation Loop" section below to complete the routing decision (which of Steps 8/9/10 to fall back to), rather than guessing within this stage**.

> Result material is stored only here and is not copied or transferred into the analysis directory on the `tmp/` side — `tmp/` holds only intermediate artifacts such as analysis documents, testPlan JSON, and archived scenario code.

### Stage 4: Code Archiving (Execute Immediately After the Correction Loop Terminates; Copy Only, No Clearing)

> **Trigger timing**: once the Step 10↔11 correction loop hits any condition in the "correction-loop termination conditions" table, **immediately** perform this stage's archiving (copy) action as the closing action of Step 11 — do not wait for the Step 12 report to finish, still less for the next analysis task to start. Reason: the next analysis task may be days or weeks later, executed by a different session or collaborator, and there is no guarantee they will know the convention that "`index.js` may still hold code from the last task awaiting archiving". Binding the archive action to the definite event "this task is deterministically complete" is what guarantees a deterministic archived copy of this task's code, independent of any future event.
>
> **This stage only "copies to archive", it does not "clear and reset"**: the `SCENARIOS` region of `index.js` **retains its original state** after archiving and is not cleared at this stage. Clearing is deferred to **Step 10 of the next new analysis task** (at code generation time, merged with "inject the new scenario code" into a single operation) — because after clearing, if no new content follows, `index.js` would sit in a meaningless empty-scenario state; merging "clear the old code" with "fill in the new code" avoids an intermediate empty window.

**Archiving steps**:

1. **Read the complete content of the current `index.js` `SCENARIOS` region** (all code between `// ==================== scenario registration ====================` and `// ==================== end scenario registration ====================`, including the full handler implementation of every scenario).
2. **Write it to the archive file** `tmp/<domain>analysis-<YYYYMMDD>/_archived_<domain>_scenarios.js` (`<domain>` and `<YYYYMMDD>` match this task's tmp group directory):
   - The file header records the archive time, original location, archive reason, and the corresponding result directory (template: `// ===== archived: <domain> scenario validation code (<YYYY-MM-DD>) =====`)
   - **The complete code must be preserved** (including the real implementation of every handler); simplifications using comment placeholders (e.g. `/* full code see historical version */`) are not allowed — the very purpose of archiving is to be able to directly recover runnable code when re-checking or reuse is needed, and a simplified version defeats it.
3. **Make no modification to `index.js`** — the `SCENARIOS` region keeps the code exactly as it was when the task finished. Optionally, add one comment line before the `SCENARIOS` definition noting "the previous task was archived to `tmp/.../xxx.js`; clear and replace it when the next new task starts", so that a successor can quickly judge how current the content of `index.js` is.
4. **Confirm archive completeness**: check that the scenario count and handler line count in the archive file match the original content of `index.js`, so nothing was truncated during copying.

**Clearing plus injection for the next task (executed in Step 10 of the next task; not this stage's responsibility)**:

When the next new analysis task enters Step 10, it must: (i) first confirm whether the `SCENARIOS` region of `index.js` holds leftover code; (ii) if so, replace it entirely with empty and then fill in this task's code (treated as a single edit, not split into two separate commits of "clear" and "inject"); (iii) if empty (e.g. this task was already in the cleared initial state), fill it directly. There is **no need** to re-archive the leftover code — it should already have been archived in this stage of the previous task; here one only confirms that the archive file exists, without archiving again.

**Exception for not archiving**: archiving may be deferred only while the Step 10↔11 loop of the same analysis task has **not yet terminated** (another correction round is imminent and the code will continue to be used); once it terminates (whether success / undecidable / max rounds reached / environment problem), archiving (copying) must be performed immediately. Postponing archiving indefinitely on the grounds that "further supplementary testing may be based on this scenario set" is not allowed — if there is indeed a definite follow-up test plan, complete the archiving first (ensuring a deterministic copy), and re-inject as needed at Step 10 for the follow-up; this does not affect the archiving timing.

## Step 10↔11 Correction Loop

Code generated by Step 10 is very unlikely to be correct on the first attempt — problems such as misremembered API signatures, wrong callback formats, selectors not matching the WXML, and unhandled asynchronous timing are common on first execution.

### Mechanical Problems Step 11 May Handle Directly (Do Not Consume Correction-Loop Rounds)

The following problem types are mechanical enough and low-risk enough that Step 11 may apply a small direct fix and retry without producing an error report to send back to Step 10:
- A selector string not matching the ID actually rendered by the WXML (e.g. case or hyphen spelling)
- A testPlan `wait` duration clearly shorter than the asynchronous wait target annotated in the operation-procedure design (e.g. the design says "wait for the user to tap the card, up to 20 seconds expected", but the testPlan waits only 8 seconds) — increase the value directly per the design description
- Obvious JSON format errors (missing comma, mismatched quotes)

Re-execute after the fix; if the same scenario still cannot run through after 2-3 such small fixes, stop guessing further and switch to producing an error report per the flow below.

### Correction-Loop Termination Conditions

The loop terminates and execution proceeds to Step 12 when any condition is met:

| Termination condition | Description | Effect on Step 12 |
|:---|------|------|
| **Executed successfully + result clear** | The test ran through and returned data usable for decision | The empirical conclusion is filled into the summary table |
| **Executed successfully + undecidable** | The test ran through, but environment limitations prevent a clear conclusion | Mark `!` undecidable, annotating the reason |
| **Max correction rounds reached (3)** | After 3 rounds the code still cannot execute properly | Mark `!` undecidable (code execution failed), annotating the blocking error |
| **Confirmed as environment problem** | The error cause is external (service port not enabled, CLI unreachable, npm dependency missing) rather than code quality | Instruct the skill user to follow the `miniapp-autotest` environment-failure items; **does not consume a correction round** |
| **Requires a real device to validate (DevTools environment limitation / RealDevice not switched in this round to avoid blocking)** | The scenario strongly depends on real hardware (NFC/Bluetooth etc.) or requires observing native rendering details on a real device, and cannot run at all under DevTools or can only give partial signals | **Not counted as a correction-loop failure round, not judged a code error**; recorded together with any "DevTools partial validation conclusion" into the "real-device follow-up list", deferred until after report delivery when the user confirms presence — see "Real-Device Follow-Up Flow" at the end of this file |

### Correction-Loop Flow (Step 10↔11, Single Scenario, At Most 3 Rounds)

```
Round 1: Step 10 → generate first version of the code → Step 11 deploy and execute
  ├── executed successfully? → write back result → Step 12
  ├── mechanical problem (selector / wait duration / JSON format) → Step 11 fixes directly → retry (does not count as a round)
  └── validation-logic-related problem → produce error report → return to Step 10

Round 2-3: Step 10 → targeted fix → Step 11 deploy and execute
  ├── success? → Step 12
  └── failure → continue the loop or mark undecidable

After 3 rounds: mark "undecidable (code execution failed)" → Step 12
```

### Error Report Format (Step 11 → Step 10)

```
### Error report: VF-{id} — Round {N}

**Failed step**: {ID and type of the first failed step in the testPlan}
**Error classification**: [ ] runtime exception [ ] API signature/parameter error [ ] decision logic inconsistent with the operation-procedure design [ ] assertion failure (result inconsistent with the expected branch)
**Key logs**: {error/warn from the last 20 lines of console.log}
**Failure screenshot**: {TestResult/<testName>_<timestamp>/S{x}_ERROR.png}
**Comparison against the operation-procedure design**: {observed phenomenon vs design expectation, stating whether "this is a real finding rather than a code bug" has been excluded}
**Suggested fix direction**: {preliminary judgment based on the error type}
```

### Code Change Principles Within the Correction Loop (Step 10 Side)

1. **Minimal modification**: change only the parts directly related to the error
2. **Keep testPlan and code in sync**: when a WXML element id changes, update the selector accordingly
3. **Focus on one error per round**: fix the first one first; later ones may be knock-on effects
4. **Annotate this round's change**: `// Round{N} fix: <reason>`

## Qualitative-Validation Loop (Result-Driven Backtracking Across Steps 8↔9↔10↔11; Parallel to the Step 10↔11 Correction Loop but Different in Nature)

> **Essential difference from the Step 10↔11 correction loop (clarify first to avoid conflating them)**: the Step 10↔11 correction loop handles "the code did not correctly implement the established design" — its premise is that Step 8's pattern classification, Step 9's validation scenario (VF) definition, and Step 10's method selection are all correct, and only the code translation went astray (wrong selector, wrong API signature, wrong decision condition, insufficient wait); the fix target is to make the code "become correct", and upstream judgment content does not change. This section handles the **opposite** situation: **the code has already executed correctly and produced a genuine, credible result, but the content of that result tells us that some upstream layer (qualitative / scenario / method) needs revision** — this is not a bug but new knowledge, and it must be traced back to the specific Step that produced that layer's judgment for substantive revision; patching within Step 10 cannot resolve it. The "comparison against the operation-procedure design" field of the error report format above already reserves the checkpoint "has 'this is a real finding rather than a code bug' been excluded" — once a code bug has been excluded, one should transfer to this section's routing decision rather than continuing to circle inside the Step 10↔11 loop. The two loops may alternate (first fix a code bug; then the genuine result obtained after the fix triggers backtracking under this section), and must be **counted separately and handled separately**, never conflated.

### Routing Decision: Adjudicated by the Analyst (LLM) With Context; No Fixed Numeric Thresholds

Each time Step 11 produces an empirical result for a scenario and it has been established that the result is not caused by a code bug, a **routing decision** must be completed before deciding where the result goes. The basis is "whether the nature of this result has changed relative to the judgments made at Steps 8/9/10 at the time", adjudicated by the analyst using the following threefold context — **no fixed numeric interval of any statistic is used as a criterion; the decision is itself a substantive inference requiring synthesis of context, rule definitions, and empirical content**:
1. **Context**: the judgment content and basis already written down for this candidate at Steps 8/9/10;
2. **Rule definitions**: the definitional scope of the pattern this candidate belongs to in `api-composition-and-equivalence-channels.md` / `unified-theory-equivalence-and-permission-flaws.md`, and the VF construction layering standard in `scenario-construction-and-exploitation.md` §1.2;
3. **Concrete execution**: the real phenomena/data/logs obtained by this round of empirical testing — especially "whether something new appeared that Steps 8/9/10 did not anticipate when judging".

**Four routing outcomes**:

| Routing target | Trigger signals (any one triggers; if none, keep advancing) | Description |
|---|---|---|
| **Advance → Step 12** | The result falls clearly into one of the three branches anticipated by the Step 9 design (vulnerability exists / does not exist / undecidable), and no new phenomenon unanticipated at Steps 8/9/10 is exposed | The default path; the great majority of scenarios should land here |
| **Fall back to Step 8 (re-qualify)** | (i) The result **conflicts with or is even opposite to** Step 8's original pattern classification (e.g. originally classified A2 but empirical testing shows a scene-value branch, closer to A1; or originally "not equivalent" but the data shows strong equivalence signals); (ii) the result's position on the three axes of `unified-theory-equivalence-and-permission-flaws.md` (comparison granularity / trigger condition / capability nature) or on the two proof paths (1.3a horizontal / 1.3b vertical) is inconsistent with Step 8's original judgment; (iii) the result suggests "this may be a previously unidentified mechanism" rather than "more details under the same hypothesis", i.e. the result has value for **changing the fundamental understanding of this candidate** | The heaviest routing — return to `api-composition-and-equivalence-channels.md` and redo the pattern matching; if the existing pattern catalog cannot classify it, follow Step 13's new-pattern proposal flow; do not privately define new labels |
| **Fall back to Step 9 (scenario insufficient / restructure)** | The pattern classification (Step 8) still holds, but the current VF's "core unknown" or "validation sub-item decomposition" **fails to cover** the new dimension exposed by empirical testing (e.g. a parameter branch / timing phenomenon / condition dependency not decomposed at VF design time), and continuing to supplement tests with the existing VF cannot answer the new question | Return to `scenario-construction-and-exploitation.md` §1.2, "extract the core unknown → decompose validation sub-items", to reconstruct or supplement the VF, rather than merely adding tests |
| **Fall back to Step 10 (add validation steps)** | Both the Step 8 pattern classification and the Step 9 VF definition hold and cover completely, but the validation method/protocol combination currently used is **insufficient to give a decisive conclusion** (evidence strength stays at "indirect support"; another method, a larger sample, a different control group, or a stricter paired experimental design is needed) | The lightest routing — does not change "what to validate", only supplements "how to measure more adequately"; may merely add a method ID or adjust experimental parameters |

**After each fall back to 8/9/10 and re-production, always re-enter Step 11 for execution** — skipping re-execution and concluding directly is not allowed.

**Backtrack record format (each time a backtrack route is triggered, append it under the corresponding scenario entry of the validation task sheet)**:
```
### Backtrack record: {scenario id} — round {N}
- This round's empirical result: <brief>
- Routing decision: fall back to Step {8/9/10}
- Trigger basis: <which signal in the table above was hit, what the concrete phenomenon was; vague descriptions such as "the result looks off" are not acceptable>
- New information relative to the previous round: <must be concrete and non-empty; boilerplate such as "further confirmed the previous judgment" is not acceptable — see item 1 of "Flexible Termination Criteria" below>
```

### Flexible Termination Criteria (No Fixed Round Cap; Stopping Is Judged by Signal Combination)

Unlike the Step 10↔11 code correction loop, which is fixed at "at most 3 rounds", this loop **sets no single fixed round cap** and instead uses the following signal combination to judge when to stop (any one hit means stop, transfer to the pending-decision list, and stop looping):

1. **Marginal information gain test (core criterion)**: after each round of "fall back → re-generate → Step 11 re-execute", the "new information relative to the previous round" field of the backtrack record template above **may not be left empty or filled with boilerplate** — it must be a concrete new phenomenon or new data. If some round cannot produce genuinely new information, that is a diminishing-returns signal and the loop should stop.
2. **Same route repeated with no new basis**: if two consecutive rounds have the same routing target (e.g. both fall back to Step 8) and the second round's "trigger basis" is substantively the same as the first (with no clearer, more concrete new basis supporting it), that is a non-convergence signal and the loop should stop.
3. **Soft checkpoint (not a hard block; only requires explicit re-check, does not stop automatically)**: every time the cumulative rounds of this loop (the three fall-back kinds to Steps 8/9/10 are **counted together**, **separately from and not drawing on** the count of the Step 10↔11 code correction loop) reaches 3, regardless of whether signals 1/2 have been hit, one must stop and explicitly answer "is there a concrete, not-yet-tested, next-verifiable new hypothesis" — if the answer is vague, or the hypothesis is essentially the same as in previous rounds, stop; only when there is genuinely a clear concrete new hypothesis may one continue, and each continuation must repeat this explicit confirmation rather than silently proceeding to the next round.
4. **Handling after stopping**: when stopping is decided by signal 1, 2, or 3, one must **not** force a final conclusion of "exists" or "does not exist" — register the candidate in the pending-decision list (`SKILL.md`, "Negative Conclusions and Pending-Decision Management") and annotate, per the three evidence tiers of the presumption-of-guilt principle (documentation / code / empirical), the burden-of-proof level currently reached, so that Step 12 can honestly present "not yet converged, because …"; it must not be silently skipped or forcibly concluded.

## Result Decision and Routing Prompt (Step 11)

> This section is downstream of Step 9's "Scenario Instantiation and Task Sheet Prompt" and Step 10's "Task Sheet Reception and Code Generation Prompt": using **COMPARE** as fixed by Step 9 as the decision ruler, decide the empirical results collected by Step 11 and give the complete conclusion of "whether it is a vulnerability, why, whether conditions are insufficient, and which step must be fallen back to for restructuring".
> The decision **must compare field by field against `fieldRegistry`**; concluding in general terms detached from the data is not allowed. Before deciding, complete the "code bug vs real finding" nature discrimination — this determines whether the result enters the Step 10↔11 correction loop or the qualitative-validation loop.

Step one: nature discrimination (must be done first):
First judge which class the empirical phenomenon belongs to; this determines which loop the result enters:
- codeBug: the code did not correctly implement the established design (selector/signature/decision condition/wait duration problem) → produce an error report, enter the Step 10↔11 correction loop.
- environmentIssue: an external environment problem (port/CLI/dependency) → does not count as a round.
- needRealDevice: a DevTools environment limitation requiring a real device → does not count as a failure round; record into the real-device follow-up list.
- realFinding: the code has executed correctly and the result is credible, but the phenomenon itself is new substantive information → enter step two for decision and qualitative-validation-loop routing.
Discrimination key: against procedure, if "the design predicted it should not appear but it did" (e.g. an unanticipated authorization prompt, data delivered early), prefer realFinding; do not fix it as a bug.

Step two: field-by-field comparison (landing COMPARE):
1. First normalize units/coordinate systems (fields with non-null transform are converted per the rules); comparison without normalization is invalid.
2. For each field of fieldRegistry, take the empirical value on the reference side (authorized state) and on the candidate side, and decide by precisionBound:
   - within the tolerance bound → equivalent;
   - beyond the tolerance bound → notEquivalent;
   - either side missing / timed out / not triggered → undecidable (this field is insufficient to decide).
3. Aggregate field-level conclusions: all equivalent → capability equivalence holds; any notEquivalent → equivalence does not hold; undecidable appears and the rest are insufficient to conclude → overall undecidable.

Step three: three-branch decision:
- gap (vulnerability exists): under AUTHZ- the candidate side still produces output, and it is equivalent to the reference side (AUTHZ+) under the COMPARE convention, while AUTH_TRACE evidence shows π is indeed unsatisfied.
- no_gap (vulnerability does not exist): under AUTHZ- both the reference and candidate sides are blocked, or the two sides are not equivalent.
- inconclusive (undecidable): observation on either side is uncertain, environment preconditions are unsatisfied, or π cannot be independently revoked (AUTH_TRACE.revocable=false).
**"Merely no authorization prompt appeared" must not be used as evidence of gap**; "undecidable" must not be written as "vulnerability does not exist".

Step four: condition sufficiency check:
Answer item by item: which fields are missing values? Which preconditions are unsatisfied? Is a control group missing (e.g. the degraded control of B1)? Are sample size and timing sufficient to support the conclusion?
If any question holds, set isInsufficient=true and state in missing "what is needed for sufficiency".

Step five: routing:
Adjudicate per the four routes of the qualitative-validation loop (premise: codeBug has been excluded):
- proceed-step12: the result falls into one of the three branches anticipated by Step 9, and no unanticipated new phenomenon is exposed.
- backtrack-step8: the result conflicts with or is opposite to Step 8's pattern classification, or has value for changing the fundamental understanding.
- backtrack-step9: the pattern classification still holds, but the current VF's core unknown / validation sub-items do not cover the new dimension exposed by empirical testing.
- backtrack-step10: the Step 8/9 judgments both hold and cover completely, only the method/sample size/control group is insufficient for a decisive conclusion.
"newInformation" must state the concrete new information of this round relative to the previous round; boilerplate such as "further confirmed the previous judgment" is not allowed.

## Real-Device Follow-Up Flow (Triggered After Report Delivery; Not Counted Among the 13 Main Steps)

Real-device mode requires a human to scan a QR code on site in mobile WeChat, so it is unsuited to the unattended Step 10↔11 correction loop. Every scenario that needs a real device for full confirmation has been collected into the "real-device follow-up list" and deferred, and **does not block the production and delivery of the report**. This section describes how to follow up on that list after report delivery.

**Trigger condition**: initiated only after report delivery when the user explicitly states they are present and can scan (e.g. "it's convenient now, a real-device test is fine"); do not proactively connect to RealDevice and wait for a scan at delivery time, and do not prompt the user before they confirm.

**Execution steps**:

1. Re-check the report's "real-device follow-up list" and confirm the scope of this execution with the user (the whole list or a specified subset).
2. Reuse the testPlan marked in the list (usually no need to rewrite scenario code), appending `--platform RealDevice --remote-timeout <recommended 180000 or longer>`; continue with the same `tmp/<domain>analysis-<YYYYMMDD>` / `autotest/TestResult/<domain>test-<YYYYMMDD>` group directory, without creating a new date group.
3. Inform the user in advance: after execution the developer tool will output a QR code, which must be scanned and confirmed within the timeout using a phone logged into WeChat; the authorization-prompt stage may still require manual cooperation (`--auto-authorize` may not fully auto-click native prompts on a real device, and `--clear-auth` has no effect on a real device; see the `miniapp-autotest` skill's "Real-Device Test Mode").
4. After results are produced, decide item by item against the list: confirmed (consistent with the previous code inference / DevTools conclusion) / overturned (contradicts the previous inference) / still undecidable.
5. **Write targeted updates back into the delivered report** (local update, without re-running Steps 0-13): for each finding covered by the real device, update (i) the "evidence strength" / "empirical status" columns of the core-findings-at-a-glance table; (ii) the empirical conclusion of the tiered subsection containing that finding; (iii) the "real-device follow-up list" subsection itself (completed items marked "confirmed" with a link to the result directory, incomplete items kept as pending). **When a real-device result contradicts previous evidence, the contradiction and the finally adopted conclusion must be explicitly annotated in the report; silently replacing the old conclusion is not allowed.**
