# Automated Filter Tool Usage Rules

> Goal: when the target functional domain's documentation/code volume is too large to hand to the LLM as a whole for analysis, use the three CLI scripts built into this skill (`scripts/api-filter/doc-filter.js` / `code-filter.js` / `cross-validate.js`) to complete the parts of Step 1 (documentation-layer collection) and Step 2 (code-layer implementation review) that are "deterministically solvable by pure code"; semantic judgments ("is it relevant", "does it hit the target capability") are always written back by the analysis flow driving the scripts after it completes them. This rules file is the invocation manual from `related-API-automated-filtering-and-location-design.md` (workspace root; the design document) to the actual code implementation; the scheme's own data-model design (ApiRecord / term sets / read-write permission matrix, etc.) remains governed by the design document, and this file covers only the operational level of "how to invoke, how to land it".

## Core Positioning

| Dimension | Description |
|---|---|
| **Applicable scenarios** | The target functional domain's official/team documentation numbers in the dozens or more, or the base-library code files are too large (thousands of lines or more), so reading through everything and sending it wholesale to the LLM for analysis is impractical |
| **Skippable scenarios** | The documentation/code volume is itself manageable (e.g. target APIs number in single digits, code files are small) — Step 1/Step 2 can be completed by direct human/LLM reading, and **tool use is not mandatory** — the tools are an aid, not a required step |
| **Roles of the three scripts** | `doc-filter.js` (corresponds to scheme a) documentation filtering), `code-filter.js` (scheme b) code filtering), `cross-validate.js` (scheme c) cross validation, and simultaneously the outer driver of the loop among the three, holding the global round counter) |
| **What this rule does not own** | It does not restate the design document's data-model design (ApiRecord fields, term classification rules, etc.) — those definitions are in Chapter 2 of `related-API-automated-filtering-and-location-design.md` in the workspace root; this file covers only operational-level rules of invocation/input/output/landing |
| **Boundary with the main flow** | The three scripts themselves **invoke no LLM**; they perform only deterministic retrieval (keyword matching, regex anchoring, bracket-counting extraction, alias resolution) and structured data persistence; semantic judgments such as "is this API relevant" and "does this code really implement the target capability" are always made by the current analysis flow (the LLM driving the scripts) and then written back via commands such as `judge` / `record-code-evidence` / `resolve` |
| **Output destination** | The confirmed API inventory produced by Step 1 and the code implementation locations produced by Step 2 are ultimately aggregated by `cross-validate.js export` into the input baseline of the Steps 3-6 convergence loop |

## 1. Tool Invocation Rules

### 1.1 Invocation Rules

1. **The three scripts share one registry file, which must be initialized first**: run `node <script>.js init --registry <path>` before the first use of any script (the `init` behavior of the three scripts is identical; any one may be run first and the others reuse the same path; repeated `init` is a safe no-op).
2. **The scripts perform only deterministic retrieval; semantic judgment is always the caller's job**: whenever `candidate` status or fields such as `pending` / `newlyPaired` / `candidates` / `docOnly` / `codeOnly` appear in a command's output, they mean "this is a queue of items awaiting judgment produced by the script, not a conclusion" — the analysis flow must first read the verbatim documentation / code fragment and make a relevance judgment, then invoke the corresponding write-back command (`judge` / `record-code-evidence` / `resolve`); the script's returned candidate queue must never be used directly as a final conclusion or written into a report.
3. **The read-write permission matrix is enforced at runtime, not merely a documentation convention**: `doc-filter.js` may write only `docEvidence` (internal identifier `docTool`), `code-filter.js` only `codeEvidence` (`codeTool`), and `cross-validate.js` only `crossValidation` plus term state transitions (`validationTool`). An out-of-authority invocation (e.g. attempting to create a new ApiRecord with `cross-validate.js`) is rejected, output to stderr with the prefix `[error] ...`, and terminated with a non-zero exit code — encountering such an error means the invocation order or tool choice is wrong, not that the script has a bug; check whether a registration action that should have been done by a)/b) was mistakenly sent to c).
4. **Recommended invocation order** (the strict order is not mandatory, but it matches the data dependencies and reduces ineffective invocations): **lines marked `[LLM]` below have no corresponding CLI command; they are purely semantic/knowledge actions that must first be completed as judgments in the current analysis flow, and only then persisted with the command immediately following** — such code-free stages are detailed in Section 1.2, "LLM-Exclusive Stage Execution Guidance"; this section only marks their exact position in the whole invocation chain:
   ```
   doc-filter.js init
     → [LLM] web search / local directory cross-check to obtain the initial set of typical APIs / keywords / return values for the target domain (scheme a-i)
     → seed (persist the previous step's result)
     → scan-filenames → scan-content (loop until loop-status shows no further growth)
          ↳ [LLM] read the verbatim documentation of each candidate produced by scan-content, judge relevance (scheme a-ii/a-iv)
     → judge/batch-judge (write back the previous step's judgments)
     → pairing-check (rerun once each time set A gains members, to capture pairings such as onX/stopX)
          ↳ [LLM] judge the actual semantics of the paired sibling API (e.g. "does <wifi-list-listener> really obtain data without permission")
     → judge (write back the pairing judgment)

   code-filter.js locate-anchor (find anchor)
     → extract-function (extract the function body; may automatically trace a second segment via alias/package jump)
          ↳ [LLM] judge whether the extracted code really is the target function's implementation (the four-branch a/b/c/d judgment of scheme b-ii-4)
     → analyze-function (count K_code/R/feature hits to aid the judgment)
     → record-code-evidence (write back confirmed/candidate/rejected after semantic judgment)
     in parallel (feature summarization sub-loop, scheme b-i-3):
          [LLM] first-round feature summarization: pick the extracted function bodies of 10 representative APIs, summarize 4 classes of CodeFeaturePattern, write them as regexes
       → feature-add (register the summarized features)
       → feature-scan (checking round: count the hit rate, collect unmatchedFunctions; this mandatory verification action may not be omitted)
          ↳ [LLM] if unmatchedFunctions is non-empty, summarize new features for them in a second round (do not assume the first-round features are already general)
       → feature-add (register new features) → repeat feature-scan until unmatchedFunctions stops producing new features
     in parallel (feature utilization sub-loop, scheme b-i-4/b-v):
          feature-locate (use converged features as new anchors to find new candidate positions; apiName left empty)
          ↳ [LLM] infer which already-documented API this position corresponds to, or whether it is an entirely new discovery (scheme b-i-4-b)
       → record-code-evidence (register the inference; for an entirely new discovery, persist codeEvidence first with the documentation side left empty)
     in parallel (mapping-table exhaustive enumeration, see Chapter 4):
          extract-object-keys (systematically enumerate all members after a mapping table is found)
          ↳ [LLM] judge item by item whether each unregistered member is a real API or noise
       → record-code-evidence or ignore; if confirmed to be the grouping body itself, additionally register with grouping-add

   cross-validate.js compare (produces the matchType classification; the two classes matched and "both sides explicitly rejected"
                              are automatically finalized in finalStatus and need no resolve — see Section 1.3)
     → [LLM] judge the concrete sub-reason of the remaining docOnly/codeOnly records (the two-branch logic of scheme c-i)
     → resolve (write back finalStatus for each docOnly/codeOnly; matched / both-sides-rejected do not need this step)
     → prune (pruning tiering; Tier1 executes automatically)
     → apply-suggestion (execute Tier2 suggestions after human confirmation; optional)
     → summary (persist this round's summary)
     → check-loop (if continue, then advance-round and return to doc-filter/code-filter for supplementary investigation;
                   if stop-converged/stop-round-cap, call export to wrap up)
   ```
5. **`cross-validate.js` is the outer driver of the loop, and the round counter can be advanced only by it**: `advance-round` may be called only when `check-loop` returns `decision: "continue"`; `doc-filter.js` / `code-filter.js` do not maintain and cannot modify the round counter, and the `addedRound` field when they write evidence is stamped automatically by the registry with the current round.

### 1.2 LLM-Exclusive Stage Execution Guidance (No Corresponding CLI Command; Derived From an Explicit User Requirement for the "pre-fetch data" Stage)

The three scripts invoke no LLM themselves (see the "Core Positioning" table), but the complete flow contains several stages that "must first be judged/summarized by the LLM, and only then persisted by invoking the following command" — no script command can substitute for these stages, and skipping them to invoke the following command out of nothing will persist shell data lacking semantic basis. The table below lists all such stages and how to execute them, corresponding one-to-one with the `[LLM]` marks in the invocation-order diagram above:

| Stage (corresponding scheme position) | Execution: how to invoke the LLM / how to execute | How the output is persisted, and which command it connects to |
|---|---|---|
| Startup initial data acquisition (scheme a-i) | Per the evidence priority in Section 2, item 1 of `documentation-and-code-collection.md`: the local documentation directory structure (`list_dir`) takes priority; for sub-domains that directory names cannot express, or where there is no referenceable directory at all, **the web search tool must genuinely be invoked** (e.g. querying "what official APIs relate to <target domain>", "what are the typical data fields / keywords of <target domain>"); only when none of the above is feasible fall back to the LLM's own parametric knowledge, and the source must be annotated | Organize the three produced sets (keywords / typical APIs / return values) into JSON and persist with `seed --termsFile/--apisFile/--returnsFile` |
| Documentation relevance judgment (scheme a-ii/a-iv) | Read the verbatim documentation pointed to by the `docPath` of candidates produced by `scan-content` / `pairing-check`, and judge, using signals such as `matchedKDoc` / `matchedR` / `exampleCodeMentions`, whether the API belongs to the target functional domain. **The criterion is "domain membership" (whether it belongs to the same documentation directory / naming family / shared artifact as already-confirmed members of the target domain), not "data value" (whether it carries sensitive data / whether data is returned)** — these are two independent questions explicitly distinguished by Core Principle 3a-1 of `SKILL.md`; the latter is Step 12's business and may not be used early for rejected judgments in this stage. Control/output-type APIs (coordinates / parameters specified by the developer, zero data returned) should still be confirmed as long as domain membership holds. Per 3a-2, boundary/doubtful cases default toward confirmed/candidate, not toward rejected; only when naming / directory / code structure are all unrelated may it be judged rejected | Write the judgment back with `judge --verdict confirmed/rejected/candidate` or `batch-judge`; on `rejected`, if the `--evidence` text hits typical data-value wording ("developer specified / pure rendering / does not return ... data itself", etc.), the command returns a `dataValueMisuseWarning` prompting re-check; use it to re-verify whether a domain-membership judgment mistakenly used the data-value standard |
| New return-value relevance judgment (scheme a-iv-2-③) | Judge item by item whether each of `scan-content`'s `newReturnCandidates` is a functionally relevant return field | Carry relevant fields as-is into `judge` / `batch-judge`'s `--newReturns` parameter; complete metadata (type/description/callbackType) is persisted together into set R |
| Whether the function is the target implementation (scheme b-ii-4) | Read the `segments` / `snippetPreview` extracted by `extract-function`, and judge the four-branch conclusion: a) hit, can be used directly b) hit but needs wider range c) not hit but there is a clue d) entirely unrelated. **Likewise judge only "does this code implement that API" (domain membership); a control/output-type API counts as "hit" as long as the code implementation genuinely exists, and must not be classified "entirely unrelated" merely because the function body does not touch sensitive data reads/writes** | a/b go to `record-code-evidence --status confirmed/candidate`; c returns to `locate-anchor` / `extract-function` to switch anchors or enlarge `--maxExpand`; d goes to `--status rejected` or no registration |
| First/second-round feature summarization (scheme b-i-3) | Select sample functions (first round: the confirmed function bodies of 10 representative APIs; second round onward: the `unmatchedFunctions` returned by `feature-scan`), read the source and summarize four classes of pattern — "keyword-corresponding code / return-value-corresponding code / system data-fetch feature / permission-judgment feature" — written as regexes | Register with `feature-add --regexOrTemplate`; after registering, `feature-scan` must be rerun once to verify convergence (mandatory action) |
| Alias-reference fallback judgment (scheme b-ii-3-a) | Triggered only when `extract-function` / `resolve-alias` returns "the regex cannot resolve an explicit assignment pattern": judge whether that expression really is an alias reference, and if so, which file / module to look in | After judging, manually specify a new `--codeFile` / `--charIndex` and re-invoke `locate-anchor` / `extract-function`; there is no dedicated write-back command (this is itself a routing judgment of "where to keep searching", not a terminal state) |
| New candidate attribution inference (scheme b-i-4-b) | Read the `candidates` produced by `feature-locate` (with `apiName` left empty) and, with the code context, infer whether the position implements some already-documented API or is an entirely new discovery | A known API goes to `record-code-evidence` for additional registration; an entirely new discovery likewise first persists `codeEvidence` with `record-code-evidence` (documentation side left empty), awaiting confirmation by `resolve` in the `cross-validate.js` cross-validation stage as to whether it is a genuine "documentation missing" case |
| Mapping-table unregistered-member nature judgment (scheme b-iv; see Chapter 4) | Compare item by item the `keys` enumerated by `extract-object-keys` against the Step 1 doc-side confirmed inventory, judging whether each unregistered member is a real API or irrelevant noise (a configuration item / telemetry constant) | A real API goes to `record-code-evidence` (codeOnly discovery); noise is not registered; the mapping-table body is additionally registered with `grouping-add` |
| docOnly/codeOnly sub-reason judgment (scheme c-i) | Read the `reasonIfMismatch` produced by `compare` (the candidate attribution direction the script already gives) and judge concretely which of range-not-covered / anchor-failure / genuine gap / false positive it is | Write back the terminal state with `resolve --finalStatus confirmed/rejected/reconsider/knownGap` |

### 1.3 `compare`'s Automatic Finalization Rules (New; Derived From a Convergence-Blocking Problem Found in Real Review)

`cross-validate.js compare` **automatically** advances `finalStatus` to a terminal state for two classes of record, with no need for the caller to `resolve` manually:
- **`matched`** (both documentation and code sides have non-rejected evidence, mutually corroborating) → automatically set to `confirmed`;
- **both sides already explicitly judged `rejected`** (not "never checked", but both documentation and code sides have been investigated and confirmed irrelevant) → automatically set to `rejected`.

Only `docOnly` / `codeOnly`, and empty-shell records with "no evidence on either side" (`matchType='unresolved'` and not both sides explicitly rejected), keep `finalStatus='candidate'` awaiting human/LLM `resolve`. **This automatic finalization rule is critical**: ignoring it and assuming every record must be `resolve`d manually not only adds needless work, but more seriously — if a `matched` record really is missed by `resolve`, its `finalStatus` stays at the placeholder `candidate` written by `compare`, and `check-loop` happens to treat `finalStatus==='candidate'` as an "unresolved" signal, so the loop can never decide `stop-converged` (it only drags on until the round cap forces a stop). If a record that was automatically finalized is found to be misjudged, `resolve` may still be used to override it explicitly (e.g. changing it to `reconsider` to request re-check); **a terminal judgment made by a human/LLM via `resolve` takes precedence over `compare`'s automatic finalization**, and the next round's `compare` will not overwrite it back.

### 1.3a Real Operational Trap: After Changing a `docEvidence` / `codeEvidence` Judgment, a Corresponding New `resolve` Is Mandatory, Otherwise the Old Terminal State Sticks (New; Derived From an Operational Omission Repeatedly Reproduced in Real Analysis)

`judge` / `batch-judge` / `record-code-evidence` are responsible only for writing their own exclusive zones (`docEvidence` / `codeEvidence`) and **never touch `crossValidation.finalStatus`** — this is the correct boundary in the permission-matrix design (a)/b) have no authority to finalize a classification conclusion directly), but it creates a real operational trap: **if an API was already `resolve`d once and left an explicit `finalStatus` (even `rejected`), and `judge` / `batch-judge` later changes its `docEvidence.status` (e.g. from rejected to confirmed), `crossValidation.finalStatus` will not update automatically** — `compare`'s "respect a terminal judgment already made by a human" logic (see the previous section) will keep preserving the old `finalStatus` as-is, even though that old judgment now contradicts the latest `docEvidence` / `codeEvidence` content.

**Illustrative case**: when analyzing any domain, `<authorize-API>` / `<authorize-API>ForMiniProgram` were judged irrelevant early on under the narrower "primary functional category" standard and were `resolve --finalStatus rejected`; later, when the standard was widened to "data relevance" at the user's request, they were re-judged as relevant and `docEvidence.status` was changed with `judge --verdict confirmed`, but **the synchronized `resolve --finalStatus confirmed` was forgotten** — on the next round's `compare`, these two APIs' `finalStatus` still sat unchanged at `rejected` (because it was recognized as "already has a human terminal state, do not overwrite"); unless one proactively uses `export` / `compare` to re-check whether each record's `finalStatus` agrees with the latest `docEvidence.status`, such "changed but not effective" records lie dormant for a long time with no error message at all.

**The other side of the same trap**: a record newly judged `rejected` for which only `judge --verdict rejected` was called but not `resolve --finalStatus rejected` — because the combination `docStatus=rejected` with `codeStatus=absent` does not satisfy the automatic-finalization condition "both sides explicitly rejected" (`compare` requires both sides to be `rejected` to finalize automatically; `absent` does not count) — will keep `finalStatus` at the default `candidate`, causing `check-loop`'s `unresolvedCount` never to reach 0 and `stop-converged` never to be reached, even though its `docEvidence.status` is already clearly `rejected`.

**Rule**: **any `judge` / `batch-judge` / `record-code-evidence` invocation that changes some API's `confirmed` / `rejected` conclusion (whether a new judgment or a change to an existing one) must be immediately followed by a corresponding `resolve` invocation in the same batch of operations** — one may not assume `compare` will handle it, because `compare`'s automatic finalization covers only the scenario "both sides are brand-new evidence with no prior human terminal state", not the "changed judgment" scenario. After a batch operation, it is recommended to rerun `compare` and visually check, for each record in the `docOnly` / `codeOnly` / `unresolved` classifications, whether its `finalStatus` is semantically consistent with that entry's latest `docEvidence.status` / `codeEvidence.status`, and to supply a `resolve` immediately where they disagree.

## 2. Data Input Rules

1. **JSON parameters that are batched or contain special characters must go through `--xxxFile <path>`, not shell inline strings**: every parameter accepting a JSON array/object supports both passing modes — inline string `--terms '[...]'` and file path `--termsFile a.json` (`resolveJsonInput` reads `xxxFile` first). **A real problem verified by testing**: command-line inline JSON handles Chinese characters and quote escaping unstably under Windows PowerShell, causing parameters to be wrongly truncated or corrupted in encoding (reproduced: a Chinese `--evidence "..."` parameter triggered a `TerminatorExpectedAtEndOfString` parse error; a `--terms` JSON containing Chinese caused the persisted content to become an `"undefined"` key). **Rule**: whenever a parameter value contains Chinese text, or is an array/object structure (whether or not it contains Chinese), first write a temporary JSON file with `write_to_file` and then pass it via the corresponding `--xxxFile` form; only simple string parameters that are pure ASCII with no special characters (e.g. `--apiName <baseline-locate-API>`, `--verdict confirmed`) may be inlined directly.
2. **The JSON parameter structures of commands such as `seed` / `judge` / `record-code-evidence` / `grouping-add` must match the field definitions of scheme 2.2-2.7**: e.g. `--terms` array elements have the form `{"term":"...","sourceApi":"...","belongsTo":"K_doc"}` (`belongsTo` may be omitted; the script classifies Chinese/English automatically per scheme 2.5); `--locations` array elements have the form `{"file":"...","startLine":N,"endLine":N,"role":"main","anchorType":"...","anchorEvidence":"...","aliasChain":[]}` (corresponding to scheme 2.3 CodeLocation). Misspelled field names do not raise errors, only being silently ignored (JS object destructuring tolerance), so before passing, check field names against the command reference table in Chapter 1 of this file.
3. **`locate-anchor`'s `hits` is `extract-function`'s locating input; `extract-function`'s `segments` is the compliant input to `record-code-evidence`**: `locate-anchor` returns only the character offset / line number of the anchor hit (`hits[].charIndex` / `hits[].lineNumber`), which is not itself a CodeLocation; passing some `hits`'s `lineNumber` to `extract-function --line` gives back a `segments` array whose structure is the compliant CodeLocation format (containing `role` / `anchorType` / `aliasChain` and other fields), which can be taken directly after semantic judgment confirms it (dropping extra fields or transferring it wholesale) and written into a JSON file for `record-code-evidence --locationsFile`, without manually re-assembling fields.

## 4. Permission Mapping Table Exhaustive Enumeration Workflow (New)

**Background**: the retrieval logic of commands such as `scan-content` / `locate-anchor` is essentially "keyword / regex hitting", which can find only content already covered by seed terms. But structured data such as a permission/scope mapping table is itself a **closed, complete, enumerable** set — once the table's range is located, one should be able to obtain "all" members, not "the part keywords happen to hit". A for instance: in a permission mapping table of 91 entries, 13 "cloud storage / friend interaction" family APIs (`<cloud-storage-peer-API>` / `<cloud-storage-peer-API>` / `<cloud-storage-read-API>`, etc.) had zero hits under keyword-hit retrieval alone because their names never entered the initial keyword seeds, and **there was no error or warning at all** — they were discovered only when `extract-object-keys` systematically enumerated the whole table; these APIs themselves have no standalone documentation entries in `api_doc` (mini-game-only APIs) and can be found only through this channel.

**Standard workflow**:

1. Use `locate-anchor` (`anchorType: scopeMappingTable` or `stringLiteral`) or manual reading to first find the anchor position of **any one known member** inside the mapping table (e.g. via the apiName string of some already-confirmed API).
2. Use that position's line number / character offset to call `extract-object-keys --line <lineNumber>` (or `--charIndex`), which automatically expands outward to find the whole table's boundaries and returns all top-level keys `keys: [{key, rawKeyText, valuePreview}]`.
3. Compare each `key` in `keys` against the Step 1 doc-side confirmed API inventory (`doc-filter.js pending` / `docEvidence.status` in `_api_registry.json`) one by one to identify members that "exist in the table but never appeared on the doc side".
4. For each unregistered member, judge its concrete nature (**the criterion is Core Principle 3a, "data relevance", of `SKILL.md`, not the "primary functional category" standard** — the literal meaning of a `groupKey` / scope group name not belonging to the target domain is not grounds for exclusion; one must look at whether the data / return values that member operates on touch the target domain's data):
   - If confirmed to be a genuinely existing API (even if documentation is missing), go to `code-filter.js record-code-evidence` to register a codeOnly discovery, later adopted via `cross-validate.js resolve --finalStatus confirmed` (referring to scheme c-i-2①, "a genuine documentation-missing discovery");
   - If it is merely an irrelevant configuration item / telemetry constant (e.g. a network policy whitelist, a staged-rollout tier table), annotate it as noise and exclude it.
   - **Under-recall risk**: when analyzing any domain, in a large permission mapping table, under the `jsapi_wxfriend_interaction` group — `<cloud-storage-peer-API>` / `<cloud-storage-read-API>` / `<cloud-storage-write-API>` / `<cloud-storage-delete-API>` / `<cloud-storage-keys-API>` / `GameServerManager.<friend-state-API>` / `<interactive-storage-API>` / `<group-info-API>` / `<friend-list-API>` / `<gift-status-API>` / `sendGiftToFriend`, and under the `<dispatch-gateway>_werun` group — `<werun-API>` (whose return value contains friends' `nickName` / `avatarUrl`), were judged irrelevant wholesale and not registered in the initial analysis because the group names sounded like "friend interaction", "cloud storage", "WeChat Steps" — this was a real missed detection caused by using the wrong judgment standard ("primary functional category" rather than "data relevance"), not a defect of `extract-object-keys` itself (it had faithfully enumerated all 91 keys; the problem lay in the semantic-judgment stage after the enumeration results).
5. **If the `role` field in the result is not `mappingEntry` and `totalKeys` is very small (<2), the location may have landed on a control-flow block or some other non-object-literal structure**; check whether the passed `--line` / `--charIndex` lands precisely on some entry inside the table, rather than on other code outside it.

**Scope reminder**: this workflow applies only to mapping tables in **object-literal form** (`{key: value, ...}`); if permission/grouping information is stored in another form (e.g. functional judgment, scattered multiple `if` branches), `extract-object-keys` cannot handle it and manual reading / `analyze-function` assistance is still required.

## 5. Documentation-Source Multi-Directory Enumeration Workflow (New)

**Background**: if `scan-filenames` / `pairing-check` are passed only one main documentation directory, they are entirely blind to other documentation directories in the project, likewise with no error message. A for instance: the documentation of a high-value API (`wx.<phone-number-API>`) actually lived in a Markdown-format directory completely separate from the main documentation directory, and scanning only the main directory caused that API to go undiscovered throughout.

**Standard workflow**:

1. At Step 0, use `list_dir` to view all top-level directories under the project root, judging one by one "whether it might contain documentation of the target domain" (do not exclude merely on the literal meaning of a directory name; when necessary use `search_content` / `search_file` to spot-check the directory contents quickly).
2. Pass all confirmed-relevant directories at once, comma-separated, to `--docRoot`, e.g. `--docRoot "api_doc,miniapp_md"`; the `perRootCount` field in the `scan-filenames` result shows how many files each directory contributed, which can confirm that multi-directory scanning really took effect (if some directory returns 0, check the path spelling).
3. If the target documentation is not in JSON format (e.g. Markdown), `scan-content` automatically falls back to plain-text keyword matching after `JSON.parse` fails; functionally it can process it normally, but `apiName` is taken from the filename rather than from a title field inside the document, so when writing back at the `judge` / `batch-judge` stage one should manually check whether the filename accurately corresponds to the target API name (and when necessary specify the correct API name explicitly with `--apiName`, rather than copying the filename).

## 6. Step 1 Candidate-Loss Prevention Mechanisms (New; Derived From Three Classes of Silent Missed Detection Found by Comparing With Historical Analyses)

**Background**: after comparing this analysis's results item by item with three historical analyses (`userInfoApiAnalysis-20260813` / `userInfoAnalysis-7-24` / `UserInfoAPIFilterTest-20260827`), 8 genuinely missed APIs were located (`<plate-picker-API>` / `<added-check-API>` / `wx.<chat-tool-API>` / `<chat-tool-mode-API>` / `<chat-tool-open-API>` / `wx.<share-API>` / `wx.<channels-profile-API>` / `button.<avatar-picker-API>`), whose root causes fall into three classes of "silent loss point" never previously exposed by the tools — not that the keywords / patterns themselves were written wrong, but that candidates were quietly dropped at some intermediate stage with no error or warning. The three root causes correspond to three code fixes respectively:

### 6.1 Missing Specific Files Inside a Leaf-Level "Partially Matched" Directory (`scan-filenames`'s `partiallyMatchedSubdomains`)

`uncoveredSubdomains` (the mechanism already in Chapters 4/5) can find only the strong signal "the whole directory has zero hits", but the case where **a directory's overall hit rate is not low while individual files inside it are still missed because their filenames contain no pattern word root** does not trigger it at all — reproduced for real: in the `chatTool/` directory, 6 of 10 files matched (60%), but `wx-<chat-tool-API>.json` / `wx-enterChatToolMode.json` / `wx-<chat-tool-open-API>.json` were missed because their filenames contain none of the `user/profile/account/...` word roots; in the `forwarding/` directory, only 1 of 11 files matched (9%), and `wx-<share-API>.json` was likewise missed. Such directories do not appear in `uncoveredSubdomains`, so analysts very easily assume "this directory has already been covered".

**Fix**: when `findUncoveredSubtrees` recurses to the leaf level (a directory that cannot be subdivided further) and finds it "partially matched", it no longer gives up directly, but lists **all specific unmatched filenames** in that directory, exposing them via the new field `partiallyMatchedSubdomains` (containing `subdomain` / `totalFiles` / `matchedFiles` / `unmatchedFileNames`), together with a `partialWarning` echoed to stdout (including the `--out` persistence branch). **Usage**: after getting the `scan-filenames` result, do not only check whether `uncoveredSubdomains` is empty; also check whether `partiallyMatchedSubdomains` is empty — when non-empty, verify one by one whether each file in `unmatchedFileNames` needs supplementary keywords or should take the same-directory fallback channel of Section 6.3 below.

### 6.2 Silent Dropping of "Filename Matched but Content Zero-Hit" Files (`scan-content`'s `contentUnmatchedFiles`)

`scan-content`'s original implementation simply `continue`d past files "whose filename had already been judged possibly relevant by `scan-filenames`, but which had zero hits after content-level keyword / return-value / sample-code scanning", producing no record at all — reproduced for real: `wx-<channels-profile-API>.json` (whose filename contains `channels` / `profile` and was correctly passed in) was silently dropped because the parameter `finderUserName` never entered the keyword set; thereafter that API vanished entirely from the whole analysis flow, appearing in neither confirmed nor rejected, and discovering this "vanished intermediate state" required manually comparing `scan-filenames`'s `matched` list with `scan-content`'s `candidates` list item by item.

**Fix**: explicitly collect these files as `contentUnmatchedFiles` (containing `docPath` / `guessedApiName`), together with a `contentUnmatchedWarning` echoed as well (including the `--out` persistence branch). **Usage**: when this field is non-empty, spot-check item by item — it may be genuine irrelevance, or a false negative from insufficient keyword coverage; one must not assume "did not enter the candidate queue = already excluded".

### 6.3 Sibling APIs Whose Relation Cannot Be Derived From Naming Patterns at All (`pairing-check`'s same-dir-fallback)

`pairing-check`'s original naming-pattern pairings (`callback-pair` / `start-stop` / `register-callback` / `crud-pair`) require that "a sibling API name can be derived from a known API name", but a missed detection entirely failing that premise was reproduced for real: `videoAccount/<channels-profile-API>` versus the already-confirmed `<channels-key-API>` in the same directory, and `chatTool/<chat-tool-API>` versus the already-confirmed `selectGroupMembers` in the same directory — no get/on/off/crud relation is derivable from their names at all.

**Fix**: add a fifth pairing relation `same-dir-fallback` (already added to the `PAIRED_API_RELATIONS` enum in `lib/registry.js`) — for each already-confirmed API, take the directory of its documentation and unconditionally register **all files in that directory that have never been registered** as candidates, requiring no naming similarity whatsoever, relying only on the naive but reliable signal "belonging to the same classification subdirectory of the documentation source". The result gains `sameDirFallbackFound` / `sameDirFallbackCount`. **Usage**: after each `pairing-check` invocation, besides `newlyPaired`, also look at `sameDirFallbackFound` — it often digs deeper than naming-pattern pairing, because it depends on no word-root matching.

### 6.4 Division of Labor and Priority Among the Three

The three mechanisms target different miss patterns and **none may substitute for the other two**: `partiallyMatchedSubdomains` addresses "never hit by the pattern at the filename level"; `contentUnmatchedFiles` addresses "filename hit but no signal at the content level"; `same-dir-fallback` addresses "the naming pattern cannot derive anything at all, and same-directory relatedness is the only clue". In one analysis all three should be **fully** run and each new field in the results checked one by one; one must not skip checking the other two merely because one of the fields is empty.

### 6.5 `pairing-check`'s `newlyPaired` Once Registered Template-Guessed Names as Real apiNames, Producing "Phantom API" Records (Fixed; Derived From a Code Defect Found in a Real Location-Class Analysis)

**Background**: `deriveSiblingNames` generates several template-guessed names for `get*`-class APIs (e.g. guessing `<locate-listener-API>` from `<baseline-locate-API>`, `<beacon-listener-API>` from `<beacon-API>`), then searches real filenames with **fuzzy containment matching** (`n.toLowerCase().includes(bareSib.toLowerCase())`) — both `<locate-change-API>` and `<beacon-service-listener>` can be fuzzily hit by `<locate-listener-API>` / `<beacon-listener-API>` (because the latter happens to be a prefix substring of the former). The original implementation, after a hit, **directly used the template-guessed name `bareSib` (rather than the fuzzily matched real filename `found`) to concatenate and register into the registry**, producing two "phantom API" records that never really existed (`wx.<locate-listener-API>` / `wx.<beacon-listener-API>`), while their `docPath` pointed at the real files corresponding to `found` (`<locate-change-API>.json` / `<beacon-service-listener>.json`) — `apiName` and `docPath` contradicted each other, requiring a human to discover and identify them at the semantic-judgment stage as "false records produced by a tool defect" and then manually `judge --verdict rejected`. This does not itself block analysis convergence, but every fuzzy-match trigger repeatedly produces such noise records, adding unnecessary manual judgment burden.

**Fix**: `fullSibName` is uniformly changed to concatenate based on the real filename `found` returned by fuzzy matching (`rec.apiName.startsWith('wx.') ? 'wx.' + found : found`), no longer using the template-guessed name `bareSib` — `bareSib` is used only to drive the fuzzy-matching step; after a hit, the registered name must be a genuinely existing filename. **Regression verified**: reproducing the scenario with a clean minimal registry (`<baseline-locate-API>` / `<beacon-API>` confirmed), after the fix `newlyPaired` correctly outputs the real filenames (`<locate-change-API>` / `<beacon-service-listener>`) and no longer produces the `<locate-listener-API>` / `<beacon-listener-API>` phantom records. **Usage**: after the fix it is still recommended to check `newlyPaired` item by item for whether the `to` field is a genuinely existing, reasonable API name — fuzzy containment matching itself may still match semantically unrelated same-prefix files (e.g. `onGet` fuzzily hitting `onGetAnythingElse`); that belongs to the category of "candidate noise", filtered by `judge`'s semantic judgment, and is different in nature from the "apiName and docPath self-contradiction" fixed by this item; the two must not be conflated.

### 6.6 `judge` / `batch-judge` Gains `dataValueMisuseWarning`: Detecting High-Risk rejected That "Substitutes the Data-Value Standard for the Domain-Membership Judgment" (New; Derived From a Real Judgment-Standard Confusion Case Found in a Location-Class Analysis; Corresponds to Core Principles 3a-1/3a-2 of `SKILL.md`)

**Background**: the Step 1/Step 2 semantic judgment should answer "does this API belong to the target domain's documentation/code set" (domain membership), but a case was observed in which the judge substituted "does this API carry sensitive data / does data get returned" (data value — a question that should be handled only at Step 12) for the domain-membership judgment — for instance: when analyzing "location-information-class APIs", 28 APIs including `<map-control-API>` / `<map-view-API>` / `<map-view-API>` / `<map-view-API>` (coordinates/angles specified by the developer) and `<wifi-control-API>` / `<wifi-control-API>` / `<wifi-control-API>` / `<wifi-control-API>` (WiFi module control) were wrongly rejected wholesale because `judge`'s `--evidence` wrote data-value reasons such as "static rendering content, not user location data" or "does not return location data itself", even though they belong to the same documentation directory / code file as already-confirmed members of the same domain and their domain membership should never have been in dispute. This class of error is not caught by the existing three mechanisms `partiallyMatchedSubdomains` / `contentUnmatchedFiles` / `sameDirFallbackFound` — those solve "a candidate was never discovered", whereas here the candidate **was already correctly discovered and sent into judgment**, and the problem is that the wrong standard was used in the judgment stage itself; moreover, the tool previously performed no check at all on the reason text of a `rejected` judgment, so the error was persisted silently and invisibly.

**Fix**: `applyJudge` (the core logic shared by `judge` / `batch-judge`) gains lightweight heuristic detection — when `verdict==='rejected'` and the `evidence` text hits typical "data-value-only judgment" wording patterns (regexes such as "developer specified / passed in", "pure rendering / geometric / control", "static rendering / configuration", "does not return / return ... data", "not ... data itself / geographic coordinates / location data"), the result gains a `dataValueMisuseWarning` field, prompting "this rejected reason appears to have judged only data value, not domain membership; please re-check per 3a-1". `batch-judge` additionally aggregates `dataValueMisuseWarningCount` / `dataValueMisuseWarnings` at the top level, consistent with the existing `staleFinalStatusWarning` / `staleFinalStatusWarnings` aggregation, so a single warning is not drowned in a large `results` array.

**Usage and limitations**: this is only a **heuristic prompt**, not an automatic correction — hitting the detection does not mean the judgment is necessarily wrong (it may be a genuine out-of-domain exclusion that merely happens to use similar wording), and not hitting it does not guarantee the judgment is right (the judge may well express the same standard confusion in other wording, e.g. writing simply "no privacy value" without any preset keyword). **This mechanism is the last mechanical fallback and cannot replace the semantic judge's proactive self-check against 3a-1/3a-2** — on encountering a `dataValueMisuseWarning`, re-examine whether that API's documentation directory / code file / naming family is related to already-confirmed members of the target domain, rather than simply ignoring the warning or changing the judgment unthinkingly.

### 6.7 The 6.5 Fix Left a Residual Defect: `fullSibName`'s Concatenation Basis Used the Wrong Object of Judgment, Producing "Double-Prefix" Phantom Records (Fixed; Derived From a Code Defect Found in a Real Hardware-Management-Class Analysis)

**Background**: the 6.5 fix changed `fullSibName` to `rec.apiName.startsWith('wx.') ? 'wx.' + found : found` — i.e. the basis for judging "whether to prepend the `wx.` prefix" was **whether the source API triggering this pairing (`rec.apiName`) starts with `wx.`**, but that basis is itself wrong: what should be examined is **whether `found` (the real matched filename) already carries that prefix**. This project's documentation naming uniformly follows the "`<namespace>-<methodName>`" format (e.g. `wx-<sensor-change-listener>.json` corresponds to the real apiName `<sensor-change-listener>`; `CameraContext-<record-stop-API>.json` corresponds to the real apiName `<record-stop-API>`), so `found` itself already fully contains the namespace prefix (which may be `wx`, or some component class name), and there is no need — nor should there be — to concatenate it once more.

**Failure mode to guard against**: when the source API `<sensor-start-API>` paired to the real file `wx-<sensor-change-listener>`, the 6.5-version logic, because `rec.apiName` (i.e. `<sensor-start-API>`) starts with `wx.`, wrongly concatenated it into `wx.wx-<sensor-change-listener>` — which coexisted in the registry with the truly correct `<sensor-change-listener>`, constituting duplicate phantom records (and such phantom records' fuzzy-matching mechanism gets them all registered automatically as `candidate` and most likely judged `confirmed` by `judge`, because their `docPath` points at really existing documentation). Similarly, when the source API `<record-start-API>` paired to the real file `CameraContext-<record-stop-API>`, it was wrongly concatenated into `wx.CameraContext-<record-stop-API>` (correct should be `<record-stop-API>`, with no `wx.` prefix). Such phantom records escape the 6.5-version detection of "apiName and docPath self-contradiction" — because this time the file pointed to by `docPath` really exists (only the apiName's prefix was concatenated wrong), so on the surface "the evidence is complete", making them more covert than the 6.5 version; **in one hardware-management-class analysis this actually produced 25 such phantom records, which were misjudged as confirmed and counted into the final API inventory, and were discovered only when a systematic count comparison was made against historical analysis results**.

**Fix**: no longer rely on `rec.apiName` to guess the concatenation method; directly perform "replace the first `-` with `.`" on `found` to restore the correct apiName (`found.indexOf('-') > 0 ? found.slice(0, dashIndex) + '.' + found.slice(dashIndex + 1) : ...`), falling back to the original logic only when `found` contains no `-` (a rare case, e.g. a pure class-name file). **Regression verified**: reproducing the minimal scenario of the two real failure cases above, after the fix `<sensor-start-API>` correctly pairs to `<sensor-change-listener>` (no double prefix), and `<record-start-API>`'s fuzzy match instead hits another genuinely existing same-prefix file `wx-<record-stop-API>` (producing no phantom records). **Usage**: this fix does not change the necessity of the existing recommendation in Section 6.5 that "one must still manually check whether the `to` / `apiName` fields of `newlyPaired` / `sameDirFallbackFound` are genuinely reasonable API names" — historically this class of defect has reproduced twice in different forms (once with a non-existent template-guessed name, once with a wrongly concatenated prefix), showing that such "looks evidentially complete but the apiName itself is wrong" phantom records cannot be eliminated by automated mechanisms alone, and that a basic plausibility check is still needed at the semantic-judgment stage for each newly appearing candidate API name (whether it is a plausible API name conforming to naming conventions).

## 7. Landing Rules

1. **Registry path**: `tmp/<domain>analysis-<YYYYMMDD>/_api_registry.json`, consistent with the tmp group directory shared by this functional domain throughout Steps 0-12 (naming rules in `SKILL.md`, "Execution Conventions"), with no separate new directory. All three scripts point at the same file via `--registry` throughout.
2. **Round summary landing**: `cross-validate.js summary --out` persists to `_tmp_<domainAbbr>_filter_round<N>_summary.md` in the same directory (`<N>` being the round number when the summary was triggered, corresponding to the registry's internal `currentRound`), one file per convergence-loop round, without overwriting previous rounds' files — this is the concrete landing form of "persist at every step (mandatory)" in the Execution Conventions during the automated filtering stage.
3. **Export landing**: after the tools converge (`check-loop` returns `stop-converged` or `stop-round-cap`), call `cross-validate.js export --out` to persist to `_tmp_<domainAbbr>_filter_export.json`, as the structured data source for writing the mandatory tmp files of Step 1 / Step 2.
4. **`export`'s output cannot substitute for the tmp landing files of Step 1 / Step 2 themselves**: `_tmp_<domainAbbr>_step1_api_list.md` (required by Step 1) and `_tmp_<domainAbbr>_step2_code_check.md` (required by Step 2) must still be narrative Markdown authored by a human/LLM — `export` gives structured facts of the kind "which APIs were finally confirmed and what the evidence is", but procedural narration of the kind "how many scanning rounds the documentation filtering took to converge" and "whether some API was found by naming-pairing detection or content matching" needs the analyst to supplement it by drawing on each round's `summary` output. Treating `export`'s raw JSON directly as the deliverable is not allowed.
5. **Archiving is completed together with the tmp group directory, with no extra action needed**: `_api_registry.json`, each round's `_tmp_<domainAbbr>_filter_round<N>_summary.md`, and `_tmp_<domainAbbr>_filter_export.json` all already land inside this functional domain's `tmp/<domain>analysis-<YYYYMMDD>/` directory, and are retained together with that directory when Step 12 organizes archiving; no separate archiving step is needed for these files.
6. **`groupingHints` is a preliminary clue for Step 3a, not a final grouping conclusion**: the `groupingHints` field in `export`'s output (scope mapping table / functional grouping information registered by `grouping-add`) serves only as a reference starting point for 3a when entering the Steps 3-6 convergence loop; the reality of the shared artifact must still be re-verified per `references/api-grouping.md`, and it must not be accepted directly as the formal grouping table — consistent with the design document's positioning that "grouping information produced by this scheme is only a preliminary clue, not a final grouping conclusion".

## 8. Error Handling

- All command-line parameter validation failures (missing required parameters, illegal enum values, JSON parse failure) and business-rule violations (out-of-authority writes, references to non-existent ApiRecords/terms) output `[error] <concrete reason>` to stderr and terminate with a non-zero exit code (uniformly caught and converted by `runCli` in `lib/cli.js`, without throwing the raw stack).
- Common errors and their meanings:
  - `docEvidence can only be written by docTool` / `codeEvidence can only be written by codeTool` / `crossValidation can only be written by validationTool`: the wrong script was invoked to register some field; check whether the right script is being used.
  - `ApiRecord does not exist: "xxx" — validationTool has no authority to create new records`: `resolve` / `compare` commands were invoked on `cross-validate.js` directly while neither `doc-filter.js` nor `code-filter.js` had yet registered that API; first create the record with `doc-filter.js seed` / `scan-content` or `code-filter.js record-code-evidence`.
  - `Term does not exist: K_doc/xxx`: `apply-suggestion` / `remove-term` was invoked on a non-existent term; check the term name spelling or whether it has already been removed.
  - `advanceRound can only be invoked by validationTool`: only `cross-validate.js` can advance the global round; do not try to advance it with another script.
  - `pairedApis.relation must be one of callback-pair/start-stop/register-callback`: the `relation` was misspelled when registering a naming pairing relation; check whether it is outside those three enum values (defined in scheme 2.1).
  - `markDocMissingConfirmedByValidation can only be invoked by validationTool`: this is a method invoked automatically inside the `resolve` command when handling the "codeOnly judged confirmed" scenario; it should not be invoked directly by other scripts; seeing this error usually means the caller skipped the `resolve` command and fiddled with internal interfaces — just take the normal `resolve --finalStatus confirmed` path.
