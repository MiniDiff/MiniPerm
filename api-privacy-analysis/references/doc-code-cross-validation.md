# Documentation-Code Cross-Validation Rules (General)

> Goal: official/team documentation usually covers the "standard invocation path" accurately, but systematically tends to omit the following: silent post-hoc zeroing of fields, server-configurable permission bypass mechanisms, implicit cross-method state coupling, and branch behavior under special scenes/parameters. Relying on documentation alone for privacy or security compliance assessment **underestimates actual data reachability**; item-by-item cross-validation against the implementation code is mandatory.

## Review Dimensions

For every API in the target functional domain, check item by item whether the "documentation claim" and the "code implementation" agree:

1. **User-authorization field**: does the documentation declare `scope.xxx`/an equivalent authorization item? Does a corresponding check-function invocation exist in the code? Do the check's trigger conditions (whether branched by parameter or by invocation sequence) match the documentation description?
2. **Return-field completeness**: can every return field listed in the documentation be traced to a real assignment source in the code? Is any of them zeroed / set to a constant / physically deleted under some conditional branch, without the documentation noting "invalid in this case"?
3. **Permission bit / permission mapping**: in the code's permission-bit mapping table (e.g. `jsapi_xxx`-type entries), does the permission identifier for this API match the category/permission described in the documentation? Does it **share the same permission identifier with another API whose permission bit is entirely different** (indicating that the two are treated as equivalent in review terms, though the documentation does not mention it)?
4. **Trigger-condition attribution**: if a permission check actually occurs inside "another method" (rather than in the method the documentation describes), explicitly call out this "cross-method condition mismatch".
5. **Precision/strength description**: is the documentation's description of precision, fuzzing degree, frequency limits, etc. only vaguely qualitative ("fairly fuzzy" / "subject to limits") while the code contains concrete quantitative values (fuzzing radius, cache duration, rate-limit threshold)? Missing quantitative values lead users to over- or under-estimate actual risk.
6. **Hidden bypass mechanisms**: do internal privilege symbols, dynamic operational whitelists, scene-specific straight-through, or similar mechanisms exist that let the API bypass the normal check path described in the documentation entirely when certain hidden conditions are met?
7. **API entry existence**: does this API have a corresponding standalone entry in the documentation directory? This is a more fundamental check than "return-field completeness" — if the code confirms the API is genuinely registrable and callable but no corresponding entry can be found anywhere in the documentation directory, that is a more severe deviation than a field-level omission (see the "API-entry-level documentation missing" label below).

## Deviation Classification Labels (Use Uniformly When Recording, to Facilitate Horizontal Aggregation)

- **Field nominally present but functionally dead**: the documentation still lists the field, but the code has made it permanently ineffective (zeroed / fixed value);
- **Hidden permission bypass** (undisclosed in documentation): an internal privilege / scene straight-through / dynamic whitelist or other circumvention mechanism exists;
- **Permission bit disconnected from documentation**: the code's permission-bit mapping is inconsistent with the documentation's category-review description, or it shares the same permission bit with another API without the documentation stating that the two are equivalent;
- **Trigger condition cross-method mismatch**: the documentation writes the trigger condition on method A, but in the code that condition is actually checked/triggered by method B;
- **Insufficient precision/strength description**: the documentation gives only qualitative description, lacking quantitative detail present in the code;
- **Authorization field entirely omitted from documentation**: the documentation says nothing about an interface's authorization requirement, but the code proves a permission check does exist (whether a traditional scope or an independent privacy-agreement prompt channel);
- **API-entry-level documentation missing** (severity above field-level omission; counts as an × deviation): this API has **no standalone entry whatsoever** in the entire documentation directory, rather than merely omitting some field or authorization note, yet **the code confirms it does have permission-check logic** (whether traditional scope or an independent privacy-agreement prompt), so reviewers/developers have no documentary channel by which to learn of this API's existence or of its permission constraint.
- **Documentation honestly reflects a permission vacuum** (different in nature from the previous item; counts as √ consistent, **not a deviation**; this label was added to avoid confusion): this API's documentation has no "user authorization" section, and **the code likewise confirms that no permission-check logic exists at all** (zero `checkPrivacy`, zero permission bits, zero static declaration) — "the documentation does not write permissions" and "there genuinely are no permissions" agree, so the documentation neither lies nor omits. The decisive factor is **the state on the code side**: if the code has permission logic and the documentation omits it, that is "API-entry-level documentation missing" (× deviation; the problem lies in documentation maintenance); if the code itself has no permission logic and the documentation honestly omits it too, that is "documentation honestly reflects a permission vacuum" (√ consistent; if there is a problem at all, it lies in the product/code's permission design itself, not in a documentation slip). The two call for different review dispositions: the former should push for documentation supplementation; the latter should push for evaluating whether a permission-check mechanism needs to be **added for this capability at all**.
  > **Important supplement (mandatory cross-check requirement, new)**: labeling an API with "documentation honestly reflects a permission vacuum" **only reflects the conclusion when that API is evaluated in isolation; it must not be taken to mean the finding has low risk priority**. An additional check under pattern D of `api-composition-and-equivalence-channels.md` is mandatory — examine whether this API is **functionally substitutable for other strongly controlled APIs (domain whitelist / scope / permission bit) in the same functional domain** (i.e. whether it can achieve the same actual effect, such as "sending data off the device"). If a substitutable relation exists, then even though this API's own documentation honestly states "zero controls", its priority must be **raised** in the core conclusions/risk ranking, because it constitutes a structural bypass of the whole control regime; it must not be filed as a low-priority √-consistent item merely because "the documentation does not lie". Typical case: the documentation for `<udp-API>.send`/`write`/`connect` honestly states "can connect to any IP and domain" (zero domain control; in isolation a √ honest item), but because it stands in a relation of complete functional substitution with `<network-request-API>`/`<upload-API>`/`<download-API>`/`<tcp-API>` in the same domain (all governed by the domain whitelist) with respect to the effect "transmitting data out", it constitutes a structural bypass of the domain-whitelist regime and must be presented in the report as a highest-priority finding; it must not be downplayed merely because "the documentation is honest".
- **Parameter-level hidden field** (new; differs from "API-entry-level documentation missing" in granularity): this API entry **does** have public documentation, but one specific parameter it accepts is **entirely unrecorded in the documentation**, and the code confirms the parameter genuinely exists and changes runtime behavior (e.g. deciding whether to retain some class of sensitive data, or whether to take some special branch). Unlike "API-entry-level documentation missing" (the whole API has no documentation), this label describes the finer-grained deviation "the API has documentation, but there is a documentation blind spot at parameter level"; it is easily missed by coarse-grained checks such as "verify whether documentation exists at all", and requires comparing, parameter by parameter, whether the fields the code actually accepts are exactly consistent with those the documentation lists (not merely checking whether documentation exists for the API name). This label often co-occurs with pattern B2 (internal privilege, tightening direction), because a "hidden parameter" is often precisely the concrete carrier of a privilege symbol — but the two concepts differ: pattern B2 describes "the direction of the privileged behavior", while "parameter-level hidden field" describes "the degree to which that privilege carrier is exposed at the documentation layer"; record them separately.

## Evidence Strength Tiers (Confidence Annotation of Conclusions; General Rule)

When producing review results or analysis conclusions, annotate each conclusion with the tier of its evidence source; do not conflate "confirmed code fact" with "speculation":

1. **Direct code implementation evidence (strongest)**: the conclusion comes directly from a readable function-body branch decision, a permission-mapping-table entry, a field assignment statement, etc., and can be supported by a concrete code line number or function name; no word such as "speculated" is added;
2. **Indirect support from official documentation (second strongest)**: code evidence is insufficient, but some indirect clue in the documentation (an example value, a naming convention, a related field) points in the same direction as the code evidence and can serve as cross-support; it must be written explicitly as "indirect support" rather than "direct proof";
3. **Speculative conclusion (must be annotated explicitly)**: because the target code file does not cover the relevant implementation, or it can only be inferred indirectly from statistics/telemetry tables, and no independently readable check branch can be found, annotate honestly as "code evidence insufficient / speculative / unconfirmed"; do not over-extrapolate, and do not skip recording this API merely because evidence is insufficient — retaining the very fact that "the evidence tier is lowest" is itself an important output.

This tiering should run through code review, cross-validation, and composition-channel investigation alike; the final report should aggregate the global evidence-tier situation once, in the methodology notes.

**New warning: debug-only pass-through branches in the developer-tool/simulator environment pollute evidence strength (new finding; must be checked)**: code commonly contains branches of the form `if (isDevtools/isSimulator) return {pass-through result}` — such branches are designed specifically for the developer-tool/simulator environment and **unconditionally skip the real permission/domain/legality checks**, and may behave in a way entirely opposite to the real-device branch. The existence of such branches directly affects the credibility of the highest tier of evidence, "direct code implementation evidence": **even when a concrete judgment function body is found (which would otherwise count as the strongest evidence), if it has not been confirmed whether that function hits a debug-only branch under the runtime environment used for the current analysis/validation, the conclusion still cannot be treated as the strongest evidence about "real-device behavior"**. Requirements: (i) during static code review, whenever any check function is found, simultaneously check whether an environment-judgment branch exists inside it (common judgment variables include `isDevtools`/simulator flags/environment-type judgments like `Se.CS`); if one exists, record separately the two conclusions "behavior under the developer-tool environment" and "behavior under the real-device environment", rather than only one of them; (ii) during runtime empirical testing (together with dynamic validation requirements such as "Reachability Determination for Component-Specific APIs"), execution must prioritize the real-device environment; when validation is possible only in the developer tool, first confirm that the check function has no debug-only short-circuit branch, otherwise the empirical conclusion may be entirely opposite to the real-device situation, and it must be explicitly annotated "! validated only in the developer-tool environment; may not represent real-device behavior".

**New warning: `<view-data-writer>`/assignment statements inside a component/API cannot be upgraded directly to "cross-thread readable" evidence (evidence-strength discipline)**: seeing `this.<view-data-writer>({...})` or a direct assignment `this.data.xxx = ...` inside a component method body in static code **may only be recorded as "a code clue / hypothesis pending validation", not as "direct code implementation evidence"** — even when what is assigned is a high-value field such as a friend's nickname or avatar. Reason: a `<view-data-writer>` call in a mini-program rendering-layer component may be either "an internal rendering-layer state update used to trigger template re-rendering within the same render tree" (not synchronized across threads to the Service layer, hence unreadable from JS) or "genuinely cross-thread bridged data to the Service layer" (readable from JS) — the single line `<view-data-writer>` cannot distinguish these two cases textually, especially when the component uses **exactly the same underlying registration mechanism as some known natively-rendered isolated component** (e.g. `p(componentName).options().behavior().template().definition().registerComponent()`); even less may one apply the intuition that "different-looking functionality must be implemented differently". **The evidence strength of such a conclusion is capped at the "code clue" tier; it can be upgraded to "confirmed by both code and empirical test" only after the Layer 1 runtime probe of the "Reachability Determination for Component-Specific APIs" section (`selectComponent` + `fields({node:true})`)**. Intermediate artifacts and stage reports must not skip empirical testing and write such a conclusion directly as a final conclusion (even under later time pressure this step may not be omitted; honestly annotating "pending empirical confirmation" is better than giving an unverified final conclusion).

## Reachability Determination for Component-Specific APIs (Mandatory Runtime Probe; Includes the "Two-Level Reachability" Method)

### Trigger Signals (Any One Requires Starting This Section's Determination Flow; Concluding From Code Walkthrough Alone Is Not Allowed)

- **Signal T1 (direct invocation anomaly)**: the permission mapping table / Service layer confirms an API is "genuinely registered with a real implementation", but business code calling `wx.xxx(...)` directly raises `TypeError: xxx is not a function` (or `typeof wx.xxx !== 'function'`) — indicating the method is not mounted on the business-accessible `wx` instance.
- **Signal T2 (component-internal state assignment, new)**: while reviewing the implementation code of a custom/built-in component, its internal methods are found to contain `this.<view-data-writer>({...})` or direct assignments such as `this.data.xxx = ...`, which textually "looks like" it wrote some data (especially high-value fields such as a friend's nickname, avatar, or identity identifier) into the component's `data` — **this is only a code clue pending validation, not evidence that "it is readable from the JS side"**. Regardless of whether that data is subsequently rendered and displayed by the component template, the determination flow below must be followed; one must not conclude directly from seeing `<view-data-writer>` that "developer JS can read this data".

Signals T1 and T2 often appear simultaneously on different facets of the same case (e.g. "when a component internally invokes an API, that API stored the result via <view-data-writer>, but whether the component itself is reachable and whether the API can be invoked independently of the component are two separate questions"). Therefore determination must validate the two levels separately per the "two-level reachability model" below; examining only one level before concluding is not allowed.

### Two-Level Reachability Model (Core, New)

When the object of analysis is a structure of the form "a component internally invokes some platform API", "the component itself" and "the API invoked inside the component" must be treated as two **independent** reachability questions and validated separately; neither may be inferred from the other (if one is confirmed safe/unsafe, that cannot be applied directly to the other level):

| Level | Object of determination | Method | Independence note |
|---|---|---|---|
| **Layer 1: the component's own methods / `data`** | Internal methods used for component template rendering (e.g. `<legacy-profile-API>(index)` returning a cached field), the component's `this.data` | See "Layer 1 Determination Flow" below (`selectComponent` + `fields({node:true})`) | Answers only "can one obtain the instance via `selectComponent` through this UI component itself and read its internal methods/data" |
| **Layer 2: the independent platform API invoked inside the component** | A platform API invoked inside the component method body as `wx.xxx(...)` and registered independently in the permission mapping table / Service-layer API registry | See "Layer 2 Determination Flow" below (`typeof` existence check + direct invocation + permission-trace comparison) | Answers only "leaving this UI component aside, can a developer invoke the same API directly in their own business code and obtain the same data" — even if Layer 1 is determined "unreachable" (the component is natively rendered and isolated), Layer 2 may still be independently reachable (the API may itself be a public interface developers can call directly, merely having also been used internally by this component on this occasion) |

**Why the levels must be separated rather than merged**: the fact that a component internally invokes an API proves only that "this invocation path exists by design", not that "this invocation path can only be triggered through that component" — many platform APIs are themselves independently registered public interfaces (possibly registered separately in the Service-layer API registry) and can be invoked directly by developer business code, regardless of "whether they were once used internally by some built-in component". Conversely, even if at Layer 2 the API cannot currently be verified as directly callable due to runtime-mode/scene limitations, one must not thereby infer that Layer 1 (the component itself) is necessarily safe or necessarily unsafe — the two are two parallel, distinct attack surfaces and must be evidenced separately.

### Layer 1 Determination Flow (Whether the Component's Own Methods/`data` Are Readable)

**At this point it is forbidden to conclude "equivalently extractable via `selectComponent`" merely from the component's `methods`/`data` definitions in the rendering-layer code (e.g. some method that appears able to read raw data, or the `<view-data-writer>` call of trigger signal T2)** — a component's method/`data` definitions prove only that "the logic exists in the design state", which is not equivalent to "programmatically accessible to business code at runtime". One of the following two determination paths must be taken to a conclusion:

1. **First check whether a non-open-component path remains reachable**: confirm whether the function carried by this component has any invocation route that does not go through this specific built-in component (e.g. another `wx.xxx()` alias, or forwarding through an ordinary custom component). If one exists → determine it as **still reachable**, handle it as a conventional directly callable API, and there is no need to enter the component runtime probe flow below.
2. **When it can be invoked only through an open component (native component), runtime measurement is required to determine whether the component is a "natively rendered layer component"**:
   - After the page/component `<lifecycle-ready-hook>`, execute: `this.<selector-query-API>().select(selector).fields({node:true,id:true,dataset:true}, cb).exec()`, and simultaneously execute `this.selectComponent(selector)`;
   - If the `fields()` result **does not contain a `node` field** (even though `id`/`dataset` return normally), and `selectComponent(selector)` returns `null` → the component is composited by the client's native rendering layer, there is no corresponding exparser node/component instance on the JS side, and the component's internal methods/`data` are **not programmatically accessible**; it can only be displayed visually and does not constitute a data-extraction channel;
   - If the `fields()` result **contains a `node` field** and `selectComponent(selector)` obtains a non-`null` component instance (with a non-empty `data` field / callable methods) → the component's internal methods/`data` are **genuinely reachable**, equivalent to invoking the data source directly, and should be included in tiering at the original risk level (and, because of the added concealment of "appears isolated but is in fact equivalently reachable", it should generally be treated as no lower risk than a direct invocation).
   - **Multiple type/sub-component variants under the same component tag family must each be measured separately; one must not infer, from a single variant (e.g. the single-item form) having been empirically confirmed isolated, that other variants of the same tag family (e.g. the list/item form) behave identically** — even when they share exactly the same underlying registration mechanism (e.g. `p(componentName).options().behavior().template().definition().registerComponent()`), Layer 1 determination should still be run once for each variant, as cross-confirmation rather than substitute evidence (see the "open-data component family" case below).
3. **Conclusion record format**: `component/method name | trigger signal (T1/T2) | Layer 1 empirical result (presence of node field + selectComponent return + data content) | final reachability determination (not programmatically extractable / equivalently reachable)`. Conclusions lacking the runtime measurement step must be explicitly annotated "! pending runtime validation"; determining the tier from static code alone is not allowed.

### Layer 2 Determination Flow (Whether the Independent Platform API Invoked Inside the Component Can Be Called Directly, Detached From the Component)

1. **Existence check** (reusing the ③ existence-detection method of `empirical-code-generation.md`): execute `typeof wx.<API name>` in the target business code (not inside the component):
   - If it is `"function"` → the API **is indeed mounted on the business-accessible `wx` instance**; proceed to the next step, permission-trace comparison;
   - If it is `"undefined"` (or a direct invocation throws `TypeError`) → the API **is not mounted in the current runtime environment/mode**; it **cannot** be determined directly as "unreachable", but can only be annotated "unreachable in the current environment; needs investigation of whether a specific runtime mode/scene gate is required for mounting" (see "runtime-mode gate" below) — **annotate the evidence insufficiency honestly, do not over-infer, and do not conclude that this independent API is necessarily safe merely because the component itself (Layer 1) has been determined safe**.
2. **Permission-trace comparison** (if the Layer 2 existence check passes): reusing the ① permission-trace comparison method, invoke the API directly from business code (constructing valid or placeholder parameters), compare the permission list (e.g. `authSetting`) before and after invocation for traces, and determine whether its permission-check path is independent of the component itself.
3. **Recommendation for investigating a runtime-mode gate**: if signal T1 / the existence check fails, and the API's other same-source functions (log prefixes, backend interface names invoked, etc.) overlap heavily with some functional domain known to require a "special runtime mode" (such as some embedding mode / mini-program launch mode), annotate the conclusion with "suspected runtime-mode gate", and note that this gate differs from both the scene-value judgment and the scope authorization in the "Additional Situations" section of `permission-layering-framework.md`; it is a third, independent admission dimension (see that file's "runtime-mode gate" entry). Do not confuse it with "scene-value judgment failed" or "missing scope authorization".

### Conclusion Summary Record Format (Both Levels Must Appear)

```
Component/API name | trigger signal (T1/T2) | Layer 1 empirical conclusion (reachability + evidence) | Layer 2 existence-check conclusion (reachability + evidence) | combined determination (e.g. "component unreachable but the internal API may be independently reachable; supplementary testing needed")
```

### Case Library (For Direct Reuse in Later Analyses of the Same Kind)

**Case 1 (the original source of this rule) — `open-data-list`/`open-data-item`.<legacy-profile-API>(index) (Layer 1)**: the initial judgment (reading only the component's `methods.<legacy-profile-API>` definition in the rendering-layer code, `return this.data.groupMembers[e]`) mistakenly concluded "batch user data can be extracted equivalently via `selectComponent`"; empirical testing later falsified this (`selectComponent` returned `null`, and `fields({node:true})` contained no `node` field), and "purely visual display, not programmatically extractable" is the final correct conclusion.

**Case 2 (re-check correction of 2026-08-13; revealed the "two-level reachability" structure and is an important supplement to Case 1) — `<group-member-API>` of the same component family (Layer 2)**: inside the `open-data-list` component, the `fetchGroupUserInfo` method body invokes, as `<group-member-API>({groupOpenIDList, success, fail})`, an **independently registered** platform API (this API is registered separately in the Service-layer API registry as `<group-member-API>: dz.w`, a completely different thing from the component's `methods.<legacy-profile-API>`; the names are similar but their layers of belonging differ, making confusion very easy). This analysis initially triggered signal T2 (seeing the component-internal `<view-data-writer>({groupMembers:...})` and directly concluding "fully readable from JS" — a real evidence-strength assessment error); after re-check, the Layer 1 flow empirically falsified the component's own reachability (consistent with Case 1's conclusion); but further investigation found that `<group-member-API>` **is itself a Layer 2 independent API that can in principle be invoked directly by developers, detached from that component** — its code has zero permission checks and is registered in no scope permission mapping table, and only because `typeof <group-member-API> !== 'function'` under the current runtime mode could its independent reachability not be finally confirmed in this test. **This is the first instance in which Layer 1 (component) and Layer 2 (API), two independent reachability questions, were observed simultaneously in one case**: Layer 1 has been falsified consistently by two empirical tests (Case 1 and this case), while Layer 2 retains the open question "suspected to require a special runtime mode to be mounted"; neither may substitute for the other in drawing a conclusion.

> **Reminder for later analysts**: when encountering the structure "a built-in/native component internally invokes an independent platform API", ask yourself two questions first: (i) can this component itself be read via `selectComponent`? (ii) can the API invoked inside this component be called directly from my own business code, detached from this component? The answers to the two questions may be entirely different (as in this case: (i) no, (ii) unknown/possibly independently yes), and answering only one of them is insufficient for a complete conclusion.

## Analysis Procedure

1. Collect all official/team documentation entries of the target functional domain (usually the field classes "parameters", "return values", "Configuration/usage", "application/activation and user authorization");
2. Locate, one by one in the implementation code, each API's real implementation function, extracting its permission-check logic, field assignment logic, and permission-bit mapping table entries;
3. Compare item by item per the "review dimensions"; for any inconsistency, record it in the review result table with the corresponding "deviation classification label";
4. After aggregating the review result table, summarize by deviation type: "which API clusters have accurate, trustworthy documentation" and "which API clusters show concentrated deviations", providing the basis for later risk prioritization.

## Output Requirements

The artifact should contain a review result table with columns `API | documentation description | actual code implementation | consistency determination (√/× + classification label)`, plus a core-conclusions paragraph at the end stating at least:
- Which class of API (e.g. "pure device measurement", "pure rendering") shows high agreement between documentation and code, so the documentation can be trusted directly;
- Which class of API (e.g. "selection type", "composed invocation type", "parameter branch type") shows concentrated deviations, so the code's actual path must govern;
- Whether the three classes of systematically missing content are found (silent field handling, server-configurable bypass, cross-method state coupling), with at least one example of each;
- **Systematic / cross-API pattern recognition**: besides recording each individual API's deviation, additionally check whether these deviations exhibit a systematic regularity spanning the whole functional domain (e.g. "an entire batch of APIs at the junction of old and new permission systems is collectively absent from some historical data-structure document"); if so, summarize it separately as an independent finding rather than stopping at enumerating isolated cases — systematic patterns often point to defects in the documentation maintenance process itself and are more valuable than individual cases.
