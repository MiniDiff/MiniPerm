# General Three-Layer Permission Framework (Portable Skill-Builtin Version)

> This file is the reusable version of the general three-layer permission framework and contains no application cases for any specific domain (location, user profile, etc.). When analyzing, read this file in full to bring in context; do not copy it to the project root, and do not check whether a same-named file already exists there (if an earlier analysis left a same-named historical file in the project root, this file takes precedence — just keep using it, there is no need to maintain two copies).
>
> **Relationship to the data-value framework**: this file answers "which approval gates must be crossed to obtain this datum"; `data-value-framework.md` answers "how much privacy weight does this datum carry once obtained". The two are orthogonal dimensions, but not unrelated — the data-value framework already lists "degree of permission protection" as one auxiliary signal of value judgment (the more strongly permission-protected a datum is, the more likely it has already been recognized as high-value), so the two sets of judgments are positively correlated but not equivalent. When analyzing, always judge them **separately** and only then cross-compare; do not substitute one for the other, or you will miss mismatch cases of the form "same value, different permission" that break this positive correlation.

## The Three-Layer Permission Framework

Whether the APIs under analysis are location, user-profile, device-management, or any other type, their permission attribution is determined uniformly by the following three layers:

| Layer | Criterion | Sub-cases |
|---|---|---|
| 1. Code layer | Whether the API must be statically declared in `app.json` (or the equivalent application manifest) via fields such as `permission` / `requiredPrivateInfos`, **or** registered with a purpose category in an independent declaration file such as a privacy agreement or privacy-protection guideline | Declared once statically by the developer; a commitment made at development time, statically checked by the client or the review tooling at runtime or at submission. **Note that within this layer there may also be a granularity difference over "whether a declaration is required"** (see methodology reminder 5 below); one must not generalize to "APIs of this class never need a code-layer declaration" |
| 2. Platform layer | Whether the API requires platform review / activation before it can be used | (i) **Static review and activation** — category review before release, self-service activation in the admin console; one-off, effective before release; <br> (ii) **Dynamic operational exemption** — at runtime the platform server issues a whitelist along dimensions such as appId/page path; changeable at any time and effective without resubmission |
| 3. User layer | Whether the user must participate in the current operation when the API is invoked at runtime to obtain the datum | (i) **Consent via prompt** — the user takes a position on "whether collection is allowed"; the datum itself is produced automatically by the device/system (passive measurement), and can be refused **in advance**; <br> (ii) **Data generated by active user operation** — the content of the datum is decided by the user's on-the-spot manual action; there is no "accept/decline", only "what content to generate" (active disclosure); <br> (iii) **Post-hoc passive notification (new)** — the datum is obtained **without prior user consent** (the user cannot prevent it before it happens), but after the fact the system informs the user in a **non-blocking** way (e.g. a one-off toast/notice) that the operation occurred; the user can only "learn afterwards", not "prevent beforehand". Its privacy implication sits between (i) "prior consent via prompt" and "no awareness mechanism whatsoever", and must not be conflated with either: the presence of a notification does not make it equivalent in authorization strength to (i), nor does the impossibility of refusal make it equivalent to zero awareness |

## Additional Situations (Not Part of the Three Layers; Note Them Only as Remarks in Per-API Analysis)

- **Internal privilege layer**: an internal bypass mechanism controlled unilaterally by the platform (client/base library); developer code cannot reach it, trigger it, or perceive it. It is not part of any link in the developer/platform/user game.
- **Third-party data-source relay**: the datum comes from an external application or source, but that upstream party is bound by the same three-layer framework when generating/obtaining it; this application is merely the receiver, and no fourth layer is needed for "externally supplied".
- **System-level / host-app-level authorization prompts (new; an important scope boundary)**: the object of analysis for this framework is the authorization management at the layer "host app (e.g. WeChat) ↔ mini-program", and **the host app itself is assumed to have already been granted all relevant system permissions by the operating system**. Therefore prompts by which the OS requests system-level permission for the host app itself (e.g. "allow WeChat to use Bluetooth", "set WeChat as the default NFC payment app") **are not objects of analysis for this framework's three-layer determination**, and no risk analysis of them needs to be developed. The objective test for whether a prompt falls within this framework's scope is: **does consenting to the prompt write into the mini-program-level `<setting-API>().authSetting`?** If yes, it is genuine authorization at the "host app → mini-program" layer (a sub-case of user-layer "consent via prompt", included in the determination); if no, it is a system/host-app-level prompt (excluded). When encountering system/host-app-level prompts, **simply note their existence honestly in the per-API analysis** (e.g. "invocation triggers a system-level XX query, but it does not write to authSetting and therefore does not constitute mini-program-level authorization"); do not develop risk analysis of that prompt layer itself, so as to avoid confusion with this framework's core object of analysis.
- **Runtime-mode gate (new; a fourth dimension that fits none of the three layers; added 2026-08-13)**: the availability of some platform APIs depends neither on a user-layer prompt nor on scene-value determination (the latter branches on launch-context state within a single launch — the API itself is always mounted on the `wx` object, and merely returns success or failure according to the scene value), but on the **runtime mode** in which the mini-program was launched this time (e.g. the special launch mode some platforms have, such as a "chat-tool mode"). Under the default runtime mode such APIs are **not mounted on `wx` at all** (`typeof wx.xxx !== 'function'`; invoking throws a `TypeError` directly rather than returning a business-level failure), and they are mounted and become callable only when the mini-program is launched in that special runtime mode. **Key distinction**: when a scene-value gate fails, the API still "exists" (`typeof` is `function`), only the callback takes the `fail` path; when a runtime-mode gate fails, the API itself "does not exist" (`typeof` is `undefined`) — the two have a clear distinguishing marker at the code level and must not be conflated in records. The runtime-mode gate belongs neither to platform-layer "static review" nor to "dynamic operational exemption" (those control whether one can be listed / serve users publicly — a release dimension), nor to code-layer "whether static declaration is required" (a compliance commitment on the developer side); it is a gate on a **technical mounting dimension** — it is recommended to annotate it separately in the analysis report as a "runtime-mode gate", neither merging it into any of the three layers nor conflating it with "scene straight-through / A2 architectural non-integration" (`api-composition-and-equivalence-channels.md` pattern A2, which means "the API is always mounted but has no permission-check branch at all"). The runtime-mode gate concerns "whether the API can be invoked at all"; A2 concerns "whether there is a permission check after invocation" — both can hold for the same API (e.g. suspected to be mounted only in a special runtime mode, and once mounted to have no permission check whatsoever). Confirming whether this gate holds requires runtime measurement (a `typeof` existence check); static code analysis alone cannot confirm it. When the measurement environment does not satisfy that runtime mode, annotate honestly that "evidence is insufficient to confirm whether this gate exists" and do not over-infer.

## Methodology Reminders (General; Apply to All Domains)

1. **Permission determination must consider the invocation sequence, not an isolated description of a single API**: if API A (low/no permission) and API B (low/no permission) when invoked in composition produce an effect equivalent to some high-permission API C, then re-annotate A and B's permission requirements according to the "actual combined effect", rather than evaluating them in isolation.
2. **Platform-layer "static review" and "dynamic operational exemption" must be listed separately**: although both are unilateral platform decisions, their timing of effect, mutability, and checking party differ; annotate them separately rather than collapsing them into "platform-layer approved = permanently safe".
3. **User-layer "consent via prompt" and "actively generated data" must be listed separately**: both answer "yes" to "does the user need to participate this time", but their privacy implications are entirely different — the former is "consenting to monitoring", the latter "actively supplying one-off content"; conflating them leads to under- or over-estimating privacy risk.
4. **This framework and these reminders are universal to all API types**: when later analyzing APIs of any new domain in the same project, reuse this framework and its determination conventions directly; there is no need to re-argue whether the framework itself is sound. Simply add an "Application Cases" section to the target document to develop domain-specific content.
5. **"Zero permission at the runtime user layer" does not mean "zero obligation at the code layer" — verify separately (dual-track regime of privacy-agreement static declaration and runtime scope; new finding)**: even if an API has no authorization prompt whatsoever at the user layer (the runtime `checkPrivacy`/`scope` check branch is empty), it may still be required to make a **static declaration** (registering a purpose-category identifier) in the developer-side privacy agreement / privacy-protection guideline. This belongs to the development-stage commitment at the code layer; it is a compliance obligation detectable by review and entirely independent of whether a prompt appears at runtime. Analysis must verify "whether the runtime user layer shows a prompt" and "whether the code layer requires a static purpose declaration" separately; one must not conclude from the former being empty that the API is subject to no permission regime at all — in reality there may be two tiers: "no runtime permission but still requires static declaration" (still checkable by review) and "no runtime permission and no declaration of any kind" (fully outside the permission regime, a review blind spot). The latter has weaker actual binding force; the analysis conclusion must distinguish these two tiers clearly and must not collapse them into "zero permission".

2. The "Three-Layer Permission Framework" and "Methodology Reminders" sections themselves **should not be rewritten per domain**; modify them only when a defect in the framework itself is found or a new sub-case must be added (modifications follow the confirmation-protection flow of Step 13 in the skill's `SKILL.md`).
