# Unified Theory of Permission-Control Flaws: A Formal Classification of Equivalence Channels and Bypass Patterns

> **Positioning of this file**: `api-composition-and-equivalence-channels.md` is the **operational rule** Step 8 uses directly (giving the investigation method, danger signals, and examples for each pattern); `equivalence-path-validation-methodology.md` is the **quantitative validation method** Steps 9-11 use (giving a numerical decision of "to what degree two paths are equivalent"). This file is the **theoretical layer** above both: it answers what the formal definition of the concept "permission-control flaw" itself is, where the various discovered patterns sit within a unified classification space, and how to discover — systematically rather than by relying on known named cases — new patterns in that space that have not yet been named.
>
> Motivation for this file: patterns A-E in `api-composition-and-equivalence-channels.md` (extended to A-F in the same revision as this file; see §3 below) were discovered and appended one at a time across successive analyses, by the method "find a concrete case → induce a rule → append it to the file". The limitation of this inductive style is that **each rule's scope is tightly bound to the concrete case of its discovery**, which easily lets later analysts degenerate into "only recognizing cases already written down". This file attempts to extract, in reverse, from all discovered cases (including the 5 newly added here: C3 / D2 effect-achievement extension / E2 / F1 / F2) **a set of orthogonal classification dimensions**, upgrading the pattern catalog from "a list of cases" to "a set of coordinate points in a classification space" — a future case not covered by any named rule can, as long as it can be located in this coordinate space, be systematically recognized as "a new instance under some known dimension combination" or as "revealing a new dimension not yet covered by the existing dimensions", without waiting until it has been written down as the Nth named case before it can be recognized.

## 1. Formal Definition of the Problem

### 1.1 System Model

A capability-controlled mobile application platform (such as the WeChat mini-program runtime) can be abstracted as a three-tier delegation chain:

```
Operating system (OS)  --authorizes-->  Container / super-app (Container)  --should in turn authorize internally-->  Guest / mini-program (Guest)
```

The three-layer framework already defined in `permission-layering-framework.md` ("code layer / platform layer / user layer") answers "**who** approves" (developer static declaration / platform review / user's per-invocation consent) — **all three of these layers belong inside the single `Container→Guest` link, differing only in their trigger/effect timing** (code layer: the static-declaration moment in the development phase; platform layer: the pre-release review or runtime dynamic-exemption moment; user layer: the runtime per-invocation moment); only their conjunction constitutes the judgment "has the container established complete sub-approval for this capability toward the mini-program". On this basis, this file introduces an **orthogonal** axis answering "besides the approval of this `Container→Guest` link, does a more upstream authorization premise at the `OS→Container` level also exist" — because the root of the great majority of permission flaws is not "unreasonable approval standards", but "the approval at the `OS→Container` layer objectively exists and is mistaken as equivalent to an equal approval at the `Container→Guest` layer (i.e. code ∧ platform ∧ user), while the latter is in fact empty".

For any capability `E` (data acquisition or hardware/resource control), its true permission requirement should be the conjunction of the approval requirements of each link in the chain:

```
Required(E) = OS→Container layer requirement ∧ Container→Guest layer requirement
            = OS→Container layer requirement ∧ (code layer ∧ platform layer ∧ user layer)
```

**The link-layer root of a permission flaw can be summarized in one sentence: the approval at the `OS→Container` layer objectively exists and is mistaken as equivalent to an equal approval at the `Container→Guest` layer (code ∧ platform ∧ user), while the latter is in fact empty.** This is precisely the **causal mechanism** of the great majority of pattern A2 cases (see below), not merely a surface symptom.

### 1.2 Formalization of Capability, Path, and Permission Vector

- **Capability** `E`: an observable target effect, in two classes (per the "two parallel threads" of `data-value-framework.md`):
  - `E = ACQUIRE(F)`: obtaining the data in field set `F` (data-acquisition class);
  - `E = ACT(O)`: producing effect `O` on the external world (hardware-control / network-output class, e.g. "turn on the flashlight", "send a sequence of bytes to some address", "overwrite the content of an NFC tag").

- **Path** `p = ⟨call_1, call_2, ..., call_n⟩`: an ordered sequence of one or more API calls (when `n=1` it degenerates to the single-API case, corresponding to patterns A/B/D/E; when `n≥2` it is the composition case, corresponding to pattern C). Path `p` **implements** capability `E`, written `p ⊢ E`, if executing `p` allows observing the effect described by `E` (data obtained, or external state changed).

- **Permission vector** `R(p)`: a four-tuple
  ```
  R(p) = ⟨osGate(p), code(p), platform(p), user(p)⟩
  ```
  where `code(p)`/`platform(p)`/`user(p)` **correspond exactly** to the already-defined code/platform/user layers of `permission-layering-framework.md`; their conjunction is the `Container→Guest` layer requirement (corresponding respectively to the three trigger timings: static declaration in the development phase / pre-release review or runtime dynamic exemption / runtime per-invocation). `osGate(p) ∈ {N/A, Present}` is the coordinate **newly added** by this file, corresponding specifically and solely to the `OS→Container` link. The **objective criterion for its value is taken directly from the "system / host-app-level authorization prompt" definition in the "Additional Situations" section of `permission-layering-framework.md`**:
  - `Present`: the implementation of path `p` depends on a system / host-app-level authorization premise that occurs only at the `OS→Container` layer and **is not written into the mini-program-level `<setting-API>().authSetting`** (e.g. system-level inquiries such as "allow WeChat to use Bluetooth" or "set WeChat as the default NFC payment app", or system-level hardware switches).
  - `N/A`: the implementation of path `p` does not depend on any `OS→Container`-layer authorization premise — i.e. in this capability's implementation chain, every link that has an authorization action has its consent result **written into** the mini-program-level `authSetting` (and is therefore already fully covered by `(code, platform, user)(p)`), and no bypass of the form "upstream authorization does not land in authSetting" exists.

  `osGate(p)` and `(code(p), platform(p), user(p))` are two entirely independent, non-overlapping objects of judgment; the dividing line is whether `authSetting` is written: the former asks "has the container obtained the upstream qualification to operate this resource/capability (and is that qualification absent from the mini-program-level authorization ledger)", the latter asks "has the container further sub-approved this qualification to the specific mini-program (and written it into the mini-program-level authorization ledger)". The typical signature of pattern A2 is precisely `osGate(p1) = osGate(p2) = Present` (both paths depend on the **same** `OS→Container`-layer authorization premise, e.g. both depend on the system Bluetooth switch), while `(code, platform, user)(p1)` is entirely empty and `(code, platform, user)(p2)` is non-empty — i.e. the gap occurs precisely at the `Container→Guest` link, not the `OS→Container` link.

- **Capability equivalence**: `p1 ≈_E p2` means both `p1` and `p2` can implement capability `E` (or the combination `{p1,p2,...}` jointly implements `E`), and `EquivDegree(p1,p2)` as defined in `equivalence-path-validation-methodology.md` (for `ACQUIRE`-type), or the corresponding effect-consistency test (for `ACT`-type; effect-equivalence judgment is in §4.4), exceeds the decision threshold determined by data/effect value.

### 1.3 Formal Decision of a Permission-Control Flaw

A permission-control flaw has **two mutually independent, non-exclusive** proof structures. The great majority of known patterns (C/D/E/F, and the sibling-capability comparison of A1/A2) rely on **horizontal inter-path comparison** — this was the original definition, and also the most intuitive and easily conceived way of gathering evidence; but the core case of A2 (see §3·A2) reveals another, more fundamental proof structure that does not depend on an external control: **vertical intra-chain tier self-evidence**, which needs no second path and can conclude independently from the candidate path's own tier asymmetry on the delegation chain. The two structures together constitute the complete extension of the permission-control-flaw decision: **a candidate need satisfy only one of them to be judged a flaw; if it satisfies both, that should be treated as mutual corroboration by two independent evidence chains, and the resulting evidence strength should be higher than a candidate satisfying only one — the two must not be treated as an either/or choice.**

#### 1.3a Horizontal Inter-Path Comparison (Inter-Path; original definition)

> If there exist two (or two groups of) paths `p1`, `p2` with `p1 ≈_E p2`, and `R(p1)` is strictly weaker than `R(p2)` at **any one link** of the delegation chain (i.e. `R(p1)`'s requirement at that link is empty while `R(p2)`'s is non-empty), then `(p1, p2)` constitutes a **permission-control flaw** with respect to capability `E`.

This definition deliberately remains "environment-agnostic" — it does not specify whether `p1`/`p2` are single APIs or compositions, whether they cross functional domains, or whether they are different operation branches of the same resource; this is precisely so that the three-axis classification below becomes a coordinate system that **further subdivides on top of this definition**, rather than part of the definition itself. **The premise for 1.3a to hold is that `p2` can be found** — for capabilities with no functionally/semantically comparable "sibling path" (e.g. NFC read/write, HCE, where the WeChat ecosystem has no other higher-permission comparison API achieving the same effect), 1.3a cannot complete the decision alone and must rely on 1.3b below.

#### 1.3b Vertical Intra-Chain Tier Self-Evidence (Intra-Path Cross-Tier; new)

> If there exists a path `p` implementing capability `E`, with `osGate(p) = Present` (the qualification-acquisition stage of this capability has an explicit `OS→Container`-layer authorization premise, i.e. the upstream delegator has identified it as a sensitive capability requiring dedicated authorization), but `(code(p), platform(p), user(p)) = (∅, ∅, ∅)` (the `Container→Guest` layer has established no sub-approval for it whatsoever), then `p` **itself** constitutes a permission-control flaw, with **no need** to find another comparable path `p2`.

This decision rests on the **Monotonicity Assumption** of the delegation chain: in a delegation chain, the approval strength of a downstream link for a capability should not be strictly lower than the approval strength already established by the upstream link — since the upstream (`OS→Container`) has determined that this capability needs a dedicated authorization gate (`osGate(p)=Present`), a downstream (`Container→Guest`) that sets no gate at all violates this assumption by itself, constituting **self-sufficient** evidence requiring no external control.

**Precondition for 1.3b**: it is meaningful only when `osGate(p) = Present` — if `osGate(p) = N/A` (the capability never involves any `OS→Container`-layer authorization premise; a purely software/logical capability), there is no "upstream baseline" to self-compare against, 1.3b degenerates to an empty judgment, and one can only resort to 1.3a. This explains why the vertical self-evidence structure appears almost exclusively in pattern A2 (and theoretically any `osGate`-related capability) — the very concept of "flaw" in patterns C/D/E/F is "two different paths achieve the same capability but with different permission requirements"; the path itself usually involves no independent `OS→Container`-layer authorization premise, so no single path offers a vertical baseline for self-comparison, and these structurally depend on horizontal comparison.

**Relation of 1.3a and 1.3b (illustrated with Beacon / NFC; the full case is in §3·A2)**:
- **Beacon scanning** satisfies both structures — horizontally: compared with the sibling capability "ordinary Bluetooth scanning" (`<adapter-API>` + `<ble-scan-API>`), the `Container→Guest`-layer permission requirements differ sharply; vertically: `<discovery-API>` itself has `osGate=Present` (system Bluetooth permission) while all three layers are empty. The two evidence chains hold independently and corroborate each other, the strongest evidence form.
- **NFC read/write / HCE** satisfies only the vertical structure — within the WeChat ecosystem there is no higher-permission "sibling API" achieving an equivalent effect for horizontal comparison (1.3a cannot apply), but the vertical self-evidence that the whole `<nfc-adapter-API>` family has `osGate=Present` (system NFC permission) while all three layers are empty still holds independently and is sufficient to conclude alone, with **no reduction of evidential force for lack of a comparable object**.

Any newly discovered concrete pattern should first be tested against whether it satisfies at least one of 1.3a or 1.3b, before considering its coordinates in the three-axis space below.

## 2. Three Orthogonal Classification Dimensions

Existing patterns A-F (and the content newly added here) can be completely re-located by the following three **orthogonal** dimensions. "Orthogonal" means the values of the three dimensions can be combined arbitrarily, with no hidden dependency such as "choosing a value on axis one automatically determines the value on axis two" — this is precisely the core improvement of this file over a "case-list" catalog: the previous A-E numbering order conflated these three dimensions, making answers to questions like "does pattern C discuss only compositions" or "does pattern D discuss only cross-category" prone to blurring.

### Axis One: Comparison Grain — What `p1` and `p2` Each "Are"

| Value | Meaning | Corresponding existing/new patterns |
|---|---|---|
| **Single vs single (1:1)** | Both `p1` and `p2` are single API calls | A, B, D, E |
| **Composition vs single (N:1)** | `p1={a,b,...}` is a composition of multiple APIs, `p2` is a single (usually higher-permission) API | C |
| **Operation branch vs operation branch (1:1, same resource)** | `p1` and `p2` are different CRUD operation branches on **the same logical resource** (e.g. read vs write); the object of comparison is not "two paths obtaining the same datum" but "two operations on the same resource, whether each one's protection strength is commensurate with the risk it creates" | **F (new)** |
| **Cross-chain-tier** | The objects of comparison are the approval states of two different links of the delegation chain (`OS→Container` vs `Container→Guest`), not two peer-level APIs | **The causal-mechanism layer of A2** (see §1.1); it is the **attribution** of the A2 phenomenon, not itself an independently comparable "path pair" |

### Axis Two: Trigger Condition — How the Permission Gap Is "Exposed"

| Value | Meaning | Corresponding existing/new patterns |
|---|---|---|
| **Unconditional / architectural** | Invoking the path at any time bypasses approval; does not depend on scene, parameter, or timing | A2 |
| **Scene / environment-value triggered** | Approval is bypassed only when a specific scene value / source-party flag is hit | A1 |
| **Parameter-value triggered** | Passing a specific parameter value degrades into an equivalent read or an inspection-free channel | E (some variants), the writer side of C1 |
| **State / timing triggered (TOCTOU type, new)** | Approval occurred at **some past moment**; afterwards the permission state may have changed (user revoked, session expired), yet the path at **the current invocation** does not re-verify but reuses the past decision result | **E2 (new)** |
| **Composition / sequence triggered** | Invoking any single member alone does not exceed authority, but the whole exceeds it after invocation in a specific order/combination | C |

### Axis Three: Capability Nature — What Kind of Effect `E` Is

| Value | Meaning | Corresponding existing/new patterns |
|---|---|---|
| **Data acquisition (ACQUIRE)** | Substantive information is returned to the mini-program JS layer after invocation | The great majority of classic A-F cases |
| **Hardware control (ACT-Hardware)** | The invocation produces an effect on physical hardware, returning no new data (e.g. vibration, NFC tag writing) | Applicable to A-F equally, but the equivalence decision must use the effect-consistency test of §4.4, not the six-dimensional data-value standard |
| **Network egress / output (ACT-Egress)** | The invocation sends data to an external network destination; the effect is "data leaving the device" rather than "data entering the JS layer" | The typical extended scenario of D2 (e.g. UDP vs domain whitelist); this file makes explicit that such cases must not be missed through being misled by the existing "data acquisition" wording |

> **Methodological reminder (the independent value of axis three)**: the textual descriptions of existing patterns A-E commonly use wording like "obtain data" and "read", which easily leads an analyst investigating pattern D (cross-functional-domain substitution channel) to search only for other paths that "can obtain the same datum", forgetting to search for other paths that "can achieve the same external effect (send/control/write)". §3.4 (the extension note for D) together with this axis constitutes the repair of this systematic blind spot: **when applying any pattern, one must explicitly declare which of the three natures its target capability belongs to, and choose the corresponding equivalence decision method by that nature**; one may not assume by default that all patterns handle only data acquisition.

## 3. Complete Pattern Catalog (Re-located in the Three-Axis Space)

The following is presented in alphabetical order by pattern, each annotated with its coordinates in the three-axis space, with concrete cases given or cited. **Italic** parts are newly added/revised here; unmarked parts follow the existing definitions in `api-composition-and-equivalence-channels.md`, with only coordinate annotation and cross-references added, without re-expanding the investigation methods (those remain governed by the rules file).

### Pattern A: Scene/Environment Straight-Through and Architectural Non-Integration

- Axis one: single vs single; Axis two: A1 = scene-triggered / A2 = unconditional architectural; Axis three: can cover all three capability natures

**A1 (scene-value whitelist straight-through)**: coordinates unchanged; examples in the rules file (referrer scene straight-through).

**A2 (architectural non-integration straight-through)**: coordinates unchanged, but its **causal attribution** is supplemented — *the root cause of the great majority of real A2 cases is a specific gap in the sense of axis-one "cross-chain-tier": the approval at the `OS→Container` layer objectively exists (e.g. the system grants Bluetooth/NFC permission to the WeChat app as a whole), but the `Container→Guest` layer (from the WeChat app to the specific mini-program) has never established a corresponding secondary approval for this capability; analysts easily mistake "the system layer already controls it" as equivalent to "the mini-program layer is also controlled", which is precisely why A2 is covert and why it lacks the at-a-glance signals of the kind "multiple APIs with different permissions share the same decision function"*.

**Two independent proof paths for A2 (new; directly correspond to §1.3a/1.3b)**: an A2 candidate's establishment does **not require** both of the following paths; either path holding independently suffices to conclude; if both hold, they should be recorded as mutually corroborating double evidence, not as a "choose one of two sufficient conditions" that can substitute for each other — this is the most important correction of this revision relative to the early analysis flow: the early flow implicitly treated "whether a sibling API can be found" as a necessary condition for A2, so capabilities without sibling APIs (such as NFC) were easily missed.

| Proof path | Precondition | Decision method | What to do if not found / not satisfied |
|---|---|---|---|
| **Horizontal: sibling-capability comparison** (corresponds to 1.3a) | Within the same functional domain there exists another "sibling API" with higher permission requirements accessing the same underlying hardware/data source | Compare link by link the `R(·)` of the candidate path `p` and of the sibling API `q`, proving that `R(p)` is strictly weaker than `R(q)` at the `Container→Guest` layer | If the functional domain genuinely has no sibling API comparable at the semantic/hardware level (e.g. NFC read/write has no control object in the WeChat ecosystem), the horizontal path does not apply — **this must not lead to judging A2 not established**; switch to the vertical path |
| **Vertical: intra-chain tier self-evidence** (corresponds to 1.3b) | The capability has `osGate(p)=Present` (an explicit system / host-app-level authorization premise exists; criteria in the "system / host-app-level authorization prompt" section of `permission-layering-framework.md`) | Prove that all three of `(code,platform,user)(p)` are empty (Service dispatch route is null / pure native forwarding; the privacy-agreement declaration table does not include it; no scope-judgment branch at runtime) | If `osGate(p)=N/A` (the capability never involves a system-level authorization premise), the vertical path does not apply and one can only rely on the horizontal path; if at that point there is also no sibling API for horizontal comparison, the candidate **cannot be decided by A2** and one should consider whether it belongs to another pattern |

*Methodological significance of the two paths: the limitation of the horizontal path is its dependence on the contingent domain feature "whether a sibling API can be found" — not every capability naturally has a control object. The vertical path depends on no external control; it suffices to prove the internal tier asymmetry "upstream has a gate, downstream has none", and it is therefore the **more general, less named-case-dependent** decision device in A2 investigation, and should be the default first investigation action (do vertical self-evidence first, with horizontal sibling comparison as a bonus/corroboration), rather than treating "finding a sibling API" as a precondition for A2 as the early analysis flow did.*

*On this basis, the predictive detection heuristic can be upgraded from "prior candidate, still requiring further confirmation" to "a sufficient and independent decision basis": for any capability whose underlying invocation ultimately depends on a permission the operating system grants to the container (super-app) as a whole (i.e. `osGate(p)=Present`, criteria being the class of prompts referred to in `permission-layering-framework.md`'s "system / host-app-level authorization prompt" section and explicitly excluded from that framework's three-layer analysis scope), the analyst should proactively check "whether `(code,platform,user)(p)` is indeed empty on all three layers"; **once the three layers are confirmed empty, the candidate already constitutes independent flaw evidence in the 1.3b sense, with no need to wait for / depend on finding a sibling API before concluding** — finding a sibling API is only corroboration, and its absence does not prevent the decision from holding. This heuristic explains why A2 cases recur with identical structure across multiple unrelated functional domains:*

| Case | Horizontal path (sibling-capability comparison) | Vertical path (intra-chain tier self-evidence) | Evidence form |
|---|---|---|---|
| Beacon scanning | Compared with `<adapter-API>`+`<ble-scan-API>` (ordinary BLE scan): both use BLE hardware, the sibling API requires `scope.bluetooth`, Beacon requires none | `<discovery-API>` itself: `osGate=Present` (system Bluetooth permission), three layers empty | **Dual evidence chain** (horizontal + vertical, each holding independently, mutually corroborating) |
| NFC read/write / HCE | No semantically comparable sibling API in the WeChat ecosystem (no other "higher-permission, equivalent NFC read/write effect" comparison channel exists), **horizontal path does not apply** | The whole `<nfc-adapter-API>` family itself: `osGate=Present` (system NFC permission), three layers empty (no mini-program-level scope / privacy-declaration layer) | **Single evidence chain** (vertical only), holding independently with sufficient evidence, with no reduction of decisional force for lack of a sibling API — this is precisely the core value of 1.3b over 1.3a: removing the contingent domain feature "whether a sibling API exists" from the preconditions of "whether a conclusion can be reached" |
| *mDNS LAN discovery (new corroborating case from the network-class analysis)* | *No clear sibling control API identified yet (subject to later investigation in the specific functional domain)* | *The system grants the WeChat app local-network/LAN-discovery capability (`osGate=Present`); the Service dispatch layer routes 10 APIs including `<mdns-API>` uniformly to `null`; three layers empty — completely isomorphic to Beacon/NFC* | At least a single evidence chain (vertical) holds |

> The mDNS case demonstrates the **cross-domain predictive power** of the vertical proof path — it is not an explanation specific to Beacon/NFC, but independently reproduces the same structure in an entirely different functional domain (network rather than hardware), confirming that "intra-chain tier self-evidence" is a transferable detection dimension independent of named cases, not a coincidence of a single case.

### Pattern B: Internal Privilege Symbols / Flags

- Coordinates and definition unchanged; see B1/B2 of the rules file. This file does not revise them.

### Pattern C: Cross-Method Composition Equivalence

- Axis one: composition vs single; Axis two: composition/sequence triggered; Axis three: mainly data acquisition, but the composition target may also be the reproduction of an `ACT`-type effect

**C1 (state-coupling type) / C2 (composition-escalation type)**: coordinates and definitions unchanged; see the rules file.

**C3: Named-benchmark composition equivalence (new)** — *when the target of the composition `{p1,p2,...}` is not "an escalation of value has occurred" in the abstract sense (C2's criterion), but can be **precisely benchmarked against a single higher-permission API `q` that already exists in the functional domain**, it should preferentially be classified as C3, because this converts "does it constitute a flaw" from a vague value comparison into an exactly computable permission-vector comparison: whether `R({p1,p2,...})` reaches `R(q)`.*

*Investigation method: for any set of low/medium-permission APIs `{p1,p2,...}` within a group, proactively search whether a single higher-permission API `q` exists in the same functional domain whose returned data / achieved effect stands in a potential capability-equivalence relation with the result of composing `{p1,p2,...}` (`{p1,p2,...} ≈_E q`); if so, do not rest content with the C2-style qualitative judgment "the value after composition is indeed higher", but further compute whether `R({p1,p2,...})` has a gap relative to `R(q)` — if the composed path is inspection-free at some link of the delegation chain while `q` has approval at that link, judge it a flaw; if the approval requirements of the two are identical (even if each triggers multiple checks), record it honestly as "the composition and the single API are permission-equivalent; a healthy-design positive example", and do not exaggerate it as risk.*

*Relation of C3 and C2: C2 is the **fallback decision** for "confirming that a non-additive escalation exists, but not necessarily being able / needing to find a named benchmark target"; C3 is the **strengthened decision** for "a named benchmark target has been found, so an exact permission-vector computation can be performed" — when investigating, first try to find a C3-style named benchmark target, and only fall back to C2's abstract value-escalation judgment when none is found; the two are not mutually exclusive, and when C3 is satisfied, C2's decision conditions are naturally also satisfied.*

### Pattern D: Cross-Functional-Domain / Cross-Category Substitution Channel

- Axis one: single vs single; Axis two: unrestricted; Axis three: D's investigation **must cover both ACQUIRE and ACT-Egress/ACT-Hardware capability natures** (new note)

**D1/D2**: coordinates and definitions unchanged; see the rules file.

*Supplementary note (repairing the capability-nature blind spot): D's original investigation-method description focuses on "whether an alternative acquisition path exists for the same high-value **data**", which easily leads an analyst to overlook the isomorphic question "whether an alternative achievement path exists for the same **effect** (especially network egress / hardware control)". This is not a new subtype but an explicit scope-extension statement for D — when investigating D, two questions must be raised simultaneously: (i) "can this datum be obtained through another seemingly unrelated category?" and (ii) "can this effect (sending out / controlling hardware) be achieved through another seemingly unrelated category, thereby bypassing the mechanism that should control that effect (e.g. a whitelist)?"*

### Pattern E: Permission-Check Target Substitution (Split into E1/E2)

- Axis one: single vs single; Axis two: E1 = parameter/logic-branch triggered; E2 = state/timing triggered (new); Axis three: mainly ACQUIRE/ACT-Hardware

**E1: silent scope substitution (former pattern E, renumbered)** — definition and investigation method unchanged: when the scope that should have been checked inside the same method is not authorized, it silently checks a different, semantically distinct scope instead, and passes as soon as the substitute scope is consented. Examples in the rules file (`<record-start-API>`).

**E2: permission-state expiry without re-validation (new, TOCTOU type)** — *the same method, at **this current invocation**, does not re-verify the **current** state of the permission it depends on, but by default reuses a historical authorization result "assumed still to hold" (e.g. assuming some precursor method previously succeeded in establishing a session/resource-level state, and therefore skipping the independent check this invocation should have), while that historical authorization state may have changed between the two invocations (the user revoked the permission in system settings, the session expired, the resource was released) — this is the concretization, in the permission-check context, of the classic "Time-Of-Check to Time-Of-Use" (TOCTOU) race pattern.*

- *Difference from E1*: E1 is "it checked, but checked the wrong target (the scope semantics do not correspond)"; E2 is "the target checked is not itself wrong, but the **moment** at which the check occurs is wrong — it relies on the residual result of some past check rather than the live state at the time of this invocation". E1's evidence is "the scope string does not match"; E2's evidence is "there exists a state flag that is reused across invocations and whose timeliness is not re-validated after being written" (this is structurally similar in code to pattern C1's "shared state field", but C1 concerns "the writer/reader permissions being unequal", while E2 concerns "whether the same permission-judgment branch's basis still reflects the true current authorization state as time passes" — the two may hit the same piece of code simultaneously; the perspectives and criteria differ and are not mutually exclusive).
- *Investigation method*: for any code branch that "checks some state flag / cached bit to decide whether permission has been granted, rather than re-triggering a live check every time", examine the **lifecycle** of that state flag — does it have an expiry mechanism, is it dynamically cleared when the permission is revoked externally (e.g. the user turns off some authorization in the system settings page), and is there a window between the clearing check and the actual use? If the state flag, once written, remains valid indefinitely with no mechanism for invalidation upon external permission change, it constitutes an E2 candidate.
- *Danger signals*: expressions such as "skip if already authorized" or "reuse the previous decision result" appear in functional documentation or code comments, and no corresponding invalidation / re-validation trigger point can be found.
- *Relation to axis-two "state/timing triggered"*: E2 is the concrete carrier, at the pattern level, of the "state/timing triggered" value newly added on axis two in this file — it reminds the analyst that besides **static** branch trigger conditions such as "different parameter values" or "different scene flags", "whether the timeliness of the judgment basis is correctly maintained when the same piece of code is invoked at different points in time" is itself an independent investigation dimension; one must not assume that an authorization state written once is permanently valid.

### Pattern F: Permission Consistency of Operation Branches on the Same Resource (New)

- Axis one: operation branch vs operation branch (same resource); Axis two: unrestricted; Axis three: can cover all three capability natures

**Definition**: patterns A-E all implicitly share one premise — the objects of comparison are "two **different** paths achieving the **same** capability goal". Pattern F addresses a different question: **the same logical resource has multiple operation branches (typically add/delete/modify/query, or read/write); is each branch's permission-protection strength commensurate with the risk it actually creates, and are they internally self-consistent with one another** — it does not require the branches to "achieve the same capability", but requires that the **relative ordering of protection strength** among branches stay consistent with the **relative ordering of risk**.

**F1: benign differentiation (positive example; record it but it does not constitute risk)** — the permission difference between operation branches properly reflects the difference in their real risks; even if "read has zero permission, write has strong permission" looks imbalanced on the surface, as long as it can be argued that the risk natures of the two genuinely differ (e.g. "the user actively discloses their own existing data on the spot" vs "silently and persistently writing into system-level public storage"), it should be recorded honestly as a positive case and not exaggerated into a flaw.

**F2: mismatch-risk type (must be evidenced and excluded per the presumption-of-guilt principle; must not default to F1)** — the permission difference among operation branches **cannot** be shown to be commensurate with the risk difference; typical situations include but are not limited to:
1. The effect of a low-protection branch can be reused as an **information bypass** for a high-protection branch (e.g. a nearly undefended "write/update" operation whose failure/success status can be probed repeatedly, thereby serving as an information-leakage bypass channel that indirectly achieves the "read/query" effect that should be protected by strong permission — i.e. "a write operation can serve as an information bypass for a read operation");
2. Some operation branch's **actual persistence / impact surface** is clearly underestimated — e.g. a "delete" operation appears to affect only local state but in fact cascades to other users' visible public data, yet is approved only by the protection standard for "local operations";
3. The operation branches of the same resource are scattered across different registration entries in the permission system: one branch is included in the privacy table / scope system while another semantically close branch is omitted (this overlaps with D2's "permission identifier mismatch"; the difference is that F2 emphasizes "alignment among branches within the same resource", while D2 emphasizes "miscategorization across functional domains").

*Investigation method: for any identified "resource" (a set of CRUD/multi-operation APIs around the same entity), list all its operation branches and their respective three-layer + link permission annotations; for any two branches `p_i`, `p_j`, if `p_i`'s protection strength is significantly lower than `p_j`'s, proactively ask "is `p_i`'s risk really lower than `p_j`'s" — one must not default to intuitions such as "read is lower risk than write" or "a seemingly minor operation is lower risk"; each must be argued one by one against the F1/F2 criteria, and the argument follows the presumption-of-guilt principle in `SKILL.md`, "Negative Conclusions and Pending-Decision Management" (default suspicion that a mismatch exists; F1 requires sufficient evidence; a negative conclusion must record the verification action performed).*

*Difference from pattern C*: pattern C compares "composed path vs single path" targeting the **same** capability; pattern F compares "different operation branches of the same resource", where each branch's goal is by itself **not** the same capability (read's goal is to obtain data, write's goal is to produce an effect), and F tests the **relative consistency of protection strength** rather than equivalence of capability. The two can coexist on the same resource without conflict (e.g. the "read" branch of a resource may itself compose with another resource's API to constitute a C-type flaw).

## 4. Unified Detection Procedure (An Operable Decision Program)

> This procedure is for Step 8 to execute, after completing the named investigation of each of patterns A-F, as one **cross-pattern systematic re-check**, ensuring that the investigation covered all combinations of the three classification axes rather than only the concrete patterns already named historically. Strict ordering is not required, but each step must leave a record of "investigated, with what conclusion"; one must not silently skip recording merely because no problem was found.

1. **Enumerate target capabilities**: for every observable capability `E` in the current functional domain (whether `ACQUIRE(F)` or `ACT(O)`), list the set of all paths `{p1, p2, ...}` known to implement `E` (or a subset of `E`), including single paths and known composed paths.
2. **Annotate each path's complete permission vector, and perform the vertical self-evidence decision (1.3b) first**: `R(p) = ⟨osGate(p), code(p), platform(p), user(p)⟩` — the annotation method for `osGate(p)`: check one by one along path `p`'s authorization-action chain whether there exists a system / host-app-level authorization premise whose "consent result is **not written into** the mini-program-level `<setting-API>().authSetting`"; if so, record `Present`; if not (all authorization actions land in authSetting and are already covered by the three layers), record `N/A`. If `osGate(p)=Present`, further verify whether `(code, platform, user)(p)` are all three empty — **if they are indeed all empty, then by 1.3b this path already independently constitutes flaw evidence and can be concluded directly, without waiting for / depending on finding a sibling path `p2` for horizontal comparison** (one must not default to "`osGate` is satisfied" ⇒ "`(code,platform,user)` is also established" — this default is precisely the hypothesis that must be actively falsified); only when `osGate(p)=N/A` or the three layers are not all empty does one need to turn to horizontal pairwise path comparison on axis one (1.3a) to judge whether a flaw exists. This order (vertical self-evidence first, then horizontal comparison) should be the default investigation order; the reason is given in §3·A2, "Two Independent Proof Paths".
3. **Axis-one scan (comparison grain)**:
   - For each pair of single paths, check whether they constitute an A/B/D/E-type flaw;
   - For any set of APIs in the functional domain whose "three-layer permissions are all empty", perform pairwise composition value/effect computation per pattern C's enumeration requirements, prioritizing the search for a C3-style named benchmark target;
   - For each identifiable "resource" (a set of multiple operation branches), check branch-by-branch, per pattern F, the relative consistency between protection strength and risk.
4. **Axis-two scan (trigger condition)**: for each identified path, besides checking its static permission annotation, additionally check — whether a branch bypass exists under a specific scene value (A1); whether a branch exists that depends on "state established by some past invocation, with no expiry/revocation linkage for that state" (E2).
5. **Axis-three scan (capability nature)**: determine which of `ACQUIRE`/`ACT-Hardware`/`ACT-Egress` each target capability is, and choose the corresponding equivalence decision method (data-acquisition class applies `EquivDegree` from `equivalence-path-validation-methodology.md`; hardware-control / network-output class uses the effect-consistency test of §4.4 below); one must not apply the six-dimensional data-value standard indiscriminately to control/output effects.
6. **Evidential exclusion**: for all "suspected flaw" candidates produced in steps 3-5, confirm one by one whether to exclude or retain them under the presumption-of-guilt principle (graded evidence + multi-round execution validation) in `SKILL.md`, "Negative Conclusions and Pending-Decision Management"; one must not conclude directly from this procedure's static investigation alone.

### 4.4 Effect-Consistency Test for Hardware-Control / Network-Output Capabilities (Extending the Scope of `equivalence-path-validation-methodology.md`)

The `EquivDegree` / information-unit folding system of `equivalence-path-validation-methodology.md` is designed for `ACQUIRE`-type capabilities (comparing the attribute sets each of two paths can derive). For `ACT`-type capabilities (effects acting on the external world, producing no returned data), the equivalence judgment should instead compare the **observable-feature set of effects** rather than the data-field set:

```
EffectEquivDegree(p1,p2) = |CommonObservableEffects(p1,p2)| / |AllObservableEffects(p1) ∪ AllObservableEffects(p2)|
```

where "observable effects" include: the physical/logical scope of the object acted upon (e.g. "which sectors of a tag are covered", "whether the range of destination IP/port sent to is restricted"), the reversibility of the effect, and whether the effect leaves an audit trail. The core question in judging whether two control-type paths constitute a flaw is "is the range of external effects `p1` can achieve fully covered by `p2`, while `p1`'s permission threshold is clearly lower" — for example, in the UDP case, `EffectEquivDegree(<udp-API>.send, <network-request-API>)` is close to 1 on the effect dimension "data leaves the device and reaches the external destination specified by the developer", while the permission vector shows a clear gap at the platform layer (UDP has no domain whitelist, request does).

## 6. Extension Mechanism: How to Propose a New Pattern (For Reference in Future Analyses)

If an analysis finds a candidate that cannot be classified into any existing cell of the table above, first try to answer the following four questions rather than directly declaring "a brand-new pattern discovered":

1. **Can it be located by three-axis coordinates**: does it fall on existing values on axis one/two/three, or does a new value need to be added on some axis? If all three axis values can be found in the existing lists, it is most likely a **new case** of some existing pattern rather than a new pattern (as mDNS is for A2).
2. **Does it satisfy at least one of the formal flaw decisions in §1.3a or §1.3b**: if taking the horizontal path (1.3a), can one explicitly write out `p1`, `p2` (or path groups), capability `E`, and at which link `R(p1)` and `R(p2)` differ? If taking the vertical path (1.3b, no `p2` needed), can one explicitly write out the concrete basis for `osGate(p)=Present` (which system/host-app-level authorization premise) and the concrete evidence that all three of `(code,platform,user)(p)` are empty (the respective verification results for Service dispatch route / privacy-declaration table / scope-judgment branch)? If no complete evidence chain can be written for either path, the candidate needs more code/documentation evidence before it can be characterized.
3. **What distinguishes it from the most adjacent existing pattern**: an explicit comparison is required (following the writing style of this file's E1 vs E2, and C vs F); one may not merely say "this is a new situation" but must precisely point out "which point the existing pattern's definition explicitly excludes and which this candidate happens to hit".
4. **Is a new classification axis needed, or only a new value on an existing axis**: only if the difference the candidate reveals cannot be expressed by the existing values of axes one/two/three (e.g. it involves a capability of an entirely new nature, neither data acquisition nor hardware control nor network output) should one consider adding a fourth classification axis; merely "a specific trigger form not seen before" usually only requires adding a value on axis two (as with this round's E2 / state-timing trigger), not an entire new axis.

Any new pattern/subtype/axis value must still follow the Step 13 "confirmation protection" flow of `SKILL.md`, and only after user confirmation may it be formally written into `api-composition-and-equivalence-channels.md` and this file.
