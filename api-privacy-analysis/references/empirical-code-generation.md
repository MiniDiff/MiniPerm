# Empirical Code Generation Rules (General)

> Goal: convert the **validation scenarios** produced by Step 9 (scenario construction and exploitation inference) (VF-\*; exploitation scenarios excluded — their technical premises are already covered by the validation scenarios, so no validation code is generated for them) into executable validation code. This rule **owns both design and implementation** — first design the operation procedure (which APIs are involved, in what order they are called, which stage is an asynchronous wait, which stage is expected to show an authorization action, and what decision conclusion each branch corresponds to), then write the concrete handler JS code and testPlan JSON accordingly. **The actual driving of code execution (IDE connection, QR scanning, batch orchestration, result collection, runtime debugging) belongs to Step 11 (execution and feedback)** — Step 11 relies on the `miniapp-autotest` skill, which is itself a pure execution engine with no ability to understand privacy-analysis methodology or author validation logic; therefore the code-authoring right must remain in this step (Step 10), performed by the role that actually made the method selection and knows how each validation method should be landed. The operation-procedure design is not an optional supplementary document but the reference basis for Step 11's execution — it determines the testPlan's wait durations / platform choice and how to interpret phenomena arising during execution (e.g. whether an authorization prompt at some node is expected). **Code generated by Step 10 is very unlikely to be correct on the first attempt** — first execution commonly reveals API signature deviations, selector mismatches, asynchronous timing problems, etc.; after a Step 11 execution failure it produces a structured error report that triggers the Step 10↔11 correction loop (at most 3 rounds), and this step must be able to receive the error report and perform a targeted fix.
>
> **This step receives two kinds of "rework" request, of different natures, which must be distinguished before handling (new; aligned with the qualitative-validation loop mechanism)**: (i) the **Step 10↔11 code correction loop** (described above) — the code did not correctly implement the established operation-procedure design, and the rework goal is "make the code correct", without changing the already-decided validation-method selection; (ii) **qualitative-validation-loop fall-back** — the code has executed correctly and genuine results were obtained, but the results themselves require additional validation steps (e.g. evidence strength insufficient, needing a stricter method / larger sample / additional control group), or the result was decided to require first returning to Step 9 to restructure the scenario (in which case Step 10 must wait for Step 9 to produce a new VF before taking effect again); the rework goal is "make the validation design more adequate", and the code itself was not previously wrong. On receiving a "fall back to Step 10" routing result, this step should first confirm that it is (ii) rather than (i) (checking against the basis in the "Error Report Format" section above), then decide whether to add a new validation method/protocol or merely adjust the parameters of an existing method (e.g. increase the sample size), rather than hunting for a concrete bug in the code as one would for (i). The full mechanism is in the "Qualitative-Validation Loop" section of `references/execution-and-feedback.md`.

## Core Positioning

| Dimension | Description |
|---|---|
| **Input source** | The validation-scenario (VF-\*) inventory produced by Step 9 (each scenario containing: APIs involved, invocation sequence, key parameters, preconditions, description of reachable data); **additional input in the correction loop**: the structured error report produced by Step 11 (with error classification, key logs, failure screenshot); **additional input in qualitative-validation-loop fall-back**: Step 11's "fall back to Step 10" routing result and its trigger basis (the result has excluded a code bug and requires adding/adjusting a validation method) |
| **Core task** | For each validation scenario: (i) match the most suitable validation method (①-⑨); (ii) design that method's **operation procedure** — listing in order which APIs/functions must be called, whether each step is synchronous or asynchronous, what signal an asynchronous step is expected to wait for (callback / user operation / system prompt), which node is expected to trigger an authorization action, and what observable phenomenon each of the success/failure/undecidable branches corresponds to; (iii) write the concrete handler JS code (with actual wait milliseconds, error handling) and testPlan JSON (with concrete platform/wait parameters) per the operation procedure. The three are output together as the "validation task sheet". In the Step 10↔11 correction loop, make a **minimal targeted fix** based on the error report (not modifying unrelated parts) and update the affected testPlan fields accordingly; in a qualitative-validation-loop fall-back, add a new validation method/protocol or adjust existing method parameters (sample size / control group), rather than fixing a bug |
| **What it does not own** | Not actually driving IDE/device execution of the code or collecting runtime results in this step — those low-level driving capabilities (connection management, QR scanning, batching, log collection) are Step 11's (execution and feedback) responsibility, relying on the `miniapp-autotest` skill; not proactively rewriting already-generated code outside the correction loop; **not making the routing decision "whether to fall back to Steps 8/9 to re-qualify/restructure the scenario"** — that decision is made by Step 11 under the qualitative-validation-loop criteria, and this step only executes the corresponding action upon receiving a "fall back to this step" result |
| **Output destination** | Two kinds of file are produced: (i) the validation task sheet (containing the operation-procedure design + scenario-registration code + embedded three-branch decision criteria, saved to `tmp/<domain>analysis-<YYYYMMDD>/`), (ii) the testPlan JSON (saved to `tmp/<domain>analysis-<YYYYMMDD>/`), delivered to Step 11 for execution; if the code did not correctly implement the design, Step 11 returns an error report and this step enters the Step 10↔11 correction loop to re-produce the corrected files; if the code executed correctly but the result requires additional validation, Step 11 falls back to this step under the qualitative-validation loop, and this step adds/adjusts validation methods and re-produces; the empirical result ultimately flows into Step 12 (tiered summary by data value) as the empirical basis for the ★★★ mark |
| **Distinction from other validation stages** | Step 7 (documentation-code cross-validation) performs a **static comparison** (documentation vs code); this rule performs **conversion of static findings into executable validation code** — addressing the need that "a path appears to exist from static code, but a runnable test is needed to verify it" |
| **Role in the correction loop** | This step is the "fixing end" of the correction loop — receiving Step 11's error report, analyzing the error classification (syntax/selector/runtime exception/timeout), making a minimal targeted fix, and re-producing the code. Do not rewrite the whole file; annotate each round's change with `// Round{N} fix:`. See the "Step 10↔11 Correction Loop" section of `references/execution-and-feedback.md` |

## Why Both "Design and Coding" Stay in Step 10 Rather Than Being Handed to Step 11

- **`miniapp-autotest` is a pure execution engine with no code-generation capability**: the skill provides generic low-level capabilities such as IDE connection, testPlan driving, and log/screenshot collection, and understands no privacy-analysis semantics of any concrete API. If the coding responsibility were placed in Step 11, Step 11 would need to re-acquire the domain knowledge of "which validation method to use, how to test this API" — which is precisely the work Step 10 has just completed; re-deriving it is both inefficient and prone to losing touch with the design intent.
- **The operation-procedure design still needs to be produced independently as Step 11's reference during execution**: judgments such as validation-method selection, invocation order, and "this step is expected to trigger authorization" are understandings of the tested API's behavioral semantics and are worth writing down explicitly before coding — so that when Step 11 encounters a phenomenon during execution (e.g. an unexpected authorization prompt at some node), it can judge against the design document "is this within expectations or anomalous" rather than guessing out of nothing; it also gives the testPlan's wait durations / platform choice an explicit, checkable basis, rather than a one-off decision by the code author that leaves no trace.
- **Debugging responsibility should also stay close to the code's owner**: since the code is authored by Step 10, implementation-level problems arising at runtime (syntax, selector, API signature, insufficient wait duration) should in principle return to Step 10 for fixing — but to reduce unnecessary round trips, Step 11 is allowed to fix **mechanical, low-risk** problems directly and retry (e.g. an obvious selector typo, or a wait time that by the operation-procedure design should obviously have been longer), without it counting as a full correction-loop round; only when the problem concerns the validation logic itself (e.g. a wrong decision condition on a high-value field, a misunderstanding of the invocation order) does it count as a formal Step 10↔11 correction-loop round.

> **Structure of this file**: Sections 1-7 are the working mainline — input validation scenarios judged `equivalent` (1) → **translate the scenario's DSL description field by field into validation code (2, core)** → code-generation conventions (3) → select a validation protocol per scenario (4) → procedure (5) → produce the task sheet and testPlan (6). **The appendix "Validation Protocol Details (9 Methods)" is a method toolbox, not on the mainline**, for consulting concrete implementation steps after a protocol is selected in Section 4.

## 1. Input: Validation Scenarios Judged equivalent

**Input threshold (important)**: this step accepts only the validation scenarios corresponding to comparison pairs whose equivalence judgment in Step 9 is **`equivalent`** — i.e. those for which all three hold: "two sequences achieving the target capability can be constructed horizontally", "a valid control can be formed vertically", and "a permission gap exists". Those judged `no_gap` (no permission gap) / `not_equivalent` (horizontal construction blocked) / `undecidable` (insufficient information) **do not enter this step**; exploitation scenarios likewise do not enter (their technical premises are already covered by the validation scenarios). The judgment results are in `_stageB_equiv_verdicts.md`.

**Each comparison pair corresponds to one independent scenario code and testPlan** — do not merge multiple comparison pairs into one scenario, so that Step 11 can count "whether it ran through, how many regenerations it took" at comparison-pair granularity (see the "Code Generation and Run Record Table" in `execution-and-feedback.md`).

For each validation scenario (VF-\*), extract the following information from Step 9's validation-scenario inventory as this step's input:

```yaml
scenarioId: <Step 9 validation scenario id, e.g. VF-{n}>
correspondingPair: <comparison pair id in _stageA_pairs.json, e.g. P1>
coreFactToValidate: <one sentence; a yes/no-answerable technical question of fact, from the VF template's "core fact to validate" field>
dslDescription: <the full scenario DSL produced by Step 9; see "DSL → Code Translation Relations" below>
apisAndSequence: <in order, including key parameter values; parameter values have already been filled in by Step 9 per parameter-sensitivity analysis>
transformBasis: <γ = (shared artifact, category A1/A2/A3, relation type B1/B2); determines code structure>
capabilityNature: <ACQUIRE | ACT-Hardware | ACT-Egress; determines whether data fields or observable effects are collected>
expectedData: <concrete fields and precision; for ACT-* types, the expected effect scope instead>
currentEvidenceStrength: <the evidence tier of the static code analysis conclusion — direct evidence / indirect support / speculation>
preconditions: <user state / environment / permission / page scene; including the initial state each side must be reset to before execution>
```

**Trigger conditions**: not all validation scenarios produced by Step 9 need validation code generated — this step is triggered only for scenarios satisfying any of the following:
- Evidence strength is "indirect support" or "speculation" (static code analysis insufficient to conclude; runtime confirmation needed)
- The scenario involves "whether a specific parameter value produces a special result" (pattern-three findings; parameter-matrix empirical testing needed)
- The scenario involves "cross-method state-coupling composed invocation" (invocation-sequence empirical testing needed)
- The scenario is marked as needing to supply ★★★ mismatch evidence to Step 12, but the current evidence is static code only

## 2. DSL → Code Translation Relations (Mainline)

The scenario DSL produced by Step 9 is the direct basis for coding in this step; each field translates per the table below, and **the test logic must not be re-derived**:

| DSL field | Translates to | Key points |
|---|---|---|
| `SCENARIO <id>` | A scenario key in the `SCENARIOS` object | The scenario ID must match the testPlan's selector rule (`#BtnScenario_{id}`) |
| `ARM <sideName>` | One execution branch inside the same handler (or an independent sub-function) | Both sides must execute sequentially in the same handler, so that device/account conditions are naturally identical |
| `SETUP <components and state>` | **State-reset** statements before execution | **Not omissible** — must eliminate side effects left by the previous side's execution (state written by the former side pollutes the latter side's observation); the same component instance must be reused |
| `AUTHZ <scope>=granted\|none` | Authorization pre-processing | Do not apply any extra authorization on the side under test; the reference side satisfies all authorization requirements. Under DevTools, cooperate with `--clear-auth` to clear authorization state |
| `CALL <api>(<params>)` | API invocation statement | **Fill parameters as given** — use the values already calibrated in the DSL, do not rewrite them yourself; the order of multiple `CALL`s strictly follows the DSL (the order for B1 dependency type may not be reversed) |
| `REGISTER <callback>` | Callback registration statement | Must be registered **before** the triggering invocation, otherwise a callback firing earlier than expected may be missed |
| `AWAIT <event>` | Asynchronous wait + **timeout fallback** | A timeout must be set (recommended to coordinate with the testPlan's `wait` duration); a timeout must be recorded as "not triggered", not silently skipped |
| `COLLECT <target>` | Result collection and `this._log()` output | ACQUIRE type collects data fields; ACT-\* type collects observable effects (scope / reversibility / audit trail). A3 type must **collect per side** (once for the trigger side and once for the callback side) |
| `EXPECT <expectedPhenomenon>` | Decision assertion | Corresponds to one branch of the three-branch decision criteria; decision wording follows Core Principle 9 of `SKILL.md` (use `√`/`×`/`!`, not colored emoji) |
| `FIELDS`/`TOLERANCE` under `COMPARE <A> vs <B>` | **Numeric comparison** logic of the two sides' results | Compare field by field per the field set; agreement within the error bound counts as consistent; **units of measure must also be unified** (e.g. coordinate system, distance unit) |
| `EFFECT scope/reversible/auditable` under `COMPARE` | Comparison logic for the two sides' **effect characteristics** | For ACT-\* types specifically; compares effect scope rather than data fields (see the ACT branch of protocol ②) |
| `VARIANT <id>` | **Another scenario registered independently** | The degraded control for B1 dependency type (omit the precursor, invoke the successor alone); a separate testPlan is required, so run-through status can be counted separately from the main scenario |

**Translation principle**: Step 9 has already completed all structural decisions in the DSL (what to call, with what parameters, in what order, what to collect, by what convention to compare, how to set authorization, in what environment to compare); this step **only performs a faithful "DSL → JS" translation** and does not change semantics. If a gap is found in the DSL itself (e.g. a necessary wait point is missing, a parameter value is obviously unusable), one should **return to Step 9 to fix the DSL**, not privately add a different logic in the code — otherwise what is empirically validated is no longer the scenario Step 9 claimed.

## 3. Code Generation Conventions

### 3.1 Safety Boundary (Inheriting Core Principle 7 of SKILL.md)

Generated validation code must obey the following constraints:
- **Allowed**: code used for observation — detecting `authSetting` changes, recording returned data, capturing error codes, comparing data equivalence, measuring timing
- **Forbidden**: attack implementation code that could actually complete fraudulent transactions, forge identity-verification results, or intercept or replay real communications
- **Safety notice in code comments**: the generic template header already presets a safety notice comment (see lines 1-6 of `miniapp-autotest/assets/testpage-template/index.js`); scenario-registration code generated by Step 10 need not add it again

### 3.2 Code Generation Template Conventions

> **The generic template is already provided by the `miniapp-autotest` skill** (`.codebuddy/skills/miniapp-autotest/assets/testpage-template/`), deployed to `.codebuddy/skills/miniapp-autotest/assets/testproject/pages/AutoTest/`. **Step 10 no longer needs to regenerate `.wxml` / `.wxss` files — the template dynamically renders all registered scenarios via `wx:for`.**

Step 10 only needs to generate the **scenario-registration code block**, written into `index.js` between `// ==================== scenario registration ====================` and `// ==================== end scenario registration ====================`.

**SCENARIOS registration format (example)**:
```javascript
// ==================== scenario registration ====================
var SCENARIOS = {};

SCENARIOS['VF-1'] = {
  title: 'VF-1: permission equivalence validation',
  desc: 'validate whether authSetting changes after invoking some API',
  methodTags: ['①'],
  handler: async function(sid) {
    var baseline = await this._getAuthSetting();
    this._log(sid, 'baseline: ' + JSON.stringify(baseline));
    // ... API invocation ...
    var after = await this._getAuthSetting();
    if (!this._diffAuth(baseline, after).unchanged) {
      this._log(sid, '× vulnerability does not exist');
    } else {
      this._log(sid, '√ vulnerability exists');
    }
  }
};
// ==================== end scenario registration ====================
```

**Template built-in helpers** (`this._log` / `this._getAuthSetting` / `this._diffAuth` / `this._sleep`, etc.): already implemented in the generic template; no need to redefine. See `references/template-guide.md` of `miniapp-autotest`.

## 4. Validation Protocol Selection (Method by Scenario)

Different types of validation scenario need different validation methods. The table below maps the core-unknown characteristics of validation scenarios (from the equivalence-channel pattern mapping in Step 9 §1.1) onto the validation protocols of this toolbox:

| Validation scenario characteristic | Core question to validate | Corresponding validation method | Method ID |
|---|---|---|---|
| Scenario describes "a no-permission / low-permission API silently obtained high-value data" | Did the permission list really not change after this API invocation? Was the data really returned? | Permission-trace comparison + parameter-matrix comparison | ①+⑥ |
| Scenario describes "API A is equivalent to API B but with different permissions" (equivalence channel) | Do A and B really return equivalent data / achieve equivalent effects under the same conditions? Are their permission-check paths really different? (If A/B are `ACT`-type with no data returned, switch to the ACT branch of protocol ②, comparing observable effects rather than data fields — see protocol ② below) | Control-group comparison | ② |
| Scenario describes "a hidden / undocumented API invocation entry exists" | Is this entry really callable at runtime? | Existence detection | ③ |
| Scenario describes "the permission check has a timing weakness (the check occurs after data return / data can be extracted before the check)" | Is the order of data return and permission check as the hypothesis states? | Timing-marker method | ④ |
| Scenario describes "data bound to a private instance was obtained indirectly through a component / mount point", or "some component's internal code appears (e.g. via `<view-data-writer>`) to expose high-value data to JS, but this is not yet empirically confirmed" | Can this component instance be accessed via `selectComponent` at runtime? Can the independent API invoked inside the component be called directly, detached from the component? (The two questions need separate validation; see the "two-level reachability" extended protocol of method ⑤) | Component / mount-point reachability probing | ⑤ |
| Scenario describes "a specific parameter value triggered different data return or bypassed permission" | Is there a substantive difference in returned data under different parameter values? Does the permission-check path stay unchanged? | Parameter-matrix comparison | ⑥ |
| Scenario describes "two low-permission APIs composed in a specific order produce high-value data" (composed invocation) | Does the target API's behavior/return value differ under different invocation sequences? | Invocation-sequence sensitivity testing | ⑦ |
| Scenario describes "usable long-term / unlimited times after one-time authorization" | Does the time interval / event interval after authorization trigger re-validation? | Session-persistence testing | ⑧ |
| Scenario describes "no rate limit; data can be obtained in bulk / at high frequency" | Is high-frequency repeated invocation really unrestricted? | High-frequency repeated invocation testing | ⑨ |

If one validation scenario hits several characteristics simultaneously (e.g. "a specific parameter value bypassed permission, and the permission list indeed leaves no trace"), multiple methods should be used in combination, but each method corresponds to an independent validation task; do not use one test to validate multiple hypotheses simultaneously.

## 5. Analysis Procedure

1. **Scenario filtering**: from the validation-scenario inventory produced by Step 9, filter by the "trigger conditions" the scenarios needing validation code generated (not all validation scenarios need validation code; see "Trigger conditions" above).
2. **Method matching**: for each scenario to be validated, determine the validation methods to use per the "validation scenario → validation method" mapping table (one scenario may need a combination of several methods).
3. **Operation-procedure design**: fill the scenario information into the corresponding method's "input" field, and design the concrete operation procedure — listing in order:
   - Which APIs/functions need to be called (including key parameter values, citing the concrete values Step 9 provides)
   - Whether each step returns synchronously and immediately, or is asynchronous and needs waiting (what is being waited for: callback firing / user physical operation / system prompt / network round trip)
   - Which node is expected to show an authorization / prompt action, and whether it appears before or after the invocation
   - What observable phenomenon each of the success / failure / undecidable branches corresponds to
4. **Code generation**: generate executable test code per the operation-procedure design — using the **scenario-registration mode** of the `miniapp-autotest` skill (see `.codebuddy/skills/miniapp-autotest/references/template-guide.md`):
   - **Scenario-registration code**: register `SCENARIOS['{scenarioId}']` in the "scenario registration" region of `.codebuddy/skills/miniapp-autotest/assets/testproject/pages/AutoTest/index.js`; each scenario's `handler` function contains the validation code logic (use `this._log(scenarioId, msg)` to record logs); the code must faithfully translate the invocation order and authorization-node decision logic of the operation-procedure design
   - **testPlan JSON**: save to the analysis task's `tmp/<domain>analysis-<YYYYMMDD>/testPlan_{scenarioId}.json`; the button selector uses the `#BtnScenario_{scenarioId}` rule; the `wait` duration is determined from the asynchronous wait target annotated in the operation-procedure design together with the internal timeout actually set in the code (do not copy another scenario's default value)
   - Decision criteria are output via `this._log()`, embedded in the logical branches of the handler code
   - `.wxml` and `.wxss` **do not need regenerating** — the generic template's `index.wxml` dynamically renders all registered scenarios via `wx:for` and is already fully automatic
   - **Clear before injecting code (mandatory; appending is strictly forbidden)**: before writing into the `SCENARIOS` region of `index.js`, first check whether it already contains code — this includes both **leftovers from the previous task** and **scenarios generated in earlier batches of this task**. **If so, clear it entirely before injecting this batch of code**, merging clearing and filling into one single edit; if empty, fill it directly.
     **Appending after old code is strictly forbidden**: when testing multiple functions consecutively, appending each time makes `index.js` accumulate continuously, causing the code volume to bloat, single executions to slow down, and logs and results to become hard to attribute to a specific scenario. When several scenarios must be executed together, they should be **injected in one batch**, not appended across multiple passes.

> **Subsequent steps**: after code generation, Step 11 (execution and feedback) actually runs it in the WeChat developer tool (DevTools / real device) via `.codebuddy/skills/miniapp-autotest/auto.js`, interpreting phenomena and configuring execution parameters at runtime by reference to the operation-procedure design given by this step. **First execution will most likely have errors** — if Step 11 returns a structured error report, this step enters the Step 10↔11 correction loop (at most 3 rounds) and, based on the error report, makes a targeted fix and re-produces the code and testPlan; the empirical result ultimately enters Step 12 (tiered summary by data value) as the empirical basis for the ★★★ mark. The full correction-loop mechanism is in `references/execution-and-feedback.md`.

## Task-Sheet Reception and Code Generation Prompt (Step 10)

> This section is downstream of Step 9's "Scenario Instantiation and Task Sheet Prompt" (`scenario-construction-and-exploitation.md`): it receives the **scenario description** (filled template) and the **task sheet (TaskBrief)** produced by Step 9, and in one invocation produces the **operational steps (operation-procedure design)** and the **code (scenario-registration block + testPlan)**.

# Appendix: Validation Protocol Details (9 Methods)

> This appendix is a **toolbox of validation methods**, not on the working mainline. The mainline is the "DSL → code" translation (Section 2); this appendix is for consulting each protocol's concrete implementation steps, decision criteria, and common pitfalls after a protocol is selected in Section 4.
> Protocol numbers ①-⑨ match the "corresponding method (id)" column of Appendix A in `scenario-construction-and-exploitation.md`.

> Uniform protocol structure: **input → preconditions → operational steps → validation-success decision → validation-failure decision → undecidable situations → result-explanation template**. "Validation success" means "the validation-scenario hypothesis is confirmed (vulnerability exists)", "validation failure" means "the validation-scenario hypothesis is falsified (vulnerability does not exist or is unreachable)", and "undecidable" means the test method is inapplicable under the current conditions and the method must be changed or tests supplemented.

### ① Permission-Trace Comparison — Validating the "zero-permission silent acquisition" hypothesis

- **Applicable scenario**: the validation scenario claims "an attacker can obtain the target data without triggering any authorization prompt and without leaving a trace in the permission list"
- **Input**: the invocation statement of the target API (including the parameter values specified in the validation scenario); the platform's "granted permission list" query interface (e.g. `<setting-API>()`)
- **Preconditions**: clear the historical authorization records of this functional domain; record the baseline permission list before invocation
- **Operational steps**: 1) query and record the baseline permission list 2) invoke the target API (using the parameters specified in the validation scenario) 3) record the returned data / observed effect (ACQUIRE type records returned data; ACT type records whether the effect occurred, e.g. whether recording really started, whether a file was generated) 4) query the permission list again and compare field by field
- **Validation-success decision** (vulnerability exists): after invocation the permission list shows **no change at all**, and **(ACQUIRE type) the returned data does contain the high-value field claimed by the validation scenario / (ACT type) the claimed effect did occur** — i.e. "data obtained (or effect achieved), no trace left"
- **Validation-failure decision** (vulnerability does not exist or is unreachable): after invocation the permission list **gained a related field** (trace left), or **(ACQUIRE type) the returned data does not contain** the high-value field claimed by the scenario / **(ACT type) the claimed effect did not occur** (data/effect unreachable)
- **Undecidable situations**: the platform has no queryable permission-list interface; or the returned data errored due to environment/insufficient permission, but a test-environment problem cannot be excluded
- **Result-explanation template**: `after invoking {API}, the permission list {gained / did not gain} the field {fieldName}; the returned data {contains / does not contain} {the claimed high-value field} → {vulnerability exists / does not exist / undecidable}`

### ② Control-Group Comparison — Validating the "equivalence channel" hypothesis (with ACQUIRE/ACT dual-branch protocol)

- **Applicable scenario**: the validation scenario claims "API A (low/no permission) can obtain / achieve data / effects equivalent to API B (high permission)"
- **Capability-nature routing (preliminary judgment, mandatory)**: first judge whether A and B's target capability is `ACQUIRE`-type (substantive data returned to the JS layer after invocation, e.g. location coordinates, user info) or `ACT`-type (only an effect produced on the external world after invocation, with no substantive data returned, e.g. `<record-start-API>` starting camera recording, `RecordManager` starting audio recording, NFC card writing / HCE response) — the criterion is in `data-value-framework.md`, "Two Parallel Analysis Threads". **The two types follow entirely different branch protocols and may not be mixed**:

#### ACQUIRE Branch (data-acquisition class; original protocol)

- **Input**: the API A under test (low-permission path); the control API B (high-permission path, already confirmed at the code level to access the same data source)
- **Preconditions**: confirm that control API B can normally obtain its data in the current environment (baseline confirmation); invoke the two APIs in the same environment and the same time window in sequence (**paired controlled experiment design**; see `equivalence-path-validation-methodology.md` Section 3.1 — prefer environment injection of a fixed true value, then temporal proximity pairing, and additionally invoke the same API twice separately to obtain its own noise baseline)
- **Operational steps**: 1) invoke control API B, record the structure and precision of the returned data 2) invoke the API A under test (using the parameter values specified in the validation scenario), record the returned data 3) **dispatch the corresponding statistical method by data type** and compare field by field (continuous numeric uses TOST equivalence testing + Bland-Altman agreement analysis; discrete/identity type uses exact matching; composite/transform-requiring type is first converted into a comparable representation via known transformations — the full dispatch table is in `equivalence-path-validation-methodology.md`, Section 3) 4) compute `EquivDegree` (the equivalence measure; see the formula in Section 2 of that file) rather than merely giving a binary "equivalent / not equivalent" conclusion
- **Validation-success decision** (equivalence vulnerability exists): the core equivalence set `C(A,B)` is confirmed non-empty by statistical testing, and A's permission-check path is **clearly weaker or empty**; the `EquivDegree` / `WeightedEquivDegree` values and directionality (whether `Δ(A→B)` / `Δ(B→A)` are symmetric) must be recorded in full, not merely reporting the conclusion word "equivalent"
- **Validation-failure decision** (equivalence does not hold): the TOST test failed (the confidence interval exceeds the tolerance bounds), or the core equivalence set is empty, or A and B's permission-check paths are **the same** (indicating no permission mismatch)
- **Undecidable situations**: control API B itself cannot run normally in the current environment (an environment problem, not attributable to A); or the sample size is insufficient so the TOST confidence interval is too wide (see `equivalence-path-validation-methodology.md`, Section 8, Challenge 5; annotate "sample insufficient" rather than directly judging "not equivalent")
- **Result-explanation template**: `control API {B} returned data = {...}; API under test {A} returned data = {...}; core equivalence set C = {...}; EquivDegree = {0-1 value}; TOST result = {...}; permission path comparison: A = {...}, B = {...} → equivalence-channel vulnerability {exists / does not exist}`
- **Knowledge-completion action (mandatory; see `equivalence-path-validation-methodology.md`, Section 6)**: after each execution of this method, a "knowledge completion record" must be produced, stating this round's empirical results on the validation / calibration / discovery of the relevant edges in the derivability graph (`knowledge/derivability_graph.json`), to be aggregated by Step 12 and to trigger the Step 13 confirmation flow

#### ACT Branch (hardware-control / network-egress class; new; aligned with `unified-theory-equivalence-and-permission-flaws.md` §4.4)

- **Input**: the API A under test (low-permission effect path); the control API B (high-permission effect path, already confirmed at the code level to act on the same hardware / the same class of external effect)
- **Preconditions**: confirm that control API B can normally trigger its effect in the current environment (baseline confirmation, e.g. can start recording normally, can write a card normally); a paired experiment cannot rely on "returned data", and **observable-effect-feature collection points** must instead be designed — the output path / duration / resolution of the recording file, the readable read-back verification of the tag content after card writing, whether the network packet's destination IP/port is restricted, etc.
- **Operational steps**: 1) trigger control API B's effect and record its **observable effect feature set** (`AllObservableEffects(B)`: the physical/logical scope of the object acted upon, the reversibility of the effect, whether an audit trail / system prompt is left) 2) trigger the API A under test's effect and likewise record its observable effect feature set 3) compare the intersection and difference of the two feature sets item by item, not "data fields" (because there are no data fields to compare) 4) compute `EffectEquivDegree(A,B) = |CommonObservableEffects(A,B)| / |AllObservableEffects(A) ∪ AllObservableEffects(B)|` (the formula is defined in `unified-theory-equivalence-and-permission-flaws.md` §4.4)
- **Validation-success decision** (equivalence vulnerability exists): `EffectEquivDegree` is high (the range of effects A can achieve is essentially fully covered by B; the two are the same class of effect at bottom), and A's permission-check path is **clearly weaker or empty** — e.g. both A and B can start the camera to continuously capture frames and produce a video file, but A's scope check is silently substituted / missing
- **Validation-failure decision** (equivalence does not hold): `EffectEquivDegree` is low (the effect ranges A and B achieve differ essentially, e.g. significant differences in object scope / reversibility), or A and B's permission-check paths are **the same**
- **Undecidable situations**: control API B cannot genuinely trigger its effect in the current environment (e.g. real hardware missing; the simulator does not support real camera/NFC actions) — **one must not therefore downgrade an ACT-type validation scenario to "code-layer comparison only" and accept an exclusion conclusion**; it should be transferred into Step 11's "real-device follow-up list" and handled per the graded evidence standards of `SKILL.md`, "Negative Conclusions and Pending-Decision Management"; one must not judge "does not exist" merely because it cannot be triggered
- **Result-explanation template**: `control API {B} observable effects = {...}; API under test {A} observable effects = {...}; common effect set = {...}; EffectEquivDegree = {0-1 value}; permission path comparison: A = {...}, B = {...} → equivalence-channel vulnerability {exists / does not exist}`
- **Key differences from the ACQUIRE branch**: this branch **does not produce** `EquivDegree` / TOST / Bland-Altman statistics (those quantities are meaningful only for paths with returned data), and **does not trigger** the knowledge-completion action for `derivability_graph.json` (that graph's nodes are defined as "semantic attributes", and ACT-type effects do not constitute semantic-attribute nodes) — if a candidate has both ACQUIRE and ACT effects (e.g. a method that both records and returns some metadata), it should be split and the two branches taken separately, producing two independent result explanations, not merged into one general conclusion

### ③ Existence Detection — Validating the "hidden entry" hypothesis

- **Applicable scenario**: the validation scenario claims "some API does not exist in the documentation / is not public, but is genuinely callable at runtime"
- **Input**: the suspected API name / path string
- **Preconditions**: no special preconditions
- **Operational steps**: execute `typeof <targetIdentifier>` in the target runtime environment (or the platform's equivalent runtime symbol-detection statement)
- **Validation-success decision** (the hidden entry genuinely exists): the return value is `"function"`
- **Validation-failure decision** (the entry is unreachable): the return value is `"undefined"`
- **Undecidable situations**: the platform's type system does not support direct runtime detection (e.g. a strongly typed language errors at compile time) — substitute means such as consulting the symbol table / decompiling are needed
- **Result-explanation template**: `typeof <name> returned {function/undefined} → this entry is {reachable/unreachable}`

### ④ Timing-Marker Method — Validating the "permission timing weakness" hypothesis

- **Applicable scenario**: the validation scenario claims "data can be obtained before the permission check completes" or "the check is post-hoc"
- **Input**: the target API invocation statement; the observable signals of the permission check being watched (system prompt, second callback, error-callback timing)
- **Preconditions**: able to record / observe millisecond-level key timestamps
- **Operational steps**: 1) record T0 (the instant the invocation is issued) 2) record T1 and the result in the success/fail/complete callback 3) if a permission prompt is observed, record the prompt appearance time T2 and the callback time T3 after the user's action 4) compare the time order
- **Validation-success decision** (timing weakness exists): the success callback (containing the high-value data claimed by the validation scenario) occurs at T1, while the permission prompt / check occurs at T2 (later than T1), or the permission check was not triggered at all
- **Validation-failure decision** (timing is normal): the data in the success callback has already been desensitized / emptied by the permission check, and the permission prompt unlocked before the data callback
- **Undecidable situations**: the timing difference is at millisecond level and the platform's callback mechanism itself has uncertainty — multiple repetitions are needed to obtain a stable pattern
- **Result-explanation template**: `T0={...}, T1(success)={...}, T2(prompt)={...}; callback order: {data returned first / prompt appeared first / no prompt appeared} → timing weakness {exists / does not exist}`

### ⑤ Component / Mount-Point Reachability Probing — Validating the "component bypass" hypothesis (with the "two-level reachability" extended protocol)

- **Applicable scenario**: the validation scenario claims "a private method bound to a native component can be invoked indirectly through the page component instance, thereby obtaining data"; or the validation scenario is "some built-in / custom component internally invokes a platform API, and it must be validated whether a developer can genuinely reach the privacy data that API processes" (the latter must be validated at the two levels separately per the "two-level protocol" below — the component itself and the API it invokes internally; one may not conclude after testing only one level; the decision basis is in the "Reachability Determination for Component-Specific APIs" section of `doc-code-cross-validation.md`)
- **Input**: the name of the method suspected to be bound to the native component; the component's CSS selector in the page; if the two-level protocol is involved, also the name of the independent platform API invoked inside that component
- **Preconditions**: the page/component has completed `<lifecycle-ready-hook>`; the target component has been rendered in the page (for Layer 1 of the two-level protocol, the component must be placed in the test page's wxml and given a selectable `id`)

**Layer 1 Protocol (whether the component's own methods / `data` are readable)**:
- **Operational steps**: 1) `const comp = this.selectComponent(selector)` 2) `this.<selector-query-API>().select(selector).fields({node:true,id:true,dataset:true},cb).exec()` 3) if comp is non-null, attempt to read the keys and content of `comp.data`, and attempt to invoke the target method
- **Validation-success decision** (bypass feasible): `selectComponent` returns non-null, the `fields` result **contains** a `node` field, and `comp.data` is non-empty or the target method can be invoked successfully and returns the data claimed by the validation scenario
- **Validation-failure decision** (not bypassable): `selectComponent` returns null, or the `fields` result **does not contain** a `node` field (composited by the native rendering layer; no instance on the JS side) — **in this case, even if the code shows that the component internally has a `<view-data-writer>` call writing seemingly sensitive fields, it should thereby be determined not bypassable; one may not assume "bypass succeeded" merely from a `<view-data-writer>` in the code**
- **Undecidable situations**: `selectComponent` returns non-null but the target method errors — the method signature may need extra parameters; consult the rendering-layer code to complete the parameters and retry
- **When the same component tag family has multiple type / sub-component variants**: place a test anchor for each variant separately and execute this protocol separately, as cross-confirmation (even if one variant has been confirmed isolated and safe, empirical testing of the other variants may not be omitted, because different variants may have entirely different underlying implementations — see the "open-data component family" case in that section of `doc-code-cross-validation.md`)
- **Result-explanation template**: `selectComponent={non-null/null}, fields.node={present/absent}, comp.data={content/empty}, method invocation={succeeded + returned data / failed + error reason} → {bypassable / not bypassable}`

**Layer 2 Protocol (whether the independent API invoked inside the component can be called detached from the component; new)**:
- **Operational steps**: 1) execute `typeof wx.<API name>` in the test page's ordinary business code (not going through any component) and record the result 2) if it is `"function"`, invoke that API directly (placeholder / valid test parameters are acceptable) and record the `authSetting` difference before and after the invocation (reusing protocol ①, permission-trace comparison) 3) if it is `"undefined"` or the direct invocation errors, record that phenomenon and **do not determine "unreachable" directly**
- **Validation-success decision** (this API constitutes an equivalence channel independent of the component): `typeof` is `"function"`, the direct invocation succeeds and returns the data claimed by the validation scenario, and `authSetting` shows no change (or, per its permission model, it can be triggered in an unintended way)
- **Validation-failure decision** (this API indeed cannot be invoked independently of the component, at least in the current environment): `typeof` is `"undefined"` or the direct invocation raises `TypeError`, and other non-component paths (e.g. aliases / forwarding methods) have been checked and confirmed unreachable
- **Undecidable situations (important; the most common result at this level)**: `typeof` is `"undefined"`, but it cannot be excluded that "the current runtime mode / scene does not satisfy the mounting conditions" (e.g. a special mini-program launch mode is required) rather than "this API can architecturally only be invoked inside the component" — in this case annotate honestly "! undecidable: evidence insufficient, a runtime-mode gate is suspected; supplementary testing is recommended in an environment that can simulate that runtime mode"; one must not, because Layer 1 (the component itself) has been determined unreachable, proceed to also classify Layer 2 as "unreachable" — the two evidence chains are independent
- **Result-explanation template**: `typeof wx.{API name} = {function/undefined}; {direct invocation succeeded and returned data / invocation errored: error message}; authSetting change = {yes/no} → {independently reachable / unreachable / undecidable (with reason)}`

> The Layer 1 part of this protocol originates from a real correction case in which a component method definition was misjudged as extractable (case details in `doc-code-cross-validation.md`); the Layer 2 part originates from the re-check correction of that case on 2026-08-13 — after Layer 1 determined the component unreachable, the independent API invoked inside that same component (`<group-member-API>`) still needed separate Layer 2 validation, and ultimately, due to current test-environment limitations, could only be annotated "undecidable" rather than directly reusing Layer 1's conclusion. The detailed decision basis of the two-level protocol is in the "Reachability Determination for Component-Specific APIs" section of `doc-code-cross-validation.md`.

### ⑥ Parameter-Matrix Comparison — Validating the "parameter-triggered equivalence" hypothesis

- **Applicable scenario**: the validation scenario claims "the API can obtain data equivalent to another higher-permission API under some specific parameter value" (pattern-three findings)
- **Input**: the target API name; the key parameter value specified in the validation scenario; the comparison reference API (high-permission path)
- **Preconditions**: able to keep all conditions other than the target parameter constant
- **Operational steps**: 1) invoke the target API with the parameter value specified in the validation scenario, recording returned data A 2) repeat invoking with other parameter values (including default / boundary values), recording returned data B 3) invoke the reference API (high-permission path), recording returned data C 4) compare A vs B (whether the parameter drives a value change) and A vs C (whether it is equivalent to the high-permission path)
- **Validation-success decision** (parameter-equivalence vulnerability exists): A's data precision / fields are highly equivalent to C's, and the permission-check path was not escalated by the different parameter value
- **Validation-failure decision** (vulnerability does not exist): A and B have no substantive difference (the parameter does not drive a value change), or A and C have a substantive difference (not equivalent), or the parameter value triggered a higher permission check
- **Undecidable situations**: the parameter value specified in the validation scenario itself causes the invocation to fail directly (an illegal boundary value)
- **Result-explanation template**: `with parameter {scenario value} data = {...}; with parameter {default value} data = {...}; reference API data = {...} → equivalence with the reference API: {equivalent / not equivalent}; permission change: {yes/no} → parameter-equivalence vulnerability {exists / does not exist}`

### ⑦ Invocation-Sequence Sensitivity Testing — Validating the "composed-invocation escalation" hypothesis

- **Applicable scenario**: the validation scenario claims "two (or more) low/no-permission APIs, composed in a specific order, can obtain high-value data that no single API can obtain"
- **Input**: the API set in the validation scenario (≥2); the invocation order specified in the validation scenario
- **Preconditions**: able to control independently whether and in what order each API is invoked; able to reset related state (e.g. restart the mini-program / clear cache)
- **Operational steps**: test and compare results under at least 4 sequences: a) invoke only the downstream API (without first invoking the upstream) b) invoke in the order specified by the validation scenario c) the reverse sequence d) invoke the downstream after using empty / illegal parameters for the upstream
- **Validation-success decision** (composed escalation exists): in sequence (b) the downstream API's behavior / return value / data volume is **significantly better** than in sequence (a) (single invocation), and the difference has statistical stability
- **Validation-failure decision** (composed escalation does not exist): regardless of sequence, the downstream API's behavior is **always identical** (no state coupling)
- **Undecidable situations**: external environment fluctuation makes repeated tests of the same sequence unstable — repeat several times and take the majority result; if still unstable, annotate honestly
- **Result-explanation template**: `sequence (a) = {...}; sequence (b) = {...}; sequence (c) = {...}; sequence (d) = {...} → composition improvement magnitude: {obvious / no difference / environmental noise} → composed-invocation escalation vulnerability {exists / does not exist}`

### ⑧ Session-Persistence Testing — Validating the "persistent exploitation window" hypothesis

- **Applicable scenario**: the validation scenario claims "after obtaining authorization once, it can be exploited continuously over a long subsequent period / across many sessions, with no need for re-authorization"
- **Input**: the API with an established authorization / session state; the downstream API depending on that state; the exploitation-window event claimed by the validation scenario (e.g. "after switching pages", "after closing and reopening the mini-program")
- **Preconditions**: first establish an authorization / session state in the manner described by the validation scenario
- **Operational steps**: 1) invoke the downstream API immediately after establishing the state, confirming the baseline is normal 2) after undergoing the interval event claimed by the validation scenario, invoke the downstream API again 3) check whether re-authorization is required
- **Validation-success decision** (persistent exploitation window exists): after the interval event the downstream API **still succeeds** in returning complete data, and re-authorization / a prompt was not triggered
- **Validation-failure decision** (the window is not persistent): after the interval event the downstream API **fails or triggers re-authorization**
- **Undecidable situations**: the interval event itself causes the session to be forcibly cleared by the platform (an invalidation condition already stipulated in the documentation) — in this case the result cannot be attributed to a "permission design defect"
- **Result-explanation template**: `baseline (immediate invocation) = {success/failure}; after the interval {event specified by the validation scenario}: {success/failure/re-authorization required} → persistent exploitation window {exists / does not exist}`

### ⑨ High-Frequency Repeated Invocation Testing — Validating the "unrestricted bulk collection" hypothesis

- **Applicable scenario**: the validation scenario claims "no rate limit; data can be collected in bulk / at high frequency within a short time"
- **Input**: the target API; the collection frequency / count expectation implied by the validation scenario
- **Preconditions**: understand whether the documentation already states an explicit rate-control description, as a comparison baseline
- **Operational steps**: within the time window implied by the validation scenario, invoke the target API N times consecutively at the frequency expected by the validation scenario, recording each success/failure and the returned data
- **Validation-success decision** (unrestricted bulk collection holds): all N consecutive invocations **succeed** in returning complete data, with no rate-control / quota errors and no data degradation
- **Validation-failure decision** (a limit exists): after some number of invocations a rate-control / quota error appears, or the returned data shows downgrading / desensitization
- **Undecidable situations**: N was set without reaching the platform's true threshold — in this case "no rate control observed" **cannot** be equated directly with "no rate control exists"; only the bounded conclusion "not observed within N invocations" can be drawn
- **Result-explanation template**: `invoked {N} times consecutively, from the {k}th invocation {error/degradation} began; or: all {N} invocations succeeded (no rate control observed within N invocations)`
