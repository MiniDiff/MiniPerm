# Data Value Judgment Framework (Portable Skill-Builtin Version)

> This file is the general reusable version of the data-value judgment framework and contains no application cases for any specific domain (location, user profile, etc.). When analyzing, read this file in full to bring in context; do not copy it to the project root, and do not check whether a same-named file already exists there (if an earlier analysis left a same-named historical file in the project root, this file takes precedence — just keep using it, there is no need to maintain two copies).
>
> **Relationship to the permission-layering framework**: `permission-layering-framework.md` answers "which approval gates must be crossed to obtain this datum" (code layer / platform layer / user layer); this file answers "once the datum is obtained, how much actual privacy weight / harm potential does it carry for the individual". The two are **orthogonal** dimensions; every API analysis must complete both sets of judgments separately before cross-comparing them — see the cross-comparison method at the end.

## Core Judgment Dimensions (Six Dimensions; General Standard; Applies to All API Types)

Do not judge data value merely from an API name or from whether it "sounds sensitive" in the documentation. Check the implementation code item by item and evaluate comprehensively along the following six dimensions:

| Dimension | Criterion | Value gradient (from high value to low value) |
|---|---|---|
| 1. Authenticity / tamper-resistance | Who produces the datum; can the data subject deliberately falsify its content | (i) Produced by system/hardware measurement (the user cannot falsify the content, only consent to or refuse collection); (ii) Issued by the server (may already be desensitized/fuzzed, but the client cannot falsify it); (iii) Actively entered or chosen by the user on the spot (authenticity is entirely at the user's discretion and may be untrue) |
| 2. Precision / recoverability | Degree of information loss between the datum and the "true state", and whether extra processing is needed to recover usable information | (i) Raw, unprocessed value (least information loss); (ii) Systematically reduced-precision / fuzzed / noised (essentially the same, but the platform actively limited the information content); (iii) Indirect form, requiring external resources (database reverse lookup, preinstalled mapping table) to recover the target information; (iv) Semantic/textual description only, not recoverable to the precision of (i)/(ii) |
| 3. Timeliness / persistence | Whether the datum reflects a static snapshot at one instant or can continuously track an individual over time | (i) Continuous / real-time stream (can track an individual's state changes over the long term and infer behavior patterns; highest information density); (ii) Single snapshot, but repeatable indefinitely at low cost (equivalent to continuous collection); (iii) Single snapshot, subject to rate limiting / caching / throttling (repeat acquisition has visible cost or delay); (iv) One-shot consumable (the state changes after acquisition, so it cannot be obtained again under the same conditions) |
| 4. Acquisition cost / friction | The interaction/decision cost that the user or system must pay extra each time the datum is actually obtained | (i) Zero interaction cost (no prompt, no awareness, silent acquisition); (ii) One-off interaction cost then infinitely reusable (e.g. readable long-term / in background after a single authorization); (iii) Each acquisition requires independent user interaction (e.g. a prompt each call demanding on-the-spot consent) |
| 5. Identifiability / association strength | Whether the datum can be strongly linked to a specific natural person or device, or remains only at the aggregate/anonymous level | (i) Directly linkable to a specific natural person's current real-time state; (ii) Linkable to a specific device/account, but not real-time (historical/derived value); (iii) Presented only at the aggregate/statistical level, not locatable to a specific individual |
| 6. Derivability / information primacy | Whether the datum can serve as input to derive other downstream information in one direction, or is itself a terminal product derived from more upstream data | (i) Source / primordial type — largest information content; can serve as input to derive downstream information at multiple granularities; (ii) Intermediate type — itself processed/dimension-reduced from more upstream data, yet can still derive finer-grained downstream information; (iii) Terminal type — can only be back-derived from more upstream data; its own information content has been compressed to the point that it cannot derive anything with greater information content than itself |

**How to use**: for each API (including each parameter invocation form), locate its value gradient on each of the six dimensions. The more the six dimensions collectively lean toward the "high-value gradient" side, the higher the datum's overall value. The six dimensions need not agree; when "one dimension is very high and another very low", state that imbalance honestly in the conclusion — this is precisely where cross-comparison with the permission dimension earns its keep.

**Mandatory check rule for dimension six (derivability conservation law)**: if datum A can derive/map datum B in one direction (given A, B can be computed or inferred with high probability, but the reverse usually cannot precisely recover A from B alone), then A's value gradient **must be no lower than** B's — that is, "the value of data upstream in an information chain ≥ the value of the downstream derived data". This is a mandatory ordering check independent of the other dimensions; one must not misjudge downstream data as more valuable than the upstream source merely because its "name/literal meaning looks more concrete and more sensitive". Investigation method: for any two APIs/fields at different information granularities within the same group or the same target data chain, check whether the output of one can serve as derivation input to the output of the other; if a one-directional derivation relation exists, verify that their value-gradient ordering satisfies "upstream ≥ downstream", and if the ordering is inverted, re-examine whether the earlier tiering judgment was wrong.

## Auxiliary Judgment Rules (Signals/Heuristics; Assist Tiering and Cross-Validation; Do Not Replace the Six-Dimension System)

Beyond the six core dimensions, the following empirical regularities are often used in practice for fast initial judgment or cross-checking of value tiers. When using them, note: **they are "generally holding correlation signals", not independently sufficient conditions**; final tiering must still rest on the systematic six-dimension assessment.

1. **Permission-protection correlation rule (positive correlation signal)**: the higher the permission-protection layer a datum enjoys (especially data requiring on-the-spot user-layer consent and requiring static declaration/review at both the code and platform layers), the more likely it is that the platform/review system has already recognized it as high-value — because the permission framework is itself a consensual encoding of the industry's view of data sensitivity. The "completeness of the three permission layers" can be used as one reference signal for value judgment: data requiring all three layers tends initially toward higher value; data with all three layers empty tends initially toward lower value. **But this signal must never replace independent judgment**: in reality, numerous "same value, different permission" mismatch cases prove that this correlation can be broken; inferring value tier directly from permission-layer height would systematically miss every mismatch scenario — which is exactly why this framework requires judging separately from the permission-layering framework and cross-comparing afterward (see the cross-comparison method at the end).
2. **Privacy-sensitivity subjective weighting rule (subjective dimension; depends on social consensus / regulatory enumeration)**: even when two pieces of data score similarly on the six objective dimensions, if one class is explicitly listed as sensitive in social perception or regulatory enumeration (e.g. biometric information, religious belief, specific identity, medical/health, financial accounts, whereabouts trajectories, and other "sensitive personal information" enumerated in personal-information-protection regulations), its value judgment should be subjectively raised above the objective six-dimension score. This rule acknowledges a "social-consensus sensitivity" component in value judgment that cannot be fully quantified by any single objective formula; the analysis should state explicitly that "the objective six-dimension score is X; because it falls in a regulated sensitive category, it is raised subjectively to Y", keeping the reasoning traceable rather than dismissing it with a blanket "very sensitive".
3. **Derivability conservation law**: see dimension six; it is a mandatory ordering check within the six-dimension system, not an optional auxiliary signal. Listed here only as a cross-reference.
4. **Irrevocability / unchangeability weighting rule**: whether the data subject can subsequently change or reset the datum to reduce continuing risk after it has leaked or been misused is an important reference for value judgment — data that is harder to change (e.g. biometrics, national ID numbers, which are essentially irrevocable for life) should have its value raised appropriately even if other dimensions score middling; data that is easier to change (e.g. phone number, a resettable account password) carries shorter-lived risk even if obtained, and can be treated as a countervailing factor.
5. **Propagation / association amplification rule**: if a single datum can serve as an "anchor" for association and matching against multiple other data sources (e.g. device unique identifier, phone number), it can greatly amplify the privacy risk surface (one leak affects multiple associated scenarios); treat this as a value amplification factor on top of the six dimensions. The judgment method matches "composability/additivity" in the Additional Dimension Notes, with the coupling object extended from "state fields" to "the concatenation of multiple independent low-value fields"; enumerate it just as actively and do not skip it merely because a single field's tier is low.

## General Value Tiering Standard (Six Tiers; Cross-Domain; Wording May Be Adapted per Domain, but Tier Count and Relative Order Do Not Change)

```
Tier 1: Continuous / streaming data — can track an individual's complete state over time; highest information density; allows inferring behavior patterns and life routines
Tier 2: Single high-precision raw data — value/content closest to the true state, unprocessed; one invocation yields the core information
Tier 3: Processed, reduced-precision / fuzzed data — essentially the same origin as Tier 2, but the platform actively limited the information content
Tier 4: Indirectly reverse-lookupable / mappable data — the data form itself is not directly the target information; requires external resources / preinstalled mappings to reverse-derive
Tier 5: User actively generated / disclosed data — content authenticity is not guaranteed by the system; the user decides on the spot whether and what to disclose
Tier 6: No data / pure control flow — produces no new information; used only for flow control or pure geometric / pure rendering computation
```

**Mandatory checks when tiering (to avoid isolated tiering and missing combination effects)**:
1. Different parameter invocation forms of the same API must be tiered **separately**; one must not assign a single tier to the whole API (tier row by row per the "parameter form × data-value matrix" in `parameter-analysis.md`);
2. APIs identified as having a shared-state / composed-invocation relationship (per `data-flow-analysis.md`, Sections 3.1/3.2) must be re-tiered by "the actual combined effect" rather than keeping the tiers from their isolated invocations — the tier of a composed invocation can only **rise** or **stay the same**; one must not judge the combination as low merely because both APIs look low when taken apart;
3. When multiple acquisition paths exist for the same target datum (including cross-domain / cross-category paths, per `api-composition-and-equivalence-channels.md` pattern D), as long as they can recover information at the same tier, the paths should be placed at the **same tier**, even if the API names, categories, and documentation sections are entirely different.

## Additional Dimension Notes (Do Not Change the Tier Itself; Annotate Separately in the Analysis)

- **Coverage / information density**: within the same tier, a path returning several associated fields at once has higher information density than one returning a single field; this can be distinguished within the tier by ★ count, but does not by itself raise the tier;
- **Composability / additivity**: certain low-tier data (e.g. device info + network info + timestamp) may, once combined, indirectly raise identifiability through statistical/fingerprinting techniques, effectively rising to a higher tier — the judgment method matches "value non-additivity enumeration" in `data-flow-analysis.md`, Section 3.2, except that the coupling object extends from "state fields" to "the concatenation of multiple independent low-value fields"; enumerate it just as actively and do not skip it merely because individual fields are low tier.

## Cross-Comparison with the Permission-Layering Framework (Core Output)

Data-value judgment is not an end in itself; its value lies in **cross-comparison** with the three-layer permission annotation of the permission-layering framework, producing a "data-value tier × three-layer permission" matrix that highlights the following two classes of mismatch:

1. **Same value, different permission**: data at the same tier (even the same concrete value/content) has multiple acquisition paths, but the three-layer permission requirements of those paths differ sharply — the highest-priority risk type in review assessment, marked ★★★;
2. **Same permission, different value**: two APIs with identical three-layer permission annotation actually yield data of sharply different value tiers — indicating that the granularity of the existing permission framework is insufficient to distinguish real risk; supplement the explanation in the permission analysis document, marked ★★.

**Star-rating usage rules (to avoid semantic drift)**: ★★★/★★ are **mismatch-type labels**, corresponding uniquely to mismatch classes 1 and 2 above respectively; they are **not** intensity indicators of "how severe the mismatch is", and they are not interchangeable with the ★ count used in the Additional Dimension Notes to denote information density (different meaning, different context). Severity differences among cases of the same type (e.g. "fully silent acquisition" is more severe than "user actively discloses but the gate is lower") must be distinguished in **prose**, not implied by adding or removing stars. The annotation format is uniformly "★★★/★★ + a parenthetical brief of the mismatch type"; writing only stars without prose is forbidden, and inconsistent star counts for cases of the same type are not allowed.

2. The sections "Core Judgment Dimensions", "Value Tiering Standard", and "Cross-Comparison Method" themselves **should not be rewritten per domain**; modify them only when a defect in the framework itself is found or a new dimension must be added (modifications follow the confirmation-protection flow of Step 13 in the skill's `SKILL.md`). All other domain differences belong in the "Application Cases" section of the respective analysis report and are not written back into this file.

## Two Parallel Lines of Analysis: "Data Acquisition" vs "Hardware Control / Output" (New; Important Scope Note)

The six dimensions of this file (authenticity / precision / timeliness / acquisition cost / identifiability / derivability) and the six-tier standard are all **designed for "data"** — that is, for cases where an API invocation **returns** some information to the developer/mini-program. But some hardware-management APIs are essentially "**manipulating hardware to produce a real effect on the outside world, without returning any new data**", for example: `vibrateLong` / `vibrateShort` (pure hardware output, no data returned), `Ndef.writeNdefMessage` (overwrites tag content; the effect acts on an external entity rather than returning to the mini-program), and HCE's `sendHCEMessage` (responds to an external reader; the effect is "what the counterpart reads", not "what we obtained"). For such APIs the six dimensions / six-tier standard **cannot be applied directly** (for instance, the "authenticity / tamper-resistance" dimension asks "can the data be tampered with", whereas these APIs are themselves "the instrument of the tampering act" — the dimension definition is mismatched).

**Recommended handling**:
1. First judge whether the API is "data acquisition" or "hardware control / output" (criterion: does the invocation return substantive new information to the mini-program's JS layer; if it merely "triggers some state change in the external world" with no substantive return, classify it as the latter);
2. "Hardware control / output" APIs do not enter the six-tier data-value system; instead describe them in the analysis report using **independent risk dimensions**: (i) what real effect the manipulation capability can produce externally (e.g. "overwrite someone else's tag content", "respond to a payment terminal query"); (ii) whether that effect is reversible / traceable (e.g. write operations are usually irreversible and leave no trace); (iii) the permission gate required to trigger the effect (still judged by the three-layer permission framework, the same one used for data-acquisition APIs — only the six dimensions / six tiers are not applied);
3. If a single API has both "acquiring data" and "controlling output" effects (e.g. in HCE read/write scenarios some methods can both read and write), split the two effects and handle them separately; do not merge them into a single vague conclusion.

**Boundary with Steps 1/2 (new)**: the distinction in this section between "data acquisition" and "hardware control / output" **only affects how Step 12 should describe the API; it does not affect whether Steps 1/2 should include it**. "Hardware control / output" is not the same as "unrelated to the target domain" — as long as the API shares a documentation directory, a code file, or a permission-mapping-table group with already-confirmed members of the target domain (i.e. domain membership as defined by Core Principles 3a/3a-1 of `SKILL.md` holds), Steps 1/2 should judge it confirmed even if it returns zero data after invocation. **Failure mode to guard against**: when analyzing a domain, map-view / WiFi-control style APIs (values supplied by the developer, zero data returned) (WiFi module control) should have been judged confirmed at Step 1 and then, at Step 12, described separately under this section's control/output handling; instead, Step 1's semantic judgment excluded them early using this section's own criterion of "whether location data is returned", causing these 28 genuinely relevant APIs to be missing from Step 1 onward, leaving Steps 3-6 / Step 8 / Step 12 unable to cover them. The correct order is: **Steps 1/2 first include by domain membership → Step 12 then applies this section's criteria to decide whether to use the six-tier score or independent risk dimensions**; one must not work backwards and use this section's classification result to decide inclusion at Steps 1/2.
