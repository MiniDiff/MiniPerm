# Mini-Program Automated Test Framework (miniapp-autotest)

> **Positioning**: a generic WeChat mini-program API runtime testing framework. Not bound to any concrete API or analysis scenario; reusable by the empirical-testing stage of any analysis workflow (privacy analysis, performance analysis, functional validation, etc.).

## Core Capabilities

| Capability | Description |
|---|---|
| **IDE automated connection** | Connects to the WeChat developer tool via `miniprogram-automator`, supporting the DevTools simulator and real-device remote debugging |
| **TestPlan driven** | All test steps are defined by external JSON (`wait` / `tap` / `screenshot` / `assert` / `evaluate`, etc.); the engine hard-codes nothing |
| **Batch execution** | Supports consecutive execution of multiple comma-separated testPlans, auto-generating an aggregated Markdown report |
| **Fault self-healing** | On IDE connection failure, automatically force-cleans processes and retries (up to 3 times, with progressive backoff) |
| **Log + screenshot collection** | Captures console logs and page screenshots throughout, archived by step number |
| **Generic test-page template** | Provides a data-driven scenario-registration-mode template; any API test needs only to inject a scenario handler |

## When to Use This Skill

- Need to validate some API's actual behavior at mini-program runtime (permissions, return values, callback timing, etc.)
- Need to execute multiple test scenarios in batch and auto-generate a report
- The "empirical validation" step of any workflow (not limited to privacy analysis)

## Decision-Text Symbol Conventions

When outputting decision conclusions via `this._log()` in a scenario `handler`, **do not use any colored emoji icon** (not limited to warning triangles / check marks / crosses — any emoji may render abnormally in some terminals, editors, and IDEs). Use plain text / symbols uniformly: `!` for warning / undecidable, `√` for holds / vulnerability exists, `×` for does not hold / vulnerability does not exist; semantics with no fixed symbol (e.g. event fired, waiting, summary) are rewritten as `[bracketed text label]`. Circled method numbers (`①`-`⑨`, etc.) are plain-text symbols and are not subject to this rule. See the "Decision-Text Symbol Conventions" chapter and its example code in `references/template-guide.md`.

### Result Directory Naming and Grouping Rules

1. **Single run**: lands directly in `TestResult/<testName>_<timestamp>/`, with `<timestamp>` fixed to the format `YYYYMMDD_HHMMSS` (auto-generated by `auto.js`; no intervention needed).
2. **Multiple testPlans belonging to the same validation task / batch** (e.g. VF-1 / VF-2 / VF-3 and other scenarios under the same analysis task): when invoking `auto.js`, **explicitly pass the task-specific `--result-path`**, so that all of that batch's output (each run directory, `last_result.json`, `batch_report_*.md`) lands automatically in the same group subdirectory — **do not move and merge manually after execution completes**:
   ```bash
   --result-path "autotest/TestResult/<domain>-<YYYYMMDD>"
   ```
3. **Group directory naming**: `<domain>-<YYYYMMDD>`; the date must use the **full 8-digit year-month-day** (never short unpadded forms like `8-5` / `8-11` — short forms sort wrongly in lexicographic order, e.g. `"8-11"` would sort before `"8-5"`).
4. **Pairing with the `tmp/` side**: if that validation task has a corresponding analysis-process directory under `tmp/` (e.g. `tmp/<domain>analysis-<YYYYMMDD>/`), then the `<domain>` string must be **exactly the same** as on the `tmp/` side (suffixes such as "analysis" / "test" may distinguish the nature, but the head word and the date must not change), ensuring that the directory name alone shows both sides belong to the same task. See the intermediate-artifact and result-material management rules of the `api-privacy-analysis` skill.

## Quick Start

### 1. Prepare the Test Code

Inject the scenario code produced by the analysis workflow's Step 10 (code generation) into `assets/testproject/pages/AutoTest/index.js`:

```javascript
// ==================== scenario registration ====================
// register your test scenarios in the SCENARIOS object
// each scenario contains: title, desc, methodTags, prerequisites, handler

SCENARIOS['MyScenario'] = {
  title: 'scenario title',
  desc: 'scenario description',
  methodTags: ['①', '②'],       // validation method ids (optional)
  prerequisites: 'precondition notes',
  handler: async function(scenarioId) {
    // your test logic
    this._log(scenarioId, 'test starting');

    // record the baseline permission state
    const baseline = await this._getAuthSetting();
    this._log(scenarioId, 'baseline: ' + JSON.stringify(baseline));

    // invoke the target API
    // wx.someApi({ ... });

    // output the decision result
    this._log(scenarioId, 'decision: vulnerability exists: ...');
  }
};
```

### 2. Create the testPlan JSON

```json
{
  "name": "MyScenario_permission-validation",
  "description": "validate some API's permission behavior",
  "entryPage": "pages/AutoTest/index",
  "steps": [
    { "id": "S1", "name": "wait for page load", "type": "wait", "ms": 3000 },
    { "id": "S2", "name": "entry screenshot", "type": "screenshot" },
    { "id": "S3", "name": "tap the test button", "type": "tap", "selector": "#BtnScenario_MyScenario" },
    { "id": "S4", "name": "wait for the test to complete", "type": "wait", "ms": 8000 },
    { "id": "S5", "name": "result screenshot", "type": "screenshot" }
  ]
}
```

> **Button selector rule**: in the template each scenario's button id is `#BtnScenario_{scenarioId}` and the result area id is `#Result_{scenarioId}`.

### 3. Execute the Test

```bash
# run at the workspace root (all paths relative to the workspace root)

# single scenario
node .codebuddy/skills/miniapp-autotest/auto.js --clear-auth --auto-authorize \
  --test-project-path ".codebuddy/skills/miniapp-autotest/assets/testproject" \
  --test-plan-path "./testPlan_MyScenario.json"

# batch multiple scenarios (recommended; --result-path groups by task, avoiding scattered results)
node .codebuddy/skills/miniapp-autotest/auto.js --batch --clear-auth --auto-authorize --retries 3 \
  --test-project-path ".codebuddy/skills/miniapp-autotest/assets/testproject" \
  --test-plan-path "./plan1.json,./plan2.json" \
  --result-path "autotest/TestResult/<domain>-<YYYYMMDD>"

# using run_all.bat (accepts multiple testPlan path arguments)
.codebuddy\skills\miniapp-autotest\run_all.bat plan1.json plan2.json
```

### 4. View Results

After the test completes, a timestamped subdirectory is generated under `autotest/TestResult/` (or the specified group subdirectory), containing `console.log`, `step_results.json`, `summary.json`, and all screenshots. Batch mode additionally generates `batch_report_*.md`.

## Real-Device Testing Mode (RealDevice)

Running tests on a real device can validate behavior the simulator cannot cover (e.g. real authorization prompts, Bluetooth hardware, NFC).

### Preconditions

- WeChat base library version >= **2.7.3**
- Computer and phone on the **same LAN**
- Phone WeChat logged in
- Already debugged successfully in the developer-tool simulator

### Execution

**Method one: modify the variables at the top of `run_all.bat` (recommended)**

```bat
:: top of run_all.bat
set PLATFORM=RealDevice
set REMOTE_TIMEOUT=120
```

Then run `run_all.bat testPlan1.json` normally. The script will automatically:
1. Launch the IDE and connect the WebSocket
2. Output a QR code to the WeChat developer tool console
3. Wait for you to scan it with WeChat (up to 2 minutes)
4. After a successful scan, automatically execute all tests on the real device

**Method two: use the CLI directly**

```bash
# run at the workspace root
node .codebuddy/skills/miniapp-autotest/auto.js \
  --batch --clear-auth --auto-authorize --retries 3 \
  --platform RealDevice \
  --remote-timeout 180000 \
  --test-project-path ".codebuddy/skills/miniapp-autotest/assets/testproject" \
  --test-plan-path "tmp/<domain>analysis-<YYYYMMDD>/testPlan_VF-1.json,..." \
  --result-path "autotest/TestResult/<domain>test-<YYYYMMDD>"
```

### QR-Code Scan Timeout Handling

- Default wait 120 seconds (2 minutes), adjustable via `--remote-timeout`
- On timeout it errors out and exits (it does not degrade to DevTools, ensuring data comes from the real device)
- If timeouts are frequent, first manually enable "real-device debugging" in the developer tool, then run the script

### Cautions

- After a real-device connection, wait an extra 5 seconds for the page to fully synchronize
- `--clear-auth` has no effect on a real device (real-device authorization state is managed by phone WeChat)
- Automatic permission-prompt clicking (`--auto-authorize`) may not fully automate on a real device
- In real-device mode, assertion-text checks may fail due to rendering differences; relax them appropriately

## TestPlan Operation Types

| Type | Required fields | Description |
|---|---|---|
| `relaunch` | `page` | Restart the mini-program and navigate |
| `tap` | `selector` | Tap an element |
| `input` | `selector`, `value` | Enter text |
| `scroll` | `selector`, `scrollTop` | Scroll |
| `screenshot` | — | Explicit screenshot |
| `wait` / `delay` | `ms` | Wait |
| `evaluate` | `fn` | Execute a JS function |
| `assert` | `assertSelector`, `assertText` | Assert the element text contains |
| `callMethod` | `method`, `args` | Invoke a Page method |

## Built-in Helper Methods of the Generic Test Page

The template `index.js` provides the following helpers, usable directly in a scenario `handler`:

| Method | Description |
|---|---|
| `this._log(scenarioId, msg)` | Record a log into that scenario's log area |
| `this._getAuthSetting()` | Return the current `wx.getSetting()` authSetting (the clean version processed by `_extractAuthData`) |
| `this._diffAuth(before, after)` | Compare two authSettings, returning `{ added, changed, unchanged }` |
| `this._hasAuthChanged(before, after)` | Check whether authSetting has changed (boolean) |
| `this._isNonAuthError(err)` | Judge whether an error is non-permission-class (e.g. unsupported by DevTools) |
| `this._sleep(ms)` | Promise-based delay |

## Template Button and Result-Area ID Rules

The template renders scenarios dynamically via `wx:for`. Each scenario's DOM IDs are:

- Button: `BtnScenario_{scenarioId}`
- Result: `Result_{scenarioId}`
- Log: `Log_{scenarioId}`

A testPlan's `selector` must use these naming rules. For example, with scenario ID `VF-1`:
- `"selector": "#BtnScenario_VF-1"`
- `"assertSelector": "#Result_VF-1"`

## Collaboration Mode With Upper-Layer Skills

This skill is a **low-level generic framework**, containing no test logic for any concrete API and no code-generation capability — this skill is a pure execution engine. An upper-layer skill (e.g. `api-privacy-analysis`), on top of this skill:

1. designs the operation procedure in its Step 10 (empirical code generation), and writes scenario-registration code per this skill's template → `assets/testpage-template/` — **the code-authoring responsibility lies with the upper-layer skill's Step 10, because this skill itself does not understand the privacy-analysis validation logic of concrete APIs**
2. before generating scenario code, **first checks whether `index.js`'s `SCENARIOS` region holds leftovers from the previous task** — if so, clear it entirely before filling in this run's scenarios (clearing and filling are merged into one single edit, not split); if empty, fill it directly
3. generates the testPlan JSON (button IDs following the template rules; `wait` durations determined from the operation-procedure design and the code's actual internal wait logic), persisting to `tmp/<domain>analysis-<YYYYMMDD>/`
4. in its Step 11 (empirical execution), deploys the code generated by Step 10, invokes this skill's `auto.js` to execute tests (run from the workspace root), and passes via `--result-path` the group directory `autotest/TestResult/<domain>test-<YYYYMMDD>/` paired by name with the tmp side
5. collects results from that group directory; on execution anomalies, first judge whether it is a "mechanical minor problem" (Step 11 fixes and retries directly) or "concerns the validation logic itself" (return to Step 10 to fix the code), triggering the Step 10↔11 correction loop
6. **immediately after the correction loop terminates, copy and archive the `SCENARIOS` code** into the corresponding `tmp/` analysis directory; `index.js` is **not cleared for now** and the code is kept as-is, to be cleared and replaced uniformly at the next new task's Step 10 (returning to item 2 of this list)

> The directory naming and archiving rules for both `tmp/` (intermediate artifacts: analysis documents, testPlans, scenario-code archives) and `autotest/TestResult/` (result artifacts: logs, screenshots, summary) are defined by the upper-layer skill; this skill only guarantees that the `--result-path` parameter is passed and used correctly, and does not decide the grouping policy itself.
>
> **`index.js` is the active test page shared by all analysis tasks**; this skill does not automatically archive or clear `SCENARIOS` after test execution ends (`auto.js` only executes the given scenarios and does not manage scenario-code lifecycle). Therefore **the responsibility for archiving and clearing lies with the caller, and the two happen at different times**: once a test task has definitively ended, **immediately** copy the `SCENARIOS` region's code into `tmp/` to archive it (guaranteeing a deterministic archive independent of later events), but **do not clear** `index.js` — leave it for the next new task's Step 10 to generate code, merging clearing with "injecting new scenario code" into one single operation and replacing then, avoiding `index.js` sitting in a meaningless empty-scenario state for long. The concrete archiving flow and timing are defined by "Stage 4: Code Archiving" in the `api-privacy-analysis` skill's `references/execution-and-feedback.md`; other upper-layer skills reusing this skill should likewise follow the same principle of "archive immediately, defer clearing to the next task".

## Known Runtime Compatibility Issues

`auto.js` may encounter two classes of known system-environment compatibility problem during `automator.launch()`. Their shared feature is that **the error message does not match the actual root cause**, easily misleading users into repeatedly investigating unrelated items. `auto.js` has built-in precise diagnostic hints — output only when an error actually occurs.

### Issue One: Node.js v20+ Causes cli.bat spawn Failure

| Dimension | Content |
|---|---|
| **Error symptom** | `Error: Failed to launch wechat web devTools, please make sure cliPath is correctly specified` |
| **Actual root cause** | Node v20+ fixed [CVE-2024-27980](https://nodejs.org/en/blog/vulnerability/april-2024-security-releases), tightening `child_process.spawn()` behavior for `.bat` files (requiring `shell: true` to invoke them properly), while `miniprogram-automator`'s `Launcher.js` internally uses `spawn()` without the `shell` option, so the `cli.bat` process cannot be created correctly. |
| **Misleading direction** | Seeing "cliPath is correctly specified", users repeatedly check / modify the cliPath and reinstall the developer tool |
| **Correct fix** | Switch to Node.js v18.17.1 (verified working) |
| **auto.js built-in diagnostic** | Matches the error text `Failed to launch wechat web devTools.*cliPath is correctly specified`, outputting the current Node version and a switching suggestion |

### Issue Two: Outdated miniprogram-automator Version Causes CLI Argument Syntax Incompatibility

| Dimension | Content |
|---|---|
| **Error symptom** | `Error: Failed to launch wechat web devTools, please make sure http port is open` |
| **Actual root cause** | Old `miniprogram-automator` versions (<0.10.0) assemble **v1 CLI syntax** inside `Launcher.js`: `cli --auto <path> --auto-port <port>` (project path as a positional argument). Newer WeChat developer tool CLIs have upgraded to **v2 syntax**: `cli auto --project <path> --auto-port <port>` (requiring an explicit `--project`). The old-style command is rejected by the new CLI (code 31: missing parameter project/appid), so the project is not opened and the automation port is not listening. |
| **Misleading direction** | Seeing "http port is open", users toggle "service port" in IDE settings and investigate firewalls / port occupancy |
| **Correct fix** | Upgrade `miniprogram-automator` to v0.12.1 or higher: `npm install miniprogram-automator@0.12.1` |
| **auto.js built-in diagnostic** | Matches the error text `http port is open`, reads `miniprogram-automator/package.json` for the current version, and outputs an upgrade suggestion |

### Design Principle Behind Both Diagnostics

Both diagnostics follow the strategy of "**output only when an error occurs, no proactive warning at startup**":

1. Newer environments (Node v22+) may have compatibility fixed in later system upgrades, so proactive checking at startup would produce stale warnings;
2. The same error text may also be triggered by other legitimate causes (e.g. the IDE service port genuinely not open); only combined with version information can it be determined whether it falls in this issue's scope;
3. It avoids redundant output during normal runs, which would interfere with viewing test results.

> The complete diagnostic process, source-level root-cause analysis, and manual verification commands for both issues are in the workspace's `runtime-toolbox-and-harm-inference-interim-plan.md` (Scheme Three) and `DevTools-automation-protocol-Page-domain-hang-feedback-report.md`.
